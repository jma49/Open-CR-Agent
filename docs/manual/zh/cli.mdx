## ocra init

为当前所在的仓库写入 `.ocra/config.json`（加 `--github` 时再写入 `.github/workflows/ocra.yml` 和 `.github/workflows/ocra-commands.yml`），然后打印剩下要做的事。它不调用任何模型或网络服务，不会运行 `gh`，运行 `git` 也只是为了找到仓库根目录（`git rev-parse --show-toplevel`）。

```bash
ocra init                          # 按环境里的 key 写 .ocra/config.json
ocra init --github                 # 同时写 GitHub workflow，可安全审查来自 fork 的 PR
ocra init --github --same-repo-only
ocra init --provider anthropic     # 当前 shell 里没有这个供应商的 key 时指定它
```

| 参数 | 含义 |
|---|---|
| `--github` | 同时写入 `.github/workflows/ocra.yml`，即 `pull_request_target` 上的[fork 方案](./github#来自-fork-的-pr)：成员和协作者的 PR 每次推送都审查，其他人的 PR 在维护者每次加上 `ocra-review` 标签时审查；只检出 base 分支，不运行 PR 里的任何东西；还会写入 `.github/workflows/ocra-commands.yml`，即[评论工作流](./github#评论工作流)：`@ocra review` 重新审查 PR，其他 `@ocra` 提及会得到回答 |
| `--same-repo-only` | 与 `--github` 一起用，改写普通的 [`pull_request` workflow](./github#github-action)。它跳过来自 fork 的 PR，它们在那里拿不到 secret |
| `--provider <name>` | `gemini`、`anthropic`、`openai` 或 `openrouter`，代替从环境里找到的 key |
| `--force` | 替换已有文件。不加时保留已有文件，并说明保留了 |

**模型。** 不加 `--provider` 时，ocra init 依次查找 `GEMINI_API_KEY`、`ANTHROPIC_API_KEY`、`OPENAI_API_KEY`、`OPENROUTER_API_KEY`，用第一个已设置的，并列出找到的其他 key；只有没有其他 key 时才选 OpenRouter。它为每一档写一个模型：

| 供应商 | `top` | `standard` | `light` | 运行时 |
|---|---|---|---|---|
| `gemini` | `google/gemini-3.1-pro-preview` | `google/gemini-3.5-flash` | `google/gemini-flash-lite-latest` | `opencode` |
| `anthropic` | `anthropic/claude-opus-5-5` | `anthropic/claude-sonnet-5-5` | `anthropic/claude-haiku-4-5` | `opencode` |
| `openai` | `openai/gpt-6-sol` | `openai/gpt-6-sol` | `openai/gpt-6-luna` | `opencode` |
| `openrouter` | `router/openrouter/free`，OpenRouter 在其[免费模型](./providers#openrouter-上的免费模型)之间挑选的路由 | 同左 | 同左 | `direct` |

对 OpenRouter，它会提示：质量不稳定，免费模型不适合私有代码，账号没有充值时大的审查可能用完每日请求数。

**运行时。** 只有在 `direct` 运行时上真实测试过的 OpenRouter 会配置成 `direct`：配置设置 `"runtime": "direct"`，以价格 0 声明端点，workflow 传 `opencode: false`，ocra 安装约 11 MB 而不是 175 MB。其他供应商仍用默认运行时 `opencode`，配置里写的是 OpenCode 目录中的模型，价格由 OpenCode 自己计算；ocra init 会链接到[选择运行时](./providers#选择运行时)。`--github` 保留了一个没有设置 `direct` 的已有配置时，workflow 会安装 OpenCode。

以 Gemini 为例，写出的文件是：

```json
{
  "$schema": "https://raw.githubusercontent.com/ocrahq/Open-CR-Agent/main/docs/schema/config.v1.json",
  "models": {
    "top": "google/gemini-3.1-pro-preview",
    "standard": "google/gemini-3.5-flash",
    "light": "google/gemini-flash-lite-latest"
  }
}
```

key 本身从不写入文件；OpenCode 从 `GEMINI_API_KEY` 读取它。模型可以像其他[配置](./configuration)一样修改。

**workflow** 就是 [GitHub](./github) 页面里的方案：key 作为 secret，每次审查 `--max-cost-usd 2`，direct 运行时下加 `opencode: false`，Action 固定到本发布版本的提交（`actions/checkout` 也按提交固定）。`ocra init --github` 随后打印：

```text
Wrote .ocra/config.json: Gemini models through GEMINI_API_KEY, on the OpenCode runtime.
  OpenCode makes the install about 175 MB; to switch to the 11 MB direct runtime later, see https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/manual/en/providers.mdx#choosing-the-runtime
Wrote .github/workflows/ocra.yml: pull requests from members are reviewed on every push, anyone else's once each time a maintainer adds the ocra-review label.
Wrote .github/workflows/ocra-commands.yml: a comment @ocra review by someone who can write reviews the pull request again, and ocra answers any other @ocra mention in its thread.

Next:
  1. Store the key as a repository secret (gh asks for its value):
       gh secret set GEMINI_API_KEY
  2. Create the label that starts a review of an outside pull request:
       gh label create ocra-review --description "Review this pull request with ocra"
  3. Commit .ocra/config.json, .github/workflows/ocra.yml, .github/workflows/ocra-commands.yml, and merge them into the default branch:
       ocra reads its configuration from a pull request's base branch,
       and GitHub runs comment workflows from the default branch.
```

私有仓库请按 workflow 里的注释删掉 `persist-credentials: false`。在任何子目录运行，ocra init 都写到仓库根目录，且从不经由符号链接写入。不在 Git 仓库里，或没找到 key 又没给 `--provider` 时，它以退出码 `2` 结束，什么也不写。

## ocra review

审查当前 Git 仓库里的代码改动。

```bash
ocra review [options]
```

| 参数 | 含义 |
|---|---|
| *（不带参数）* | 审查未提交的改动：已暂存、未暂存和未跟踪的文件 |
| `--from <ref>` | 审查 `--to` 从 `<ref>` 分叉以来的改动（基于 merge base） |
| `--to <ref>` | 区间终点，默认 `HEAD`，必须配合 `--from` 使用 |
| `--commit <sha>` | 审查单个 commit 相对其父 commit 的改动 |
| `--format text\|json\|sarif` | 输出格式，默认 `text`。`sarif` 输出 [SARIF 2.1.0](#sarif-输出) |
| `--output <file>` | 把结果写入文件，而不是输出到 stdout。文件整体替换；如果该路径本身，或仓库内途经的某个目录，是符号链接，则拒绝写入（退出码 `2`，在调用任何模型之前）；已存在但不是普通文件的路径同样拒绝。因此 `/dev/stdout`、命名管道和进程替换（`>(…)`）都不可用：要输出到 stdout，不加 `--output` 即可 |
| `--pr <number>` | 审查一个 GitHub PR，见 [GitHub Pull Request](./github) |
| `--repo <owner/name>` | `--pr` 所在的仓库（默认取 `GITHUB_REPOSITORY` 或 `origin`） |
| `--mr <iid>` | 审查一个 GitLab Merge Request，见 [GitLab Merge Request](./gitlab) |
| `--project <id\|路径>` | `--mr` 所在的项目（默认取 `CI_PROJECT_ID` 或 `origin`） |
| `--publish` | 配合 `--pr` 或 `--mr`：把评审发布到 PR 或 Merge Request |
| `--full` | 配合 `--pr` 或 `--mr`：审查所有文件，而不是只审查上次评审之后改动过的文件 |
| `--max-cost-usd <n>` | 本次运行的花费上限。达到 80% 时仍在运行的审查任务停止，已找到的问题保留；这些任务的文件算作未审查（退出码 `3`），已经审完的任务除外。剩下的部分留给核查和裁决；再用完时，剩余问题标为*未核查*，不会拦下改动。任务大约每 10 秒报告一次花费，所以每个任务最多超出这段时间的花费加上正在进行的一步。任务按分组逐个运行，涉及敏感路径（`auth/`、CI 工作流等）的分组先跑，所以受限的运行会先审完风险最高的那部分文件；使用 `--pr` 时，下一次审查接着审剩下的 |
| `--plan` | 免费，不调用模型：显示会审查和排除的文件、分组、审查任务和每个首轮提示词的大小（含 `--ultra` 下的规划调用，或审查员按分组分任务时为大分组所做的规划调用）。任务的模型链已知时，按链上第一个模型的价格估算这些提示词的输入花费，逐个任务并给出总计：[自行声明的供应商](./providers#你自己的端点)用声明的价格，价格为 0 或经由 ocra Cloud 时显示 `input unpriced`，其余显示 `input price unknown`。输出、后续轮次、核查和裁决不做估算。JSON 格式的规划还按来源列出每个任务的首轮提示词（`context`）：token 数、被截断的文本或被截短的列表（`cut`），以及同一提示词里前面的来源已经有的行（`duplicateTokens`）。跳过 light 模型分组，所以较大的改动按每个文件一组显示（超过 20 个文件时按目录）。和 `--pr` 或 `--mr` 一起用时，按审查实际会覆盖的范围规划：能判断时只规划自上次审查以来改动的部分，和审查本身一样，并会说明（`--full` 则规划全部）。不写会话日志 |
| `--import-sarif <文件>` | 把分析工具（Semgrep、CodeQL 等）的 SARIF 2.1.0 日志里的结果加入审查，可以重复使用。见 [SARIF 输入](#sarif-输入)。不能和 `--plan` 一起用 |
| `--no-linked-tasks` | 配合 `--pr` 或 `--mr`：不把改动[关联的 issue](./how-it-works#关联的任务) 交给审查员（配置中的 `linkedTasks`） |
| `--guidelines <范围>` | 每个审查任务拿到 `AGENTS.md` 的哪些章节：`all`、`matched` 或 `reviewer`（见 [`guidelineScope`](./configuration)）；覆盖配置 |
| `--without <来源>` | 从每个审查提示词里去掉这些上下文来源（逗号分隔），用来和带着它的运行对比，衡量每个来源的价值：`description`（变更请求的描述，标题保留）、`changed_files`、`linked_tasks`、`guidelines`（同时跳过依赖它的审查员）、`rules`（仓库的规则，不是审查员自带的）、`accepted`、`learnings`、`project_docs`、`callers`、`analyzer`。计入配置哈希。`--plan` 显示去掉它们之后的提示词 |
| `--sarif-evidence <文件>` | 把分析工具 SARIF 2.1.0 日志里落在改动上和改动附近的结果交给审查员，作为需要核实的证据，而不是问题；可以重复使用。见 [SARIF 作为证据](#sarif-作为证据) |
| `--graph <文件>` | 在这个[代码图](#ocra-graph)里查找改动符号的调用方，在 `--scip` 之后、搜索之前。不能和 `--plan` 一起用 |
| `--scip <文件>` | 先在这个 [SCIP](https://github.com/scip-code/scip) 索引里查找改动符号的调用方（见[模式](./how-it-works#模式)）。不能和 `--plan` 一起用 |
| `--ultra` | 以成本换召回率，见[模式](./how-it-works#模式) |
| `--depth <depth>` | `quick`、`standard` 或 `deep`：配置没有设置的那些项的预设；覆盖 [`depth`](./configuration#审查深度) |
| `--no-ultra` | 不使用 `--ultra`，即使配置或你的 ocra Cloud 账户开启了它（[`ultra`](./configuration#执行参数)） |
| `--min-inline-severity <severity>` | 配合 `--publish`：只把严重程度不低于此值（`critical`、`warning` 或 `suggestion`）的问题发成行内评论；覆盖 [`minInlineSeverity`](./configuration#行内评论) |
| `--max-inline-comments <n>` | 配合 `--publish`：本次审查的问题最多发 `n` 条（0 到 1000）行内评论；覆盖 [`maxInlineComments`](./configuration#行内评论) |
| `--fixes` | 为问题给出经过检查的修复，效果同 [`fixes: true`](./configuration) |
| `--reviewers <ids>` | 只运行这些审查员，用逗号分隔（例如 `security`） |
| `--temperature <n>` | 采样温度，0 到 2；覆盖 `sampling.temperature`（[配置](./configuration#执行参数)） |
| `--seed <n>` | 采样种子，运行时和供应商支持时才生效（`opencode` 不支持）；覆盖 `sampling.seed` |
| `--resume <run-id>` | 重试同一审查的一次早先运行，已经完成的部分不再付费：输入没变（同样的提交、配置、提示词、ocra 版本和采样）的已完成任务直接复用，只运行剩下的；失败的任务和中途被截断（部分审查）的任务会重新运行。读取[会话](#会话记录) `.ocra/sessions/<run-id>`，且只读取本机 ocra 写下的内容：来自另一台机器或另一个用户的会话，或随改动一起带来的会话，都会被拒绝（退出码 `2`），会话里后加的行会被忽略并给出警告。不能复用的任务照常运行，并有一条警告说明数量。复用的任务不产生花费，所以花费上限不会把它们挡在外面；它们在 [JSON 输出](#json-输出)里带 `reusedFrom`，本次运行的 `usage` 只算本次实际花费。不能和 `--plan` 一起用 |
| `--config <文件>` | 用这个配置文件代替 `.ocra/config.json`（与 `--pr` 或 `--mr` 一起用时代替 base 分支的那份）；和 `--no-repo-config` 一起用也生效。见[配置](./configuration) |
| `--no-repo-config` | 用于不信任的代码：忽略 `.ocra/config.json` 及其插件（与 `--pr` 一起用时，base 分支的也忽略）；模型从 `OCRA_MODEL_*` 或 `--config` 读取；memory、rules 和 `AGENTS.md` 从 `--from` 所在的提交读取，否则不使用 |
| `-h, --help` | 显示帮助 |

`--commit` 不能和 `--from`、`--to` 同时使用。

### 进度

进度输出到 stderr，所以用 `--format json` 时 stdout 上的内容仍可直接给程序解析：

```text
[ocra] Reviewing: Working tree changes
[ocra] 4 file(s) selected, 1 excluded · risk tier: lite
[ocra] 2 bundle(s) (grouped)
[ocra] 2 review task(s)
[ocra] correctness-1 started: auth session handling (2 file(s))
[ocra] correctness-1 reviewing with google/gemini-3.5-flash
[ocra] correctness-1 google/gemini-3.5-flash: 3 step(s), 3 tool call(s) (read_file 2, task_done 1), 19558 in / 118 out / 0 reasoning tokens, $0.0062
[ocra] correctness-1 completed in 5.9s · 0 finding(s)
```

模型超过 30 秒没有新输出时，ocra 会打印 `Model is thinking...`。

### 退出码

| 退出码 | 含义 |
|---|---|
| `0` | 审查完成，结论为 `approved`、`approved_with_comments` 或 `minor_issues` |
| `1` | 结论为 `significant_concerns`：至少有一个经核查确认的 critical 问题（未经确认的只会得到 `minor_issues` 和 `0`）。结论只是参考意见，可能受被审查改动的影响，见[工作原理](./how-it-works#结论verdict)。配合 `--pr` 时，维护者针对 head commit 的 `@ocra override` 会把它变成 `0`（[GitHub](./github#强制放行阻塞的结论)） |
| `2` | 参数、Git 或配置错误，或者没有任何审查任务完成。错误行会写出错误代码，例如 `ocra [VCS_REF_UNKNOWN]: Unknown commit: nope`（[代码列表](./embedding#错误)） |
| `3` | 审查不完整：有选中的文件没有被审查（任务失败、超时、触及花费或任务数上限，或者没有审查员覆盖它），或只审查了一部分（审查员在调用完成工具之前用完了全部 30 步，或自己停了下来；提示信息会说明该怎么做），或者有 critical 没能核查。它优先于 `1`，CI 不会放行不完整的审查 |
| `130` | 被 Ctrl-C 或 SIGTERM 中断；仍会打印部分报告，不会发布任何内容 |

### JSON 输出

`--format json` 输出完整报告，格式与会话里的 `report.json` 相同：

- 变更信息、风险档位、结论、总结；
- 每个改动文件的覆盖情况：已审查、失败、未审查（没有启动任务）、不完整（任务没有调用完成工具就结束；`ended` 为 `step_cap`、`context_window` 或 `stopped_early`）、自上次评审后未改动，或被排除及原因；审查 PR 时，本次是增量还是全量及原因（`scope`）；
- 分组、各任务结果、被 Matrix 跳过的（审查员，分组）组合；
- `refuted`（被核查丢弃的问题及原因）、`unverifiedCriticals`（核查没能检查的 critical 数量）、`judgement`（Judge 合并、丢弃或重新定级的记录）、开启修复时的 `fixes`（`asked`、`proposed`，以及每条被拒绝问题的 `fingerprint` 和 `reason`：`declined`、`failed`、`stale`、`unchanged`、`unsafe`、`too_large`、`no_parser` 或 `syntax`）；
- 问题列表，以及 `rereview`：已修复、未再报告、未重新检查、未改动或已驳回的旧问题，记录了报告者时各带 `reviewer`；
- `remembered`：被 memory 接受的问题，带来源 `source`（`repository` 表示 `.ocra/memory.json`，`account` 表示你的 [ocra Cloud memory](#ocra-cloud-账户里的-memory)）；维护者的放行在 `changeRequest.override`；
- `learnings`：任务拿到的每条 [learning](./rules#ocralearnings)，带 `title`、`critical`、`source` 和它去过的分组 `bundles`；
- `projectDocs`：交给任务的每个[项目文档段落](./how-it-works#项目文档)，带 `path`、`heading` 以及交给的分组 `bundles`；没有时不出现；
- `linkedTasks`：交给任务的每个[关联 issue](./how-it-works#关联的任务)，带 `tracker`、`key`、`url`、`title`、`state`、`labels`，以及文字是否被裁剪（`cut`）；没有关联时为空，本地审查或关闭开关时不出现；
- `mergeChecks`：每条[合并前检查](./how-it-works#合并前检查)，带 `id`、`instruction`、`outcome`（`passed`、`failed` 或 `inconclusive`）和 `reason`，按配置的顺序；没有配置时不出现；
- `analyzerEvidence`：用 [`--sarif-evidence`](#sarif-作为证据) 交给任务的每个工具，带 `version`、结果条数 `results` 和它们去过的分组 `bundles`；
- `inline`：设置了[行内评论策略](./configuration#行内评论)时出现，包含它的 `minSeverity` 和 `maxComments`，以及 `held`：策略没有发成行内评论的每条问题（`fingerprint`，`reason` 为 `below_floor` 或 `over_cap`），按策略排出的顺序；这些问题本身仍在 `findings` 里；
- token 用量与花费；设置了花费上限时的 `spendLimit`（`reached` 为 `review` 表示审查任务因此停止，`total` 表示整个上限用完）；警告信息。

这个格式是一份约定（`"version": 1`）：后续版本只会新增可选字段和取值集合里的新值，否则就会改版本号。遇到不认识的覆盖状态时，当作没有审查。

**每条问题**包含 `fingerprint`（多次运行间保持稳定；`ocra memory add` 接受它的前缀）、`reviewer`、`category`、`severity`、`verification`（`confirmed`、`uncertain` 或 `unchecked`）、`file`、`lines`（`{ start, end }`，没能对应到行时不存在）、`inDiff`、`status`（`new`，或之前报过时为 `unfixed`）、`title`、`body`、可选的 `suggestion`、可选的 `fix`（`{ startLine, endLine, replacement }`，开启时由 [Fix 阶段](./how-it-works)设置，作为[可提交的建议](./github#可提交的建议)给出）、`evidence`、可选的 `rule`（`{ kind, id }`：这条问题所依据的[仓库规则](./rules)或经验，`kind` 为 `rule` 或 `learning`；审查员点名了交给它的某一条时才有）、`code`（引用的代码）、`--ultra` 下的 `lowConfidence`、Verify 判断问题在这次改动之前就已存在时的 `preExisting`，以及 `provenance`（它的 `task`，已知时还有 `model`）。`tasks` 里的每个任务带有 `usage`（token 和花费；一条问题的花费就是其任务的花费）；没有调用完成工具就结束的任务还带有 `ended`：它的文件只算审查了一部分。审查员随后得到了[收尾的一轮](./how-it-works)的任务还带有 `wrapUp`（`{ findings }`，它在那一轮报告的问题数），它的文件仍然只算审查了一部分。

**报告的 `provenance`** 记录：

- `ocraVersion`；
- `promptHash`：这份配置会发出的系统提示词的哈希（审查员和辅助阶段的；从不包含改动）；
- `configHash`：实际生效的配置加上 `--reviewers`、`--ultra` 和 `--max-cost-usd` 的哈希；不含采样设置和密钥（key 只以变量名出现）；
- `sampling`：实际应用的 `temperature` 和 `seed`，`notApplied` 列出没能应用的；
- `agents`：每个启用的审查员和 `verifier`、`judge`、`helper`、`writer` 四个角色的 `tier`、`models` 中的模型链（[自己的](./configuration#按-agent-指定模型)或所在层级的）、设置了时的[推理强度](./configuration#推理强度) `effort`、`applied`（没有发出调用时不存在），以及 `notApplied` 的采样设置；
- `rules`：每条路径规则的 `id`（问题的 `rule` 引用的就是它）、`path`、`rule` 和 `source`（`repository` 表示 `.ocra/rules.json` 和 `.ocra/rules.md`，`shared`、`account` 或 `plugin`）；
- `accountSettings`：登录时所用[账户设置](./configuration#账户设置)的 `version`。

报告的 [JSON Schema](https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/schema/report.v1.json)（draft 2020-12）由代码生成并经测试核对；`@open-cr-agent/core` 的 `reportJsonSchema()` 返回它。

**`--plan` 的 JSON** 同样带版本号，有自己的 [JSON Schema](https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/schema/plan.v1.json)：变更信息、风险档位、有上次审查时的 `scope`（`incremental` 带 `since`，或 `full` 带 `reason`，和报告中的一样）、选中和排除的文件、分组、各任务（估算的提示词大小、`models`、设置了时的 `effort`、模型链已知时的 `inputCost`：`model` 为链上第一个模型，`status` 为带 `usd` 的 `priced`、`unpriced` 或 `unknown`）、被跳过的组合、`groupingSkipped`、`promptTokens`（总计）、有任务带估算时的 `inputCost`（已定价任务的 `usd` 之和及各状态的任务数）、警告信息、`settings`（每项的 `key`、`value`（默认值时不存在）和 `source`），以及读取了账户设置时的 `accountSettings`。

### SARIF 输出

`--format sarif` 把审查结果写成 [SARIF 2.1.0](https://docs.oasis-open.org/sarif/sarif/v2.1.0/sarif-v2.1.0.html) 日志，代码扫描和安全看板读取的就是这种格式。上传到 GitHub 的方法见[代码扫描](./github#代码扫描)。

- **规则和结果。** 每个审查员类别（`correctness`、`security` 等）一条规则，每个问题一条结果：
  - 级别来自严重程度：`critical` 为 `error`，`warning` 为 `warning`，`suggestion` 为 `note`；
  - 消息是标题、正文和修改建议；区域是问题所在的行；
  - `partialFingerprints` 里是它的指纹（`ocra/v1`）；
  - 问题的 `fix` 放在 `fixes` 里，替换那几整行；
  - 审查员、严重程度、核查结果、状态、任务，以及已知时的模型放在属性里。
- **没有行号的问题**作用于整个文件：没有区域。
- **沿用的问题。** 审查 PR 时，之前的审查报告过、仍然打开、所在文件这次没有重新审查的问题，作为规则 `ocra-carried-over` 下的结果写出，标为 `unchanged`，没有行号。
- **不完整的审查。** 退出码为 `3` 的审查标为执行不成功；没审到的文件数和警告写成通知；结论、风险档位、没审到的文件和花费写在运行属性里。

来自改动和模型的文字只作为文字：方括号和反斜杠会被转义，花括号写成两个，网址插入零宽空格。`--plan` 不能输出 SARIF。

### SARIF 输入

ocra 不运行任何分析工具：你自己运行 Semgrep、CodeQL 或其他工具，再用 `--import-sarif <文件>` 交给 ocra 它的 SARIF 2.1.0 日志（可以重复使用，每个最大 20 MB）。日志里的每个 run 成为一个任务 `sarif-<工具>-<n>`，审查员是工具名，没有花费；它的问题在 `provenance.task` 里指向这个任务。

- **只保留落在改动上的结果**：文件在审查范围内，行号落在 diff 的某个 hunk 里。其余结果，以及没有文件和行号、路径在仓库之外或没有消息的结果，计入一条警告。每个 run 最多取 200 条。
- **严重程度**来自结果的 level，没有时取规则的默认值：`error` 为 `critical`，`warning` 为 `warning`，`note` 和 `none` 为 `suggestion`。标题：规则的简短描述、名字或 id。正文：消息、规则的说明，以及工具、版本、规则和帮助链接。
- **引用的代码决定行号。** 结果里的代码片段（没有时取文件对应的行）和审查员引用的代码走同一套定位；对不上的会让问题变成文件级。
- **之后它就是一条普通的问题**：memory 和驳回照样生效，核查会检查它，Judge 会把它和审查员的重复问题合并，它也计入结论。

已用 Semgrep 1.178.0 写出的日志测试过；其他工具的日志遵循同一标准。

### SARIF 作为证据

`--sarif-evidence <文件>`（可以重复使用，每个最大 20 MB）则把日志交给审查员：一条结果是审查员要在代码里核实的线索，而不是一条问题。适合噪音太多、不能原样发出的 linter 和规则集。同一个日志可以同时传给两个参数。

- **落在改动上和改动附近的结果**：文件在审查范围内，行号落在 diff 的某个 hunk 里，或离它不超过 10 行。两个日志重复的结果只显示一次。
- **每个分组最多 20 条**：先是落在改动上的，再按 `error`、`warning`、`note` 排，带 `security` 标签的优先，然后按文件和行号；每条消息截到 300 个字符。没放进去的计入一条警告。
- **分组里的每个审查员都看到落在自己文件上的结果**，只是带 `security` 标签的结果，在有安全审查员审查该文件时只交给它（没有时交给所有审查员）。每条一行，写明文件和行号、工具、规则、严重程度，以及在改动上还是在改动附近；审查员被告知，只有结果属于自己负责的方面、并且是这次改动引入或加重的，才报告它。
- **审查员据此报告的是它自己的问题**，和其他问题一样核查、裁决、计入结论。没有审查员确认的结果不会报告；用 `--import-sarif` 的话它会被报告。
- **报告写明交了什么**：[`analyzerEvidence`](#json-输出)。只有给了日志提示词才会变长，所以不带这个参数的运行和以前完全一样。

### 会话记录

每次审查（`--plan` 除外）都会写入 `.ocra/sessions/<id>/events.jsonl`（运行过程中逐行写入事件）和 `report.json`。运行 id `<id>` 出现在第一行进度输出、JSON 报告（`runId`）、摘要评论（"覆盖范围和花费"）和 SARIF 日志（`automationDetails.id`，`ocra/<id>`）里。每次任务尝试的事件在 `attempt` 里记录审查员读过的文件、搜索过的内容和最后的文字（有长度上限），以便分清一个文件是没打开过，还是读过但没发现问题；这些都不会写进报告。旁边的 `trace.json` 按时间铺开整次运行：每个阶段何时开始；每个任务和它的每次尝试（模型、步数、各工具的调用次数、读过的文件、搜索次数、token、花费、耗时、怎样结束）；每次普通模型调用（规划、分组、改动导读、核查、裁决、重新定位）的模型、耗时和花费；以及每条报告过的发现的去向：保留、在审查范围外、被核查推翻、被裁决合并或丢弃（附原因），或被过滤。它不含代码、提示词、模型回答或搜索的文字，所以可以作为这次审查的证据交给 reviewer。报告对象（[库](./embedding)里的 `report.trace`）也带着它；JSON 报告不带。这个目录自带 `.gitignore`。

`events.jsonl` 的每一行末尾都有一个 `seal`：用你自己的密钥计算的 HMAC。这个密钥由 ocra 在首次使用时生成，存放在 `~/.config/ocra/session-key`（`$XDG_CONFIG_HOME/ocra/`，Windows 上是 `%APPDATA%\ocra\`），只有你能读取。`--resume` 只读取 seal 有效的行，因此一个会话只能在写下它的那台机器、那个账户上恢复；删除这个密钥只会让之前的会话无法恢复，不影响其他功能。如果 ocra 无法生成或读取密钥，审查会给出警告，这次的会话不能恢复；读不了的密钥文件（例如 `sudo ocra` 之后属于另一个用户）保持原样，不会被替换。

## ocra graph

生成一个提交的代码图：每个源文件的定义，以及其中各个名字被使用的行，见[工作原理](./how-it-works#模式)，供 `ocra review --graph` 使用。它只读取 git 对象，不运行仓库里的任何东西。

```bash
ocra graph --out ~/.cache/ocra/graph.json             # HEAD
ocra graph --out graph.json --rev origin/main         # 另一个提交
ocra graph --out graph.json --cloud                   # 从 ocra Cloud 的代码图开始
```

`--out` 已有代码图时会更新它：内容已在图里的文件不再读取，所以第一次之后，每次更新只花在改动过的文件上。读不了的代码图（格式不同，或超过 512 MB）会给出警告并重新生成。超过 1 MB 的文件和不是 UTF-8 文本的文件不计入。代码图只保存名字、种类和行号，从不保存代码。可以在每次推送后在主分支上生成它，在多次运行之间保留这个文件（例如放进 Actions 缓存），再交给针对这个分支的 PR 审查。

加上 `--cloud` 时，代码图从自托管 ocra Cloud 服务器为仓库默认分支生成的最新代码图开始（服务器按 `CODE_GRAPH` 的设置，每次推送生成一份），而不是从 `--out` 的文件开始：只读取和解析这个提交之后改动过的文件。服务器是 `ocra login` 登录的那一个，仓库是主机和路径与 `origin` 一致的那一个。没有可用的代码图时（未登录、服务器不保存代码图、服务器不保存这个仓库的代码图、代码图格式不同），ocra 会给出警告，像不加 `--cloud` 时一样从 `--out` 的文件或从头生成，命令仍然成功。代码图只交给解析器读取，其中没有任何东西会被运行。

## ocra learn

从历史里的修复提交起草 [learning](./rules#ocralearnings)，让审查记住团队已经修过一次的问题：

```bash
ocra learn mine                    # HEAD first-parent 线上最新的 20 个修复
ocra learn mine --max 50           # 多看一些
ocra learn mine --max-cost-usd 0.5 # 花费到上限就停止起草
```

修复指标题这样写（`fix:`、`revert`、"fixes"、"bug"）且最多改动 5 个源文件的提交；文档、测试和数据文件不算。对每个修复，helper 角色调用一次模型，读它的标题、说明和 diff（截断到固定长度，作为数据），起草标题、正文、符号和关键词，或者回答这个修复没有对其他改动有用的经验。随后 ocra 不经过模型检查草稿：

- 符号必须出现在 diff 里；路径取修复改动过的目录，从不用模型给的；
- 已有 learning 在 `source.ref` 里记录过的修复不会再起草；覆盖已有 learning 的某条路径、且标题用词大多相同的草稿会被丢弃；origin 上 `ocra/learnings-*` 分支（最新的 20 个）里的 learning 也同样对待，这些分支是打开或已关闭的提议留下的：等待审查的不会重复起草，被人关闭而没合并的，在删除它的分支之前不会再起草；
- 只有选取会把草稿交给它来源的那个修复时，才保留它。

保留的每条 learning 写进工作区的 `.ocra/learnings/<标题>.md`，带 `source: { kind: fix-commit, ref: <sha> }`，从不设 `critical`，并打印路径。文件名取标题的小写字母、数字和连字符，最多 60 个字符，并在完整的词处结束。像其他文件一样阅读、修改、提交。最后一行统计写入、没有经验、重复和因花费上限没起草的数量，以及调用的花费。`ocra learn` 使用 `.ocra/config.json` 的运行时和模型（helper 角色的），或者 `--config <file>` 指定的文件里的，不审查任何东西，也不写会话。

### 从已接受的问题

`ocra learn feedback` 从团队用 [`ocra memory add`](#ocra-memory) 接受的问题起草，最新的在前，和审查一样从同一个版本读取 `.ocra/memory.json`。每次调用拿到问题的标题、团队给出的理由和它所在的文件，只有理由不止适用于这一条问题时（这里有意这样写、风险在别处处理）才写成经验；这条 learning 随后告诉审查员在那里不要报告什么。路径取该文件所在目录，`source` 是 `{ kind: review-feedback, ref: <问题 id> }`，检查、限制和 `--propose` 都和 `mine` 相同。

`ocra learn feedback --pr <n>`（或 `--mr <iid>`，`--repo`、`--project` 与审查时相同）还会从这个 PR 或 MR 的审查里、有写权限的人在讨论串中拒绝的问题起草：一条表示拒绝的回复（`@ocra dismiss`、"won't fix"、"by design"），或者有写权限的人把讨论串标记为已解决时他们的最后一条回复。每次调用拿到问题的标题、他们说的话和这次变更里的该文件。和 `@ocra remember` 一样，作者本人也可以在这里拒绝：这不会影响审查结论，而 `--propose` 会把 learning 交给一个 pull request。被他人编辑过的回复、没有写权限的人的回复、没人回复的讨论串都不产生候选。

### 从文档

`ocra learn import docs/postmortems/*.md` 从团队自己写的东西起草：事故复盘、规范、设计笔记。每个 Markdown 文件的每个 `##` 小节（第一个小节之前的文字归在文档标题下）是一个候选，连同它按路径提到的最多 5 个仓库文件（如 `src/db/pool.ts`），从受信任的版本读取。没有提到仓库文件的小节不会起草：没有审查能拿到它。只有审查员能在这些文件的 diff 里检查的内容才会写成经验；路径取这些文件所在目录，`source` 是 `{ kind: document, ref: <文件>#<小节> }`。单个文件最大 256 KB。

### 从 pull request 备注

`ocra learn remember --pr <n>`（或 `--mr <iid>`，`--repo`、`--project` 与审查时相同）从 PR 或 MR 上有写权限的人留下、且没被他人编辑过的每条 [`@ocra remember <备注>`](./github#让-ocra-记住) 起草（最多 20 条）。每次调用拿到 PR 标题、备注，以及备注按路径提到的 diff 文件；没提到时，diff 不超过 5 个文件就用整个 diff，否则不起草。配置和审查一样从 base 读取。要求经验以外东西的备注（批准、改设置）会被拒绝。`source` 是 `{ kind: remember, ref: <仓库>#<编号>/<评论 id> }`。

### 通过 pull request 写回

`ocra learn mine --propose` 不写工作区：它把保留的 learning 开成一个 GitHub pull request 或 GitLab Merge Request，在默认分支上新建 `ocra/learnings-<时间>` 分支并提交一次，全部通过平台 API 完成（不从本地 push）。`--repo <owner/name>` 选 GitHub，`--project <id|path>` 选 GitLab；两者都没给时，平台依次取 `--pr` 或 `--mr` 的平台（用于 `remember`）、所在的 CI（GitHub Actions 或 GitLab CI）、origin 的主机（github.com 或 gitlab.com），最后是唯一设置了令牌的那个平台。在 GitHub 上需要有 contents 和 pull request 写权限的 `GITHUB_TOKEN`（或 `GH_TOKEN`）；仓库取 `--repo`，其次 `GITHUB_REPOSITORY`，否则取 origin。在 GitLab 上需要有 api scope 和 Developer 角色的 `GITLAB_TOKEN`，发往的地址与[审查](./gitlab)时相同；项目取 `--project`，其次 `CI_PROJECT_ID`，否则取 origin。变更请求列出每条 learning 和它的来源，命令打印它的地址。

pull request 设为检查通过后自动合并（仓库允许 squash 就用 squash，其次 rebase，再次 merge commit）；如果它不需要任何检查，就立即合并。在 `.ocra/config.json` 里设 `"learnings": { "requireReview": true }`，或在命令行加 `--require-review`，就留给人来审查和合并。仓库关闭了 auto-merge，或 GitHub 拒绝时，ocra 给出警告并让 pull request 保持打开。用 workflow 自己的 `GITHUB_TOKEN` 开的 pull request 不会触发任何 workflow，必需的检查永远不会报告结果：如果分支保护要求检查，请用 GitHub App 或个人 token（[Action](./github#从历史和备注中学习) 会把这样的 pull request 留给人合并）。

在 GitLab 上，Merge Request 设为流水线成功后合并，使用项目自己的合并方式，合并后删除分支。GitLab 会立即合并没有运行中流水线的 Merge Request，所以 ocra 先最多等约 15 秒，等新分支触发的流水线；到时仍没有，就说明它不需要任何检查，立即合并。项目要求流水线成功才能合并却没有流水线，或 GitLab 拒绝时，ocra 给出警告并让 Merge Request 保持打开。用 `GITLAB_TOKEN` 做的提交和任何 push 一样会触发项目的流水线。

`ocra learn check` 不调用模型：它列出每条有路径匹配不到 HEAD 上任何文件的 learning，格式为 `<id>: no file matches <路径>`，只要有一条就以 1 退出。模块搬家或改名后，审查不再按这些路径选中这条 learning，只能靠它的 symbols 和 keywords；请改它的 paths。可以放进 CI 及早发现。ocra Cloud 的 Learnings 页对默认分支显示同样的结果。

## ocra reply

在 PR 或 MR 上回答提到 `@ocra` 的评论，回复在同一个讨论里：

```bash
ocra reply --pr 7 --comment 2154873301            # 对话区的评论
ocra reply --pr 7 --comment 1891230045 --inline   # diff 某一行上的评论
ocra reply --mr 12 --comment 4811                 # GitLab 的 note
```

`--repo` 和 `--project` 与审查时一样指定仓库，令牌也相同；`--config <file>` 读取该文件，代替 base 的 `.ocra/config.json`（例如用来设置 `github.botLogin`）。ocra 只回答这样的评论：在这个变更请求上、在代码之外提到 `@ocra`、确实在提问、作者有写权限（GitLab 上是 Developer 及以上角色）、没被他人编辑过、也不是 ocra 自己发的；每条评论只回答一次（回答里带 `<!-- ocra:reply <id> -->`）。其他评论只在 stderr 打印 `[ocra] Not answering: <原因>`，不调用模型，退出码为 `0`，所以 workflow 可以对每条评论都运行它。出错时（例如缺少令牌、模型调用失败）退出码为 `2`。

回答是 writer 角色的一次调用，输入是描述、讨论里最近的评论；如果评论在某一行上，再加上该文件的 patch 和那一行附近的代码；否则是问题提到的文件，再否则是最小的几个 patch。文件取自审查的选择结果，并经过同样的访问策略读取，所以提问拿不到机密文件或被排除的文件。回答最多约 250 词，与审查发现一样渲染（提及和命令都会被中和）。配置和审查一样从 base 读取。`ocra reply` 不做审查，也不写会话；要更深入地看某一段，请用 `ocra review`。v0.10.0 新增。

## ocra stack

维护一个分支栈：每个分支是一个 PR 或 MR，base 是它下面的那个分支，这样大的改动可以分成小步审查：

```bash
ocra stack create feat/parse -m "feat: parse the input"   # 从当前分支建分支，提交已暂存的改动
ocra stack create feat/apply -m "feat: apply it"          # 下一步，叠在 feat/parse 上
ocra stack submit --draft                                  # 推送两者，#1 基于 main，#2 基于 feat/parse
git switch feat/parse && git commit --amend               # 修改下层分支
ocra stack restack                                         # 把 feat/apply 变基到它上面
ocra stack sync                                            # #1 合并后：删除 feat/parse，把 feat/apply 移到 main 上
ocra stack submit                                          # 推送，把 #2 的 base 改为 main
```

| 命令 | 作用 |
|---|---|
| `create <branch>` | 从当前分支创建该分支并叠在当前分支上；`-m <message>` 提交已暂存的改动 |
| `track [<parent>]` | 把当前分支叠在 `<parent>` 上（默认是主干），用于不是 `create` 建的分支，或另一个克隆里的分支 |
| `log` | 显示当前分支所在的栈，并标出需要 restack 的分支 |
| `restack` | 自下而上把每个分支变基到其父分支的最新提交上，然后回到原来的分支 |
| `submit` | 推送每个分支（`--force-with-lease`），为还没有变更请求的分支打开一个（`--draft` 为草稿），base 为其父分支，并更新每个 base 和每个描述里的栈列表 |
| `sync` | 拉取远端，找出变更请求已合并的分支，把它们的子分支移到被合并分支的父分支上，删除这些分支并 restack。它不推送：接着运行 `submit` |

栈是记录在本克隆 git config 里的分支树（`branch.<name>.ocraParent`，以及 `branch.<name>.ocraParentHead`，即分支所基于的父分支提交），根是主干，也就是 origin 的默认分支。restack 运行 `git rebase --onto <parent> <parentHead> <branch>`，所以被 amend 或 squash 合并的父分支不会被重放。遇到冲突时它停在那个分支：解决冲突，运行 `git rebase --continue`，再运行一次 `ocra stack restack`。除 `create` 和 `track` 外，每个命令都要求工作区干净。

`submit` 和 `sync` 使用 `GITHUB_TOKEN`（或 `GH_TOKEN`）或 `GITLAB_TOKEN`，`--repo` 或 `--project` 与审查时相同；令牌需要 PR（MR）的写权限。描述里的栈列表在 `<!-- ocra:stack -->` 标记之间；标记之外你写的内容保持不变。如果栈里有分支的变更请求已经合并，`submit` 在推送任何内容之前就会拒绝：先运行 `sync`。ocra Cloud 在 PR 页面显示这个栈，并能从最下面合并到你选的那一个，遇到平台拒绝合并的就停下。v0.11.0 新增。

## ocra generate

在 Pull Request 或 Merge Request 的分支上写入一个提交：为改动的代码补测试，或为新增、修改的声明补文档注释。

```bash
ocra generate tests --pr 7                   # 在改动的源文件旁新建测试文件
ocra generate docstrings --mr 12             # 在改动的行里补文档注释
ocra generate tests --pr 7 --dry-run         # 以 diff 打印这些修改，不提交
ocra generate docstrings --pr 7 --json       # 输出一行 JSON 结果
```

`--repo`、`--project` 和 `--config <file>` 与 `ocra reply` 相同，令牌也相同；令牌必须能写这个分支（GitHub：contents 写权限；GitLab：api scope 和 Developer 角色），提交以令牌所属的账号身份写入。

文件由 ocra 选：审查会选中的改动源文件（绝不包括机密文件、生成文件或第三方代码），语言为 TypeScript、JavaScript、Python、Go、Java 或 Kotlin（文档注释另支持 Rust）；不包括测试、类型声明、符号链接和子模块；新增行最多的优先，最多 5 个，每个最多 60,000 个字符。每个文件调用一次 writer 角色，模型看到描述、该文件的 patch 和文件本身，文件经过审查的访问策略读取。

- **tests** 为每个源文件新建一个测试文件，路径按仓库的命名习惯：默认放在源文件旁，用 `.test`，旁边的测试用 `.spec` 时也用 `.spec`；`__tests__/` 里已有测试时放进去；`test_<name>.py` 或 `<name>_test.py`，或放在 `tests/` 下；`<name>_test.go`；Maven 或 Gradle 布局用 `src/test/java/…/<Name>Test.java`（Kotlin 同理）。旁边有测试时，模型会参考它的框架和风格。路径上已有文件就跳过：ocra 从不修改已有文件。ocra 不运行这些测试（它不运行仓库里的任何代码，也不安装、不构建），提交信息里写明了这一点；测试由变更请求自己的 CI 运行。
- **docstrings** 为改动中还没有文档注释的声明补注释，用该语言的写法（`/** … */`，Go 用 `//`，Rust 用 `///`，Python 用 `"""` docstring）。ocra 只插入注释行，只插在改动的行里，不改任何已有的行；模型的回答如果要做别的，这个文件的回答整体被拒绝。

某个文件的调用失败或回答被拒绝时，跳过该文件，原因打印在 stderr；只有全部调用都失败时，这次运行才算失败。ocra 只在它读到的 head 之上提交：如果期间有人 push，GitHub 上分支更新会因为不是 fast-forward 被拒绝，GitLab 上会先比较分支，并要求每个修改的文件仍是原样。

加 `--json` 时，stdout 不打印 diff，而是一行 JSON：

```json
{"kind":"tests","outcome":"committed","headSha":"<40 hex>","commitSha":"<40 hex>","files":["src/retry.test.ts"],"usage":{"inputTokens":0,"cachedTokens":0,"outputTokens":0,"reasoningTokens":0,"costUsd":0},"reason":null}
```

| `outcome` | 含义 | 退出码 |
|---|---|---|
| `committed` | 分支上多了一个提交，`commitSha` 是它 | `0` |
| `dry_run` | `--dry-run`：修改已生成并打印，没有提交 | `0` |
| `nothing` | 没有可写的文件，或模型什么也没补；`reason` 列出每个被跳过的文件 | `0` |
| `head_moved` | ocra 读取之后分支有了新提交；没有提交 | `3` |
| `not_writable` | 令牌不能写这个分支：fork 的分支、受保护的分支、只读令牌 | `3` |

`files` 列出修改涉及的路径，无论是否提交；`committed` 和 `dry_run` 时 `reason` 为 `null`。用法、配置和模型错误的退出码为 `2`。结构是 `@open-cr-agent/cloud-contract` 里的 `generateResultSchema`。v0.11.0 新增。

## ocra fix

为审查已经报告的一条问题写一个经过检查的修复，做法和 `ocra review --fixes` 一样，然后打印出来。ocra Cloud 用它为没有修复的已存问题提供修复。它不提交也不推送任何东西。

```bash
ocra fix --pr 7 --finding finding.json --head <sha> --json   # GitHub 拉取请求
ocra fix --mr 12 --finding - --json < finding.json             # GitLab 合并请求，问题从 stdin 读入
ocra fix --commit HEAD --finding finding.json                  # 本地提交；只打印替换的代码
ocra fix --from main --finding finding.json                    # 本地范围，同 review --from
```

| 选项 | 含义 |
|---|---|
| `--finding <file\|->` | 问题的 JSON，格式与 ocra Cloud 存储的一致（`@open-cr-agent/cloud-contract` 里的 `sharedFindingSchema`）；`-` 从 stdin 读取。最多 256 KiB |
| `--head <sha>` | 审查这条问题时的完整提交 id。变更的 head 不是它时，ocra 不调用模型，回答 `head_moved` |
| `--pr`、`--repo`、`--mr`、`--project` | 拉取请求或合并请求，同 `ocra generate`，使用相同的令牌（有读权限即可） |
| `--from`、`--to`、`--commit` | 改为本地范围或提交，同 `ocra review`。未提交的改动无法修复：修复指向某个提交里的行 |
| `--config <file>` | 用这个配置文件代替仓库的配置（`--pr` 或 `--mr` 时是基础分支的） |
| `--max-cost-usd <n>` | 花费上限，否则用配置里的 `maxCostUsd`。ocra 在调用前检查；进行中的调用不会被中途截断 |
| `--json` | 在 stdout 打印一行 JSON，说明结果 |

ocra 通过审查的访问策略读取变更和问题所在文件在 head 上的内容（从不读取密钥路径或 `.git/`），并像审查锚定问题那样重新找到问题引用的代码（`code`）。只有 [Fix 阶段](./how-it-works)会为之请求修复的问题才会得到修复：它的代码在变更新增或保留的行里恰好对应一处，最多 30 行，并且不是低置信度。它是否已经有修复无关紧要。这样的问题会在 `fixer` 角色上得到一次调用（`roles.fixer` 和 `models` 与审查相同；登录时经过 ocra Cloud 的网关），模型看到的问题文本被当作数据，另有该文件的补丁和文件摘录。回答的检查与审查中完全相同：这些行仍是引用的那些行；只改这些行；不含控制字符或双向文本字符；最多 4,000 个字符、新增最多 20 行；文件的语法错误不增加（tree-sitter）。不加 `--json` 时，stdout 只有替换的代码。

加 `--json` 时，stdout 是一行：

```json
{"fingerprint":"b491fb26b470419c","headSha":"<40 hex>","outcome":"proposed","fix":{"startLine":3,"endLine":3,"replacement":"  for (let i = 0; i < prices.length; i++) sum += prices[i];"},"reason":null,"cause":null,"usage":{"inputTokens":0,"cachedTokens":0,"outputTokens":0,"reasoningTokens":0,"costUsd":0}}
```

| `outcome` | 含义 | `reason` | 退出码 |
|---|---|---|---|
| `proposed` | 通过全部检查的修复，替换 `headSha` 上该文件第 `startLine` 到 `endLine` 行 | `null` | `0` |
| `rejected` | 模型给出了回答，但被某项检查拒绝，或调用失败 | `failed`、`unchanged`、`unsafe`、`too_large` 或 `syntax` | `0` |
| `not_fixable` | 不是会请求修复的问题，或模型回答没有局部修改能修复它，或没有解析器认识该文件的语言 | `not_candidate`、`declined` 或 `no_parser` | `0` |
| `stale` | head 上的文件里已经没有问题的代码，或文件已不存在。请重新审查变更 | `stale` | `3` |
| `head_moved` | head 不是 `--head` | `null` | `3` |

存储的文本被脱敏或截断过（`redacted`、`truncated`）、而代码又找不到的问题，结果是 `not_candidate` 而不是 `stale`：它存储的代码可能不是文件里的样子。用法、输入和配置错误，以及运行时无法启动，退出码为 `2`；模型调用失败时结果是 `rejected`，理由为 `failed`，`cause` 说明失败的是什么（其他理由下为 `null`）：`timeout` 调用超过了自己的时限，`quota` 所有模型都用完配额或被限流，`refused` 端点拒绝了请求（密钥、模型名或某个参数），`unavailable` 端点出错或连不上，`invalid_output` 它回答了但 ocra 读不懂，或 `unknown`；端点自己的报错只写到 stderr（v0.21.0）。结构是 `@open-cr-agent/cloud-contract` 里的 `fixResultSchema`（[ADR-0077](https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/adr/0077-fix-one-finding.md)）。v0.19.0 新增。

## ocra mend

对已被人接受的问题运行一轮修复循环：为每条问题写一个经过检查的修复，然后要么打印出来（`--level propose`，默认），要么作为一个提交写到拉取请求或合并请求的分支上（`--level commit`）。由调度方（ocra Cloud，或 CI 工作流）在有变化时启动下一轮，并在各轮之间保存状态；没有进程等待 CI。仓库里的代码一概不运行：提交由变更自己的检查来测试。ocra 从不强制推送、批准或合并。

```bash
ocra mend --pr 7 --findings accepted.json --head <sha> --json              # propose：打印检查过的修改
ocra mend --pr 7 --findings accepted.json --level commit --state state.json --json
ocra mend --mr 12 --findings - --level commit --json < accepted.json       # GitLab 合并请求
ocra mend --pr 7 --checks --level commit --state state.json --json         # head 上失败的检查
ocra mend --pr 7 --conflicts --state state.json --json                     # 给出合并冲突的解决方案
ocra mend --from main --findings accepted.json                             # 本地范围；只能 propose
```

| 选项 | 含义 |
|---|---|
| `--findings <file\|->` | 已接受的问题，JSON 数组，最重要的在前，每条的格式与 ocra Cloud 存储的一致（`sharedFindingSchema`）；`-` 从 stdin 读取。最多 200 条、2 MiB |
| `--checks` | 同时处理拉取请求或合并请求的 head 上失败的检查（见下文）。带上它时可以不给 `--findings`。需要 `--pr` 或 `--mr`（v0.22.0） |
| `--conflicts` | 先解决把基准分支合并进 head 时的冲突（见下文）。带上它时可以不给 `--findings`。需要 `--pr` 或 `--mr`，并在仓库的克隆里运行（v0.22.0） |
| `--level <level>` | `propose`（默认）：检查过的修改写在结果里，不提交。`commit`：在分支上写一个提交 |
| `--state <file>` | 上一轮打印的 `state`。变更的第一轮不用给 |
| `--head <sha>` | 审查这些问题时的完整提交 id。变更的 head 不是它时，ocra 不调用模型，回答 `head_moved` |
| `--protect <glob>` | 任何一轮都不能修改的路径，在内置的之外；可重复。只增加路径，不减少 |
| `--pr`、`--repo`、`--mr`、`--project` | 拉取请求或合并请求，同 `ocra generate`。`--level commit` 需要能写该分支的令牌 |
| `--from`、`--to`、`--commit` | 改为本地范围或提交。这里不会提交：`--level commit` 回答 `not_writable` |
| `--config <file>` | 用这个配置文件代替仓库的配置（`--pr` 或 `--mr` 时是基础分支的） |
| `--max-cost-usd <n>` | 这个变更各轮合计的花费上限，包含状态里已花的；否则用配置里的 `maxCostUsd` |
| `--json` | 在 stdout 打印一行 JSON，说明结果 |

**一轮做什么。** 它取前 5 条仍未关闭的问题。每条在 `fixer` 角色上得到一次调用，规则同 [`ocra fix`](#ocra-fix)：在 head 上重新找到问题的代码，回答只能改这些行，要小，语法错误不能增加。这条通道写不了的问题（它的代码在文件里出现不止一次或不在变更的行里，跨度超过 30 行，或 fixer 回答没有局部修改能修复它），在 `direct` 运行时上改由 `fixer` 角色的一个任务处理：一个 agent，带着审查的只读工具，外加一个 `edit` 工具，用来替换内存里那份 head 副本中某个文件的整行。它没有 shell，不写磁盘，不访问网络；只有以完成工具结束时它的修改才算数，修改可以跨变更内的多行和多个文件。在 `opencode` 运行时上，这样的问题交给人处理（`not_candidate`）。无论哪条通道，修改之后都要通过代码里的闸门，以及 `verifier` 角色上的一次调用：它读问题、被替换的行、替换内容和周围的文件，必须回答这个修改解决了问题且没有带来新的缺陷；回答"不确定"、调用失败，或回答不是约定的 JSON，都会拒绝这个修改。通过的修改按问题的顺序合在一起；与前面的修改碰到同样的行，或会让这一轮超过 10 个文件或新增 200 行的，留到下一轮。提交只写在这一轮读到的 head 之上，从不强制推送，提交信息列出它修复的问题。

提交写入后，这一轮会在拉取请求或合并请求上留一条评论：这个提交修了什么、哪些没有修以及原因，还有撤销它的 `git revert` 命令（v0.22.0）；评论发不出去只是一条警告，提交仍然有效。

**闸门。** 一轮只修改变更里审查会读的普通文件。它从不修改 CI 配置（`.github/`、`.gitlab/`、`.gitlab-ci.yml`、`.circleci/`、`.buildkite/`、`Jenkinsfile`、Azure 和 Bitbucket 的流水线）、`.ocra/`、`AGENTS.md`、`CODEOWNERS`、依赖清单（`package.json`、`pyproject.toml`、`requirements*.txt`、`Pipfile`、`go.mod`、`Cargo.toml`、`pom.xml`、Gradle 的构建和设置文件、`Gemfile`、`composer.json`）、`Dockerfile`、`Makefile`、生成的文件、迁移文件，以及 `--protect` 指定的路径。在测试文件里，修改不能新增关掉测试的调用（`.skip`、`.only`、`.todo`、`xit`、`@Ignore`、`@Disabled`、`pytest.mark.skip`、`skipif`、`xfail`、`unittest.skip`、`t.Skip`、`#[ignore]`）。修改不含控制字符或双向文本字符。被闸门拒绝的问题交给人处理。

**失败的检查。** 带 `--checks` 时，一轮还会读取 head 的检查：在 GitHub 上是它的 check run，在 GitLab 上是合并请求在这个提交上最新流水线的作业。一个检查要被处理，须是失败的（GitHub 上是失败或超时，不含被取消或跳过的；GitLab 上是不允许失败的作业失败了），并且在目标分支的 head 上没有以同样的名字失败：那里本来就坏的不归这个变更修。一轮最多处理 3 个，排在问题之后，同在 5 个条目的限额内。每个检查交给上文那样的 fixer 任务，给它检查的名字、失败作业日志中失败那一步输出的最后 200 行（最多 20,000 个字符，去掉时间戳和终端控制序列；在 GitHub Actions 上是失败的那一步，在 GitLab 上是作业的脚本段，这样失败之后才运行的步骤不会把它挤出去）以及变更涉及的路径；日志对它只是数据，ocra 什么都不运行。在 GitHub 上读取 Actions 作业的日志需要令牌有 `actions: read`；没有时，以及其他应用的检查，任务拿到的是检查自己报告的内容；两者都没有的检查交给人（`not_candidate`），在 `opencode` 运行时上所有检查都是如此。任务被要求修代码，只有变更有意改了行为时才改测试，失败不是变更造成时（服务故障、超时、缺少机密）不做修改；闸门仍然拒绝关掉测试的修改，verifier 仍然读每一处修改。一个失败的检查只要失败的方式不变，就是同一个条目，尝试次数也延续：按它的名字和日志里第一行指出失败的内容来认，数字和 id 除外。检查还在运行且没有别的条目可处理时，这一轮什么都不做，不计轮数，回答 `waiting`：等它们结束后再启动下一轮。平台的检查读不到时，这一轮只处理问题，并给出警告。

**合并冲突。** 带 `--conflicts` 时，一轮先在本地克隆里读取基准分支是否还能合并进 head：对两个提交运行 `git merge-tree`，不检出任何文件，也不运行仓库的钩子、合并驱动或过滤器。能合并时，这一轮与不带该选项时相同。不能合并时，这一轮只处理冲突，每条问题都是 `deferred`，原因为 `conflicts`，不计尝试次数。每个冲突的文件是一个条目。`fixer` 角色的一次调用读取它的冲突区域（共同祖先的文本、两边的文本和每个区域前后 20 行，都作为数据），逐个区域作答，或者拒绝；代码把答案放回 git 已合并的行之间，所以那些行不会变。留下冲突标记、含控制字符或双向字符、或让文件解析得更差的答案会被拒绝，`verifier` 角色的一次调用还必须回答每个区域都保留了两边的意图。一轮最多解决 5 个文件，每个文件 8 个区域，每个区域 120 行（超出为 `too_large`）；某一边删除、重命名、改了模式或是二进制的文件，以及闸门保护的文件，交给人处理（`needs_human`）。只有每个冲突文件都解决了才会写入合并；否则什么都不写，还没处理的文件是 `deferred`，原因为 `conflicts`。`--level propose` 时每个条目是 `proposed`，`resolved` 是文件解决后的完整内容，`mergeParent` 是要合并的基准分支提交。`--level commit` 时这一轮写一个合并提交，父提交是 head 和那个提交，并从克隆推送到变更请求的分支：普通推送，从不强推，也从不变基，所以分支移动了会得到 `head_moved`，令牌推不上去的分支（fork、受保护分支）会得到 `not_writable`。提交的作者是机器人账号的地址（在 GitHub 上是 `<id>+<login>@users.noreply.<host>`，GitHub 因此显示这个账号），这一轮的评论会说明它是基准分支的合并，并给出撤销用的 `git revert -m 1`（v0.23.2）。只在仓库所有者希望 ocra 往分支上加合并提交的仓库里对冲突使用 `--level commit`（[ADR-0079](https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/adr/0079-merge-conflicts-as-a-merge-commit.md)）。

**上限。** 一条问题有 2 次尝试，一个变更有 6 轮，各轮合计受花费上限约束。状态记录这些计数：每一轮都传入上一轮打印的状态。没有尝试过的问题，或修改没有写入的问题（这一轮已满、head 变了），不消耗尝试次数。

加 `--json` 时，stdout 是一行：

```json
{"headSha":"<40 hex>","outcome":"committed","stopped":null,"commitSha":"<40 hex>","mergeParent":null,"items":[{"fingerprint":"b491fb26b470419c","check":null,"conflict":null,"resolved":null,"regions":[],"outcome":"fixed","reason":null,"cause":null,"edits":[{"path":"src/total.ts","startLine":3,"endLine":3,"replacement":"  for (let i = 0; i < prices.length; i++) sum += prices[i];"}]}],"state":{"rounds":1,"costUsd":0.06,"items":{"b491fb26b470419c":{"attempts":1}}},"usage":{"inputTokens":0,"cachedTokens":0,"outputTokens":0,"reasoningTokens":0,"costUsd":0}}
```

| `outcome` | 含义 | 退出码 |
|---|---|---|
| `committed` | 分支上有了一个提交 `commitSha`；处理冲突的一轮之后它是合并提交，`mergeParent` 是它的第二个父提交 | `0` |
| `proposed` | `--level propose`：修改或解决后的文件在 `items` 里，没有提交 | `0` |
| `nothing` | 没有问题得到通过检查的修改；`items` 说明原因 | `0` |
| `stopped` | 没有运行：变更达到了 `stopped` 指出的上限（`rounds` 或 `spend`） | `0` |
| `head_moved` | head 不是 `--head`，或 ocra 读取之后分支有了新提交；没有提交 | `3` |
| `not_writable` | 令牌不能写这个分支，或变更是本地的 | `3` |
| `waiting` | `--checks`：head 的检查还在运行，且没有别的条目可处理；不计轮数 | `0` |

`items` 的每一项是一条问题，顺序与输入相同，之后是每个失败的检查各一项：它的 `check` 是检查的名字（问题为 `null`），`fingerprint` 是循环用来记录它尝试次数的 id。处理合并冲突的一轮改为每个冲突文件一项，排在被推迟的问题之后，它的 `conflict` 是文件路径（其余为 `null`）：

| 条目的 `outcome` | 含义 | `reason` |
|---|---|---|
| `fixed` | 它的修改在提交里，或它的文件已在合并提交里解决 | `null` |
| `proposed` | 它的修改或解决后的文件（`resolved`）在结果里，等人提交 | `null` |
| `rejected` | 这一轮没有修改通过；下一轮可以再试 | `failed`、`unchanged`、`unsafe`、`syntax`、`declined`、`unresolved`、`unsure` 或 `unchecked` |
| `deferred` | 没有尝试，或没有写入；不计尝试次数 | `no_room`、`overlap`、`conflicts`、`head_moved` 或 `not_writable` |
| `needs_human` | 已关闭，交给人决定 | `not_candidate`、`no_parser`、`out_of_scope`、`protected`、`too_large`、`tamper`，或两次尝试都用完时的 `attempts` |
| `gone` | 它的代码已不在 head 上 | `stale` |

`edits` 替换 `headSha` 上 `path` 的第 `startLine` 到 `endLine` 整行；只有 `fixed` 或 `proposed` 的条目才有，冲突文件的条目始终为空：它是 `proposed` 时 `resolved` 是整个文件，否则为 `null`。这时它的 `regions` 列出每个冲突区域及其答案，方便人不看整个文件就能读：`line` 是答案在 `resolved` 里的起始行，`ours` 是变更请求一边的行，`theirs` 是基准分支一边的行，`resolved` 是写下的行，都用换行连接；其他条目的 `regions` 为空（v0.23.0）。条目的 `reason` 为 `failed` 时，`cause` 说明失败的是什么，取值与 [`ocra fix`](#ocra-fix) 相同，否则为 `null`（v0.21.0）。用法、输入和配置错误，以及无法启动的运行时，退出码为 `2`。结构是 `@open-cr-agent/cloud-contract` 里的 `mendResultSchema`、`mendStateSchema` 和 `mendFindingsSchema`（[ADR-0078](https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/adr/0078-fix-loop.md)）。评审者的要求仍在计划中。v0.20.0 新增；带 `edit` 工具的任务是 v0.21.0 新增；失败的检查和合并冲突是 v0.22.0 新增。

## ocra metrics

对 `.ocra/sessions/` 下已完成的审查做统计，数据来自每个会话的 `report.json`，不调用任何模型：

```bash
ocra metrics                       # 文本表格
ocra metrics --format json         # 给看板或脚本用；带 "version": 1
ocra metrics --since 2026-10-01    # 只统计在该日期及之后开始的运行
ocra metrics --sessions /srv/ocra  # 另一个会话目录，比如 CI runner 上的
```

它报告运行次数（按结论分；不完整的运行次数，即留下了没审完的文件或未核查的 critical、退出码为 3 的运行；没有可读报告的会话数）、花费（总计、每次运行、token 数）、问题数（报告条数、按指纹去重数、按严重程度和核查状态分）、早先问题的去向（fixed：后来代码已不在；dismissed：被审查者驳回；两者之比即接受率），以及每个审查员各自的任务数、失败任务数、花费和同样的统计。`--resume` 复用的任务在复用它的那次运行里不计花费：它的花费只计一次，记在实际付费的那次运行里。已修复或被驳回的问题归于上次审查记录的审查员，没有记录时归于最先报告该指纹的审查员。只统计版本 1 的报告；JSON 输出和报告一样是带版本号的约定。

## ocra memory

有些问题本身没错，但已被接受：风险在别处处理了，或者团队决定接受它。把它们记下来，ocra 就不会再报告：

```bash
ocra review                                  # 每条问题都会显示一个 id，例如 #1a2b3c4d
ocra memory add 1a2b3c4d --reason "重试次数由网关限制。"
ocra memory list
```

`ocra memory add` 在 `.ocra/sessions/` 下最新的会话里查找这个 id（`--session <dir>` 可指定别的会话），写入 `.ocra/memory.json`；提交它即可共享。被记住的问题（审查员、文件和引用的代码都相同）不会出现在报告里，只会计数；审查员也会看到自己所审文件里已被接受的问题。审查 PR 时这个文件从 base 提交读取，所以 PR 无法压掉针对自己的问题。文件无效时审查会报错停止。

### ocra Cloud 账户里的 memory

[登录](#ocra-loginocra-logoutocra-whoami)后，也可以在 ocra Cloud 网页上的某次审查里记住一个问题（"Remember"，并填写理由）。每次审查前（本地、`--pr` 或 `--mr`），ocra 按仓库哈希读取你的账户为这个仓库保存的条目（`GET /api/memory`），与 `.ocra/memory.json` 一起生效：任一方列出的问题都不报告，两边都列出的计为仓库的。报告写明每个被隐藏问题的来源 `source`（`repository` 或 `account`）；终端打印 `N finding(s) hidden by your ocra Cloud memory`，PR 的总结评论也会给出数量。

- 未登录或设置了 `OCRA_CLOUD=off` 时从不读取；`--no-upload` 不影响它（读取不会发送任何关于本次审查的内容）。
- 读取失败时会给出警告，只使用仓库的文件。
- 只在账户[共享问题](#ocra-loginocra-logoutocra-whoami)时生效，因为它按账户的盐计算的哈希保存；否则审查会提示一次：只应用仓库自己的 memory。
- `ocra memory add` 只写入 `.ocra/memory.json`。

## ocra login、ocra logout、ocra whoami

**开发中。** ocra Cloud（[ADR-0024](https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/adr/0024-ocra-cloud.md)）的地址是 https://app.ocracloud.com；`OCRA_CLOUD_URL` 可以指定其他服务器，例如公司自己部署的服务器；它的证书由公司自己的证书颁发机构签发时，用 `NODE_EXTRA_CA_CERTS` 把该机构交给 Node，否则每次调用都会失败并给出证书错误。不登录也能审查；设置 `OCRA_CLOUD=off` 后这几个命令拒绝运行。

```bash
ocra login                                    # 显示一个验证码，并打开浏览器确认
ocra whoami                                   # 当前登录的 GitHub 账号，以及本机是否发送问题
ocra logout                                   # 在服务器上结束会话，并删除本地保存的会话
```

`ocra login` 使用 OAuth 设备授权流程（RFC 8628）：打印一个验证码（如 `BCDF-GHJK`），打开服务器上的确认页（加 `--no-browser` 只打印链接；不在当前服务器上、或不是 https 或本机 http 的页面只打印），然后等待你在已登录该服务器的浏览器里批准。只批准你自己刚刚发起的验证码。这个会话可以用服务器上保存的 key 调用模型、上传结果，但不能读取这些 key，也不能修改账号；可在服务器的会话页面撤销。

**会话**保存在 `~/.config/ocra/credentials.json`（`$XDG_CONFIG_HOME/ocra/`，Windows 上为 `%APPDATA%\ocra\`），只有你本人可读。

- 它和旁边的盐都以原子方式写入（先写临时文件再改名）。文件里没有会话时按未登录处理：审查会警告一次并指出该文件，然后不连接 ocra Cloud 继续；`ocra logout` 会删除它。
- 访问令牌有效期一小时；刷新令牌每次使用后都会更换。同时运行的进程共用会话：同一时刻只有一个进程在 `credentials.json.lock` 下续期，其他进程等待它（最多两分半钟，等待超过五秒时打印 `Waiting for another ocra process to renew the ocra Cloud session...`；超过 90 秒的锁，或其进程在本机已退出的锁，视为已退出的进程留下的，会被打破），然后使用它保存的结果。`ocra login` 和 `ocra logout` 也取同一把锁，续期也不会覆盖期间另存的会话。有效令牌收到 401 时续期并重试一次。
- 服务器拒绝续期即会话结束：审查会警告 `your ocra Cloud session ended: run ocra login`；`ocra whoami` 以 1 退出。
- 连不上 ocra Cloud（网络错误、5xx、429）时会话保留；审查只警告一次，然后在没有你账户的规则、限额（含 `maxCostUsd`）、模型和 memory 的情况下运行，也不上传；指定了 `ocra-` 模型的审查则以错误停止，`ocra whoami` 以 2 退出。账户设置返回 404 视为没有设置，不警告。
- `ocra login` 拿到令牌却读不到你的登录名时，仍保存会话，并说明登录名未知。

**经由 ocra Cloud 的模型。** 登录后，`ocra-<provider>/<model>` 会经由 ocra Cloud、使用服务器上为 `<provider>` 保存的 key 调用（服务器列出的 chat completions 接口；供应商只有 Messages 接口时用它，例如 `ocra-anthropic/<model>`）：

```json
{ "runtime": "direct", "models": { "standard": "ocra-openrouter/qwen/qwen3.8-27b:free" } }
```

- 按 ocra Cloud 列出的模型价格计费（输入、输出和缓存输入，每百万 token），报告中的费用和 `--max-cost-usd` 都会计入。ocra Cloud 没有列出价格的模型没有价格：两者都不计入它，并给出点名该模型的警告。
- 提示词及其中引用的代码经过 ocra Cloud，它只记录每次调用的模型、状态码、token 数和耗时，从不记录内容。
- 没有使用 `ocra-` 模型的审查不读取会话，也不连接 ocra Cloud；配置中以 `ocra-` 名称自行声明的 provider 保持原有声明。
- [推理强度](./configuration#推理强度)按 ocra Cloud 为该 provider 列出的方式发送（`openai`：`reasoning_effort`；`openrouter`：`reasoning.effort`），没有列出时用 `openai`；不认识的方式会被忽略并给出警告。回答不是 provider 列表时审查停止。
- 使用 `"runtime": "direct"` 时，ocra 在整个运行期间于令牌过期前五分钟续期。续期失败时警告一次并重试：先隔一分钟，之后间隔逐渐拉长（最长五分钟），令牌过期后也继续，直到运行结束。`opencode` 只在启动时读取一次令牌，所以 ocra 给它一个比 `runTimeoutMinutes` 多十分钟仍有效的令牌；运行可能比任何令牌都长时会警告：大约一小时后，经由 ocra Cloud 的调用会失败。只有新令牌会更持久时，ocra 才为此续期已保存的令牌；已保存的令牌几乎同样新时不续期。

**账户设置。** 登录后，`ocra review` 会把账户设置放在配置之下应用（见[账户设置](./configuration#账户设置)）。账户还可以开启 `ultra`，效果如同传了 `--ultra`，除非配置设置了 `ultra`；命令行上的 `--ultra` 和 `--no-ultra` 始终生效。账户补充了哪些会打印出来（`From your ocra Cloud settings: …`）。`--plan` 也会读取它们，并在末尾列出 Settings，标明每项设置的来源：`shared`（extends 的共享配置）、`file`、`env`（`OCRA_MODEL_*`、`OCRA_EFFORT_*`）、`account`（含 `ultra`）、`depth`（[审查深度](./configuration#审查深度)填补的项）、会合并的列表（`include`、`exclude`、规则）用 `+` 连接来源（例如 `shared+account`；账户的 `exclude` 只在配置没有设置时生效），或 `default`。连不上 ocra Cloud 时会给出警告，计划只显示配置本身。

**审查会上传什么。** 每次审查后，已登录的 CLI 会发送统计：结论、是否审完所有文件、各级别问题数、文件数、任务数、token、费用、耗时、来源（本地、GitHub、GitLab）和 ocra 版本；每个审查员的任务数、失败任务数、各级别问题数、费用（不含 `--resume` 复用的任务，本次运行没有为它们付费），以及它早先的问题已修复或被驳回的数量；已确认、不确定和未检查的问题数；早先的问题一共有多少已修复或被驳回（计入记录的审查员；记录审查员之前的问题，只有本次审查仍有同一指纹时才计入）。除非账户开启了共享问题，从不发送路径、标题、指纹、问题描述或代码。

- 仓库以其规范化地址 `https://host/owner/repo` 加盐后的 SHA-256 发送（去掉用户名、凭据、端口、末尾的 `/` 和 `.git`，统一大小写，因此 `git@host:owner/repo.git` 和 `ssh://git@host:22/owner/repo` 得到同一个值）。使用 `--pr` 或 `--mr` 时是平台上的仓库；本地审查用 origin（本地路径形式的远程按原样使用；没有 origin 时用目录）。本地审查的上传不说明是哪个仓库：服务器可以把同一仓库的审查归在一起，却不知道是哪个仓库。打开 [`cloud.shareRepoName`](./configuration#ocra-cloud) 后，每次上传还会给出仓库的路径（`owner/name`）和规范化后的地址。自建 GitLab 部署在子路径下（`https://host/gitlab/…`）或由另一台主机提供 SSH 时，SSH 克隆的地址与合并请求的不同，因此对该克隆的本地审查与 `--mr` 审查算作不同的仓库；HTTPS 克隆则一致。
- `--pr` 或 `--mr` 审查还会说明是哪个拉取请求或合并请求：仓库的上述地址、编号和头提交，以便 ocra Cloud 在其上显示结论；还有每个[关联的 issue](./how-it-works#关联的任务) 的平台、编号、地址和状态，以便检查是否关联了 issue；交给任务的每条 [learning](./rules#ocralearnings) 的 id，以便统计每条 learning 被用到的次数；以及每条[合并前检查](./how-it-works#合并前检查)的 id 和结果。本地审查只在共享问题时发送 learning 的 id。代码、标题和路径（包括 issue 的标题和标签）仍只按下文发送。
- 远程是 SSH 形式、或带端口或末尾 `/` 的仓库，在 0.5.0 之后得到过一次新的哈希（0.5.0 按原样计算）：旧的审查和 memory 要重新记录后才能对上。
- 盐是随机值，保存在凭据旁的 `upload-salt`，所以每台机器的哈希不同。账户开启共享问题时，盐是账户的：登录时和每次审查前读取，保存在 `account-salt`（只有你可读），所以你的所有机器哈希一致。审查需要本机的盐却读不了 `upload-salt`（例如 `sudo ocra` 之后属于另一个用户），或无法创建它（目录只读）时，文件保持原样，审查给出警告，不向 ocra Cloud 发送任何内容。无法把账户的盐保存到 `account-salt` 时，审查给出警告，并使用刚收到的盐。
- `--no-upload` 跳过单次上传，`OCRA_CLOUD=off` 关闭 ocra Cloud；上传失败只会给出警告。

**共享问题。** 在账户的 Settings 里打开"Send findings and the code they quote to ocra Cloud"（默认关闭）后，上传还会带上每个问题的指纹、审查员、级别、类别、核查结果、文件、行范围、标题、描述、建议和引用的代码，让网页可以完整展示这次审查；问题带有修复时，还会带上修复（替换的行和替换后的代码），以及 `--ultra` 是否以低置信度保留了它（v0.19.0），[`ocra fix`](#ocra-fix) 会读取这一项。上传还会带上问题的证据，和拉取请求评论里展示的一样：最多 5 条，每条一行，超过 300 个字符截断（v0.19.0），以及它所依据的规则或经验的类型和 id（v0.24.0）。它还会按指纹列出本次审查看到已修复或被驳回的早先问题（每类最多 200 个），让网页可以标出它们。修复要么原样发送，要么不发：脱敏或 4 KB 截断会改动它时就不发，因为网页可以把它提交到拉取请求。关联 issue 的标题和标签、每条合并前检查的理由也随之发送，同样经过脱敏。ocra Cloud 自己运行的审查不论这个开关是否打开，都会保留它的问题（见[自动审查](./cloud#自动审查与-ocra)）。

- 发送前，ocra 会把路径、类别、标题、描述、建议、代码和证据中看起来像密钥的内容替换为 `[redacted]`，并把问题标记为已脱敏：PEM 和 PGP 私钥块、AWS key id（`AKIA…`、`ASIA…`）、GitHub token（`ghp_`、`gho_`、`ghs_`、`ghu_`、`ghr_`、`github_pat_`）、GitLab token（`glpat-`）、`sk-` 开头的 key（包括 `sk-ant-`、`sk-or-`、`sk-proj-`）、Slack token（`xoxb-` 等）、Google API key（`AIza…`）、npm token（`npm_…`）、Slack 和 Discord 的 webhook URL、URL 中的密码（`postgres://user:…@`）、`curl -u user:…`、`--user user:…` 和 `mysql -p…` 中的密码、`Bearer` 或 `Basic` 之后（同一行或下一行）的凭据（之后若是普通单词，如在行文中，则保持不变；小写形式，如 HTTP/2 头中的，只在其后是 16 个字符以上且含数字的凭据时才算），以及赋给 `password`、`passphrase`、`secret`、`secret_key`、`token`、`api_key` 这类名字的值：带引号的（`password = "…"`，包括在 JSON 字符串中引号被转义的），不带引号、写成 `NAME=…`（`.env`、命令行参数、查询字符串）或位于行尾的（YAML 中的 `password: …`），YAML 块标量的各行（`password: |`），或 `--password …`、`--api-key "…"` 这类参数之后的值（路径除外）。不带引号的值如果只有字母（`changeme`、`string`），或看起来是代码（函数调用、`process.env.TOKEN` 这类带点的名字、`${…}`、以 `,` 或 `;` 结尾的行），则保持不变；但在 `NAME=` 或参数之后，结尾的 `;`、`,`（参数之后还有 `)`）表示 shell 命令结束，前面的值仍会被替换。此外还有 32 个字符以上的十六进制串（包括 `dop_v1_` 这类前缀之后的），以及 32 个字符以上、含数字且看起来随机的 base64 串（路径，以及以哈希加扩展名结尾的文件名如 `index-Bx92KqLm.js`，不受影响）。这只能识别模式，不能识别所有密钥；服务器会再做一遍同样的处理。
- 最多 200 个问题、256 KB 文本，每个字段先截断到 4 KB 再脱敏（标记为已截断；截断处所在的 token 会整体脱敏）。终端打印 `Sent this review's counts and N finding(s) to ocra Cloud`。
- 只有服务器返回账户的盐（它只在开关打开时返回）、并且本机同意时才发送问题：`ocra login` 发现开关打开时会说明这一点，并在凭据旁的 `share-findings`（只有你可读）中记下本机的同意；审查发现开关关闭时会删除它。打开开关后，或关闭再打开后，请在每台机器上重新运行 `ocra login`；在此之前，这台机器的审查会给出警告，只发送统计。因此 ocra Cloud 不能自己开启共享。审查前连不上 ocra Cloud 时，审查会警告，用 `account-salt` 里的盐（没有时用本机的）计算哈希，不发送问题，也不应用账户的 memory。
- `--no-upload` 和 `OCRA_CLOUD=off` 仍然什么都不发送。

**实时观看审查。** 账户开启共享问题时，已登录的审查还会在运行中把进度实时转发给 ocra Cloud：即 `ocra serve` 流式输出的事件（见 [ocra serve](./serve)），包括问题，按同样方式脱敏，大约每秒发送一次（`POST /api/live`）。终端会打印一次 `[ocra] Watch this review live: <地址>`；在这个页面上可以把这次运行按人或按链接分享给别人，让他们实时观看并评论其中的问题。v0.11.0 新增。

- 转发从不拖慢审查：ocra Cloud 没有接收的一批事件会在一秒后重发；连续失败三次后 ocra 警告一次（`stopped relaying this review to ocra Cloud live`）并继续审查。结束时最多再等五秒发送剩下的事件。
- 服务器还不支持实时转发（404），或已不再接收这次运行的事件（ocra Cloud 每次运行最多保留 5,000 个），转发会结束，不给警告。
- `--no-upload` 和 `OCRA_CLOUD=off` 不转发任何内容，未开启共享问题的账户也不转发。

## ocra plugins

在这台机器上允许你的 ocra Cloud 设置所列出的插件（见[来自 ocra Cloud 账户的插件](./plugins#来自-ocra-cloud-账户的插件)）。这些命令不连接 ocra Cloud；`allow` 和 `deny` 会运行 npm。

```bash
ocra plugins allow <name>@<version>   # 精确版本：先显示这个包，再安装
ocra plugins deny <name>              # 移除它：之后不再加载
ocra plugins list                     # 已允许的插件及其 integrity
```

`allow` 运行 `npm view <name>@<version> --json`，显示包的名称、版本、发布者、维护者和 integrity，然后运行 `npm install --ignore-scripts --no-audit --no-fund --save-exact --prefix <dir> <name>@<version>`，安装到 `~/.config/ocra/plugins/`（`$XDG_CONFIG_HOME/ocra/plugins/`，Windows 上为 `%APPDATA%\ocra\plugins\`）。只有 npm 安装的正是这个版本、且 integrity 与 registry 一致时，才记录到该目录的 `plugins.json`。npm 以参数列表运行，从不经过 shell，使用你的 npm 配置中的 registry 和凭据。不是 npm 包名的名称、或者是范围或标签的版本，会在运行 npm 之前被拒绝（退出码 2）。
