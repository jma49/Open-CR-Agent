## ocra init

为当前所在的仓库配置好 ocra：写入 `.ocra/config.json`，加 `--github` 时再写入 workflow `.github/workflows/ocra.yml`，然后打印剩下要做的事。它不调用任何模型或网络服务，也不会替你运行 `gh` 或 `git`。

```bash
ocra init                          # 按环境里的 key 写 .ocra/config.json
ocra init --github                 # 同时写 GitHub workflow，可安全审查来自 fork 的 PR
ocra init --github --same-repo-only
ocra init --provider anthropic     # 当前 shell 里没有这个供应商的 key 时指定它
```

| 参数 | 含义 |
|---|---|
| `--github` | 同时写入 `.github/workflows/ocra.yml`：即 `pull_request_target` 上的[fork 方案](./github#来自-fork-的-pr)。成员和协作者的 PR 每次推送都审查，其他人的 PR 在维护者每次加上 `ocra-review` 标签时审查一次；只检出 base 分支，不运行 PR 里的任何东西 |
| `--same-repo-only` | 与 `--github` 一起用，改写普通的 [`pull_request` workflow](./github#github-action)。来自 fork 的 PR 在那里拿不到 secret，不会被审查；对接受外部贡献的项目来说，这往往是大部分 PR |
| `--provider <name>` | `gemini`、`anthropic`、`openai` 或 `openrouter`，代替从环境里找到的 key |
| `--force` | 文件已存在时替换它。不加时保留已有文件，并说明保留了 |

**模型。** 不加 `--provider` 时，ocra init 依次查找 `GEMINI_API_KEY`、`ANTHROPIC_API_KEY`、`OPENAI_API_KEY`、`OPENROUTER_API_KEY`，用第一个已设置的，并列出找到的其他 key。只有在没有其他 key 时才会选 OpenRouter 的免费模型。它为每一档写一个模型，走该供应商兼容 OpenAI 的端点，并带上每百万 token 的标价（取自 2026-10-04 的 [models.dev](https://models.dev)），所以报告的花费和 `--max-cost-usd` 都会计入：

| 供应商 | `top` | `standard` | `light` |
|---|---|---|---|
| `gemini` | `gemini-3.1-pro-preview` | `gemini-3.5-flash` | `gemini-flash-lite-latest` |
| `anthropic` | `claude-opus-5-5` | `claude-sonnet-5-5` | `claude-haiku-4-5` |
| `openai` | `gpt-6-sol` | `gpt-6-sol` | `gpt-6-luna` |
| `openrouter` | `stealth/space-bunny-alpha`，免费（[预览模型](./providers#openrouter-上的免费模型)） | 同左 | 同左 |

**运行时。** 配置里设置 `"runtime": "direct"`，只调用它声明的端点；不装 OpenCode 时，ocra 约占 11 MB 而不是 175 MB（[不装 OpenCode](./installation#不装-opencode)）。出于同样的原因，workflow 给 Action 传 `opencode: false`。不是 ocra init 写的配置不受影响：默认运行时仍是 `opencode`；`--github` 保留了一个没有设置 `direct` 的已有配置时，workflow 照旧安装 OpenCode。direct 运行时已经通过 OpenRouter 做过真实审查；通过 Gemini、Anthropic、OpenAI 兼容 OpenAI 的端点还没有。

以 Gemini 为例，写出的文件是：

```json
{
  "$schema": "https://raw.githubusercontent.com/jma49/Open-CR-Agent/main/docs/schema/config.v1.json",
  "runtime": "direct",
  "models": {
    "top": "gemini-api/gemini-3.1-pro-preview",
    "standard": "gemini-api/gemini-3.5-flash",
    "light": "gemini-api/gemini-flash-lite-latest"
  },
  "providers": {
    "gemini-api": {
      "type": "openai-compatible",
      "baseUrl": "https://generativelanguage.googleapis.com/v1beta/openai",
      "apiKeyEnv": "GEMINI_API_KEY",
      "models": {
        "gemini-3.1-pro-preview": { "input": 2, "output": 12, "cachedInput": 0.2 },
        "gemini-3.5-flash": { "input": 1.5, "output": 9, "cachedInput": 0.15 },
        "gemini-flash-lite-latest": { "input": 0.3, "output": 2.5, "cachedInput": 0.03 }
      }
    }
  }
}
```

key 本身从不写入文件：文件里只有保存它的环境变量名。模型和价格可以像其他[配置](./configuration)一样修改。

**workflow** 就是手册里的方案，加上作为 secret 的供应商 key、`opencode: false`，以及每次审查的 `--max-cost-usd 2`。它把 Action 固定到这个版本的 ocra 所记录的发布提交上，并以注释写明版本，和 [GitHub](./github) 页面里的示例一样。`ocra init --github` 会打印剩下的步骤：

```text
Wrote .ocra/config.json: Gemini models through GEMINI_API_KEY, on the direct runtime.
Wrote .github/workflows/ocra.yml: pull requests from members are reviewed on every push, anyone else's once each time a maintainer adds the ocra-review label.

Next:
  1. Store the key as a repository secret (gh asks for its value):
       gh secret set GEMINI_API_KEY
  2. Create the label that starts a review of an outside pull request:
       gh label create ocra-review --description "Review this pull request with ocra"
  3. Commit .ocra/config.json and .github/workflows/ocra.yml, and merge them into the default branch:
       ocra reads its configuration from a pull request's base branch.
```

私有仓库请按 workflow 里的注释删掉 `persist-credentials: false`。在仓库内任何目录运行，ocra init 都写到仓库根目录；它拒绝经由符号链接写入；没找到 key 又没给 `--provider`，或不在 Git 仓库里时，它以退出码 `2` 结束，什么也不写。

## ocra review

审查当前 Git 仓库里的代码改动。

```bash
ocra review [options]
```

| 参数 | 含义 |
|---|---|
| *（不带参数）* | 审查未提交的改动：已暂存、未暂存和未跟踪的文件 |
| `--from <ref>` | 审查 `--to` 从 `<ref>` 分叉以来的改动（基于 merge base） |
| `--to <ref>` | 区间终点，默认 `HEAD`，必须配合 `--from` 使用 |
| `--commit <sha>` | 审查单个 commit 相对其父 commit 的改动 |
| `--format text\|json\|sarif` | 输出格式，默认 `text`。`sarif` 输出 [SARIF 2.1.0](#sarif-输出) |
| `--output <file>` | 把结果写入文件，而不是输出到 stdout |
| `--pr <number>` | 审查一个 GitHub PR，见 [GitHub Pull Request](./github) |
| `--repo <owner/name>` | `--pr` 所在的仓库（默认取 `GITHUB_REPOSITORY` 或 `origin`） |
| `--mr <iid>` | 审查一个 GitLab Merge Request，见 [GitLab Merge Request](./gitlab) |
| `--project <id\|路径>` | `--mr` 所在的项目（默认取 `CI_PROJECT_ID` 或 `origin`） |
| `--publish` | 配合 `--pr` 或 `--mr`：把评审发布到 PR 或 Merge Request |
| `--full` | 配合 `--pr` 或 `--mr`：审查所有文件，而不是只审查上次评审之后改动过的文件 |
| `--max-cost-usd <n>` | 本次运行的花费上限。花费达到上限的 80% 时审查任务停止：不再启动新任务，正在运行的任务也会被停下，已经找到的问题保留；这些任务的文件算作未审查，所以退出码为 `3`。剩下的部分留给核查和裁决。如果这部分也用完，剩余的问题会标为*未核查*，不会拦下改动，报告里也会写明。运行中的任务大约每 10 秒报告一次花费，所以一次运行最多会超出上限：每个任务在这段时间里的花费，加上它正在进行的那一步。任务按分组逐个运行，所以受上限约束的运行会审完一部分文件，而不是每个文件都只开个头；使用 `--pr` 时，下一次审查会接着审剩下的文件 |
| `--plan` | 不调用任何模型（免费），显示会审查和排除的文件、分组、审查任务以及每个任务首轮提示词的大小，包括 `--ultra` 下或 5 个文件以上的分组在审查前的那一次规划调用。任务的模型链已知时，它按链上第一个模型的输入单价估算这些首轮提示词的输入花费，逐个任务给出并给出总计：[自行声明的供应商](./providers#你自己的端点) 的模型用声明的价格，价格为 0 或经由 ocra Cloud 的模型显示 `input unpriced`，其他只由运行时目录定价的模型显示 `input price unknown`。这只是输入部分的估算：输出、后续轮次、核查和裁决在运行前无法得知。由于跳过了 light 模型分组，需要分组的较大改动会按每个文件一组显示（超过 20 个文件时按目录分组）。和 `--pr` 一起用时按全量审查来规划，而不是只看上次审查以来的改动；不会写会话日志 |
| `--import-sarif <文件>` | 把分析工具（Semgrep、CodeQL 等）写出的 SARIF 2.1.0 日志里的结果加入审查，可以重复使用。只保留落在改动行上的结果，它们和审查员的问题一样经过核查和裁决。见 [SARIF 输入](#sarif-输入)。不能和 `--plan` 一起用 |
| `--ultra` | 以成本换召回率，见[模式](./how-it-works#模式) |
| `--reviewers <ids>` | 只运行这些审查员，用逗号分隔（例如 `security`） |
| `--temperature <n>` | 每次模型调用的采样温度，0 到 2；覆盖[配置](./configuration#执行参数)里的 `sampling.temperature`。不设置时用各供应商的默认值 |
| `--seed <n>` | 每次模型调用的采样种子，运行时和供应商支持时才生效；覆盖 `sampling.seed`。`opencode` 运行时没有种子设置，会报告为未应用 |
| `--config <文件>` | 读取这个配置文件，而不是仓库的 `.ocra/config.json`（与 `--pr` 或 `--mr` 一起用时，代替 base 分支的那份）。文件是你自己的，所以和 `--no-repo-config` 一起用也生效；它列出的插件从文件所在目录解析，审查 PR 和 Merge Request 时照样不加载。见[配置](./configuration) |
| `--no-repo-config` | 忽略 `.ocra/config.json` 及其中列出的插件（与 `--pr` 一起用时，base 分支的也忽略），模型改从 `OCRA_MODEL_*` 或 `--config` 读取；memory、rules 和 `AGENTS.md` 从 `--from` 所在的提交读取，否则不使用。审查不信任的代码时使用 |
| `-h, --help` | 显示帮助 |

`--commit` 不能和 `--from`、`--to` 同时使用。

### 进度

进度输出到 stderr，所以用 `--format json` 时 stdout 上的内容仍然可以直接给程序解析：

```text
[ocra] Reviewing: Working tree changes
[ocra] 4 file(s) selected, 1 excluded · risk tier: lite
[ocra] 2 bundle(s) (grouped)
[ocra] 2 review task(s)
[ocra] correctness-1 started: auth session handling (2 file(s))
[ocra] correctness-1 reviewing with google/gemini-3.5-flash
[ocra] correctness-1 google/gemini-3.5-flash: 3 step(s), 3 tool call(s) (read_file 2, task_done 1), 19558 in / 118 out / 0 reasoning tokens, $0.0062
[ocra] correctness-1 completed in 5.9s · 0 finding(s)
```

模型超过 30 秒没有新输出时，ocra 会打印 `Model is thinking...`，让长时间的审查不会看起来像卡住了。

### 退出码

| 退出码 | 含义 |
|---|---|
| `0` | 审查完成，结论为 `approved`、`approved_with_comments` 或 `minor_issues` |
| `1` | 结论为 `significant_concerns`：至少有一个经核查确认的 critical 问题。未经确认的 critical 只会得到 `minor_issues`，退出码为 `0`。结论只是参考意见，可能受被审查改动的影响，见[工作原理](./how-it-works#结论verdict)。配合 `--pr` 时，维护者针对 head commit 的 `/ocra override` 会把它变成 `0`（见 [GitHub](./github)） |
| `2` | 参数、Git 或配置错误，或者没有任何审查任务完成。错误行会写出错误代码，例如 `ocra [VCS_REF_UNKNOWN]: Unknown commit: nope`（[代码列表](./embedding#错误)） |
| `3` | 审查不完整：有选中的文件没有被审查（任务失败、超时、触及花费上限或任务数上限，或者没有审查员覆盖它），或者有 critical 因核查失败、预算不足而没能核查。它优先于 `1`：不完整的审查不会只报告为阻塞，CI 不会因此放行 |
| `130` | 被 Ctrl-C 或 SIGTERM 中断；仍会打印部分报告，不会发布任何内容 |

### JSON 输出

`--format json` 会输出完整报告：变更信息、风险档位、结论和总结、每个改动文件的覆盖情况（已审查、失败、未审查（没有为它启动任何任务）、自上次评审后未改动，或被排除及原因）、审查 PR 时本次是增量还是全量审查及原因（`scope`）、分组、各任务结果、被 Matrix 跳过的（审查员，分组）组合、被核查丢弃的问题（`refuted`，附原因）、核查没能检查的 critical 数量（`unverifiedCriticals`）、Judge 合并、丢弃或重新定级的记录（`judgement`）、问题列表、与上次审查的对比（`rereview`：已修复、未再报告、未重新检查、未改动和已驳回的旧问题，上次审查记录了报告者时，每条带上报告它的 `reviewer`）、被 memory 接受的问题（`remembered`，每条带来源 `source`：`repository` 表示 `.ocra/memory.json`，`account` 表示你的 [ocra Cloud memory](#ocra-cloud-账户里的-memory)）、维护者的放行（`changeRequest.override`）、token 用量与花费，设置了花费上限时还有上限本身以及本次运行是否达到了它（`spendLimit`：审查任务因此停止时 `reached` 为 `review`，整个上限用完时为 `total`），以及警告信息。会话里的 `report.json` 格式相同。

这个格式带版本号（`"version": 1`），是一份约定：后续版本只会新增可选字段，否则就会改版本号。每条问题包含 `fingerprint`（多次运行间保持稳定；`ocra memory add` 接受它的前缀）、`reviewer`、`category`、`severity`、`verification`（`confirmed`、`uncertain` 或 `unchecked`）、`file`、`lines`（`{ start, end }`，问题没能对应到具体行时不存在）、`inDiff`、`status`（`new`，或者之前的审查也报过时为 `unfixed`）、`title`、`body`、可选的 `suggestion`、可选的 `fix`（`{ startLine, endLine, replacement }`：替换改动后文件中这几整行的代码，PR 或 MR 的评论会把它作为[可提交的建议](./github#可提交的建议)给出；目前还没有审查员会产生它）`evidence`、`code`（引用的代码）、`--ultra` 下的 `lowConfidence`，以及 `provenance`：报告它的那个任务在 `tasks` 里的 `task`，运行时能说出时还有 `model`。`tasks` 里的每个任务带有自己的 `usage`（token 和花费；一条问题的花费就是它所属任务的花费）。报告的 `provenance` 说明这次审查是用什么做的：`ocraVersion`；`promptHash`（这份配置会发出的系统提示词的哈希：每个启用的审查员和每个辅助阶段的，从不包含改动本身）；`configHash`（实际生效的配置，加上会改变审查的参数 `--reviewers`、`--ultra` 和 `--max-cost-usd` 的哈希；不含采样设置和密钥，key 只以变量名出现，从不保存）；以及 `sampling`：运行时实际应用的 `temperature` 和 `seed`，`notApplied` 列出要求了却没法传下去的设置；以及 `agents`：每个启用的审查员和 `verifier`、`judge`、`helper` 三个角色各自的模型层级 `tier`、`models` 中的故障切换链（[自己的](./configuration#按-agent-指定模型)，没有就是所在层级的）、设置了时的[推理强度](./configuration#推理强度) `effort`、是否已应用 `applied`（这个 agent 没有发出调用时不存在），以及 `notApplied`：它的调用没有发送的采样设置；`rules`：本次审查使用的路径规则，每条包含 `path`、`rule` 和来源 `source`（`repository` 表示 `.ocra/rules.json`，`shared` 表示共享配置，`account` 表示你的 ocra Cloud 账户，`plugin` 表示插件）；以及 `accountSettings`：登录时所用[账户设置](./configuration#账户设置)的版本 `version`。报告的 [JSON Schema](https://github.com/jma49/Open-CR-Agent/blob/main/docs/schema/report.v1.json)（draft 2020-12）由代码生成并经测试核对；`@open-cr-agent/core` 的 `reportJsonSchema()` 返回同一份 schema。`--plan` 输出的 JSON 同样带版本号（`"version": 1`）：变更信息、风险档位、选中和排除的文件、分组、各任务及其估算的提示词大小、模型链 `models`、设置了时的推理强度 `effort`、模型链已知时的 `inputCost`（`model` 为链上第一个模型；`status` 为带 `usd` 的 `priced`、`unpriced` 或 `unknown`）、被跳过的（审查员，分组）组合、是否跳过了模型分组（`groupingSkipped`）、首轮提示词的估算总大小（`promptTokens`）、有任务带估算时的输入花费估算总计（`inputCost`：已定价任务的 `usd` 之和，以及 `priced`、`unpriced`、`unknown` 的任务数）、警告信息，然后是 `settings`：每项设置的 `key`、`value`（默认值时不存在）和来源 `source`，以及读取了账户设置时的 `accountSettings`。它的 [JSON Schema](https://github.com/jma49/Open-CR-Agent/blob/main/docs/schema/plan.v1.json) 同样由代码生成并经测试核对。

### SARIF 输出

`--format sarif` 把审查结果写成 [SARIF 2.1.0](https://docs.oasis-open.org/sarif/sarif/v2.1.0/sarif-v2.1.0.html) 日志，代码扫描和安全看板读取的就是这种格式。上传到 GitHub 的方法见[代码扫描](./github#代码扫描)。

- **规则和结果。** 每个审查员类别（`correctness`、`security` 等）一条规则，每个问题一条结果：
  - 级别来自严重程度：`critical` 为 `error`，`warning` 为 `warning`，`suggestion` 为 `note`；
  - 消息是标题、正文和修改建议；
  - 区域是问题所在的行；
  - `partialFingerprints` 里是它的指纹（`ocra/v1`）；
  - 问题有 `fix` 时，它放在 `fixes` 里：用建议的代码替换那几整行；
  - 审查员、严重程度、核查结果、状态、任务，以及已知时的模型放在属性里。
- **没有行号的问题。** ocra 没能定位到行的问题作用于整个文件：它没有区域。
- **沿用的问题。** 审查 PR 时，之前的审查报告过、仍然打开、而且所在文件这次没有重新审查的问题，也会作为结果写出。它们归在规则 `ocra-carried-over` 下，标为 `unchanged`，没有行号：审查状态里没有保存它们的行。
- **不完整的审查。** 退出码为 `3` 的审查会标为执行不成功。没审到的文件数和警告写成通知。结论、风险档位、没审到的文件和花费写在这次运行的属性里。

来自改动和模型的文字只作为文字：方括号和反斜杠会被转义，因此拼不出内嵌链接；花括号按 SARIF 的要求写成两个；网址会被插入一个零宽空格，和 PR 评论里一样。`--plan` 没有问题可写，所以不能输出 SARIF。

### SARIF 输入

ocra 不运行任何分析工具。你自己运行 Semgrep、CodeQL 或其他工具，再用 `--import-sarif <文件>` 把它写出的 SARIF 2.1.0 日志交给 ocra（可以重复使用，每个文件最大 20 MB）。日志里的每个 run 在报告里都是一个独立的任务 `sarif-<工具>-<n>`：审查员是工具名，没有花费，文件是它报告过的文件；它的问题在 `provenance.task` 里指向这个任务。

- **只保留落在改动上的结果**：文件在本次审查范围内，行号落在 diff 的某个 hunk 里。整仓库扫描的其余结果会被留下并计入一条警告；没有文件和行号、路径在仓库之外、没有消息的结果也一样。每个 run 最多取 200 条。
- **严重程度**来自结果的 level，没有时来自规则的默认值：`error` 为 `critical`，`warning` 为 `warning`，`note` 和 `none` 为 `suggestion`，正好是 [SARIF 输出](#sarif-输出)的反向映射。标题是规则的简短描述、名字或 id；正文是消息、规则的说明，以及一行写明工具、版本、规则和帮助链接。
- **引用的代码决定行号。** 结果里的代码片段（没有时取文件对应的行）和审查员引用的代码走同一套定位；对不上的引用会让问题变成文件级。
- **之后它就是一条普通的问题**：memory 和驳回照样生效，核查会对照 diff 检查它，Judge 会把它和审查员的问题放在一起裁决（工具和审查员重复报告的问题在这里合并），它也计入结论。

已用 Semgrep 1.178.0 写出的日志测试过；其他工具的日志遵循同一标准。

### 会话记录

每次审查（`--plan` 除外）都会写入 `.ocra/sessions/<id>/events.jsonl`（运行过程中逐行追加事件）和 `report.json`。这个 `<id>` 就是运行 id：第一行进度输出会写出它，JSON 报告以 `runId` 携带它，摘要评论在"覆盖范围和花费"里显示它，SARIF 日志以 `automationDetails.id`（`ocra/<id>`）携带它，因此从任何一处都能找回同一次运行。这个目录自带 `.gitignore`，日志既不会被提交，也不会在下一次审查时被当成改动。

## ocra metrics

对 `.ocra/sessions/` 下已完成的审查做统计，数据来自每个会话的 `report.json`，不调用任何模型：

```bash
ocra metrics                       # 文本表格
ocra metrics --format json         # 给看板或脚本用；带 "version": 1
ocra metrics --since 2026-10-01    # 只统计在该日期及之后开始的运行
ocra metrics --sessions /srv/ocra  # 另一个会话目录，比如 CI runner 上的
```

它报告运行次数（按结论分、有多少次留下未审查的文件、有多少个会话没有可读的报告）、花费（总计和每次运行、token 数）、问题数（报告条数、按指纹去重数、按严重程度和核查状态分）、早先报告的问题后来的去向（fixed：后一次审查里代码已不在；dismissed：被审查者驳回；两者之比即接受率），以及每个审查员各自的任务数、失败任务数、花费和同样的去向统计。已修复或被驳回的问题归于上次审查随它记录的审查员；记录审查员之前的报告则归于最先报告该指纹的审查员。只统计版本 1 的报告；JSON 输出和报告一样是契约，同样按版本管理。

## ocra memory

有些问题本身没错，但已被接受：风险在别处处理了，或者团队决定接受它。把它们记下来，ocra 就不会再报告：

```bash
ocra review                                  # 每条问题都会显示一个 id，例如 #1a2b3c4d
ocra memory add 1a2b3c4d --reason "重试次数由网关限制。"
ocra memory list
```

`ocra memory add` 会在 `.ocra/sessions/` 下最新的会话里查找这个 id；用 `--session <dir>` 可以指定别的会话。条目写入 `.ocra/memory.json`，提交这个文件即可与团队共享。被记住的问题（审查员、文件和引用的代码都相同）不会出现在报告里，只会计数；审查员也会看到自己所审文件里已被接受的问题，不会再提。审查 PR 时，这个文件从 base 提交读取，因此 PR 无法借此压掉针对自己的问题。`.ocra/memory.json` 无效时审查会报错停止，和 `.ocra/rules.json` 无效时一样。

### ocra Cloud 账户里的 memory

[登录](#ocra-loginocra-logoutocra-whoami)后，也可以在 ocra Cloud 网页上的某次审查里记住一个问题（“Remember”，并填写理由）。每次审查开始前，无论是本地审查还是 `--pr`、`--mr`，ocra 都会按仓库哈希读取你的账户为这个仓库保存的条目（`GET /api/memory`），与 `.ocra/memory.json` 一起生效：任一方列出的问题都不会报告，两边都列出的计为仓库的。报告会写明每个被隐藏问题的来源 `source`（`repository` 或 `account`）；账户 memory 隐藏了问题时，终端会打印 `N finding(s) hidden by your ocra Cloud memory`；PR 的总结评论也会说明有多少问题被发起审查的账户的 memory 隐藏。未登录或设置了 `OCRA_CLOUD=off` 的审查从不读取它。`--no-upload` 不影响它：读取 memory 不会发送任何关于本次审查的内容。读取失败时会给出警告，审查只使用仓库的文件。账户 memory 按账户的盐计算的仓库哈希保存，因此只在账户开启共享问题（见下文）时生效；共享关闭而账户记住了问题时，审查会提示一次：本次只应用仓库自己的 memory。`ocra memory add` 仍然只写入 `.ocra/memory.json`。

## ocra login、ocra logout、ocra whoami

**开发中。** ocra Cloud（[ADR-0024](https://github.com/jma49/Open-CR-Agent/blob/main/docs/adr/0024-ocra-cloud.md)）的地址是 https://app.ocracloud.com；`OCRA_CLOUD_URL` 可以指定其他服务器。ocra 的其他功能都不依赖这几个命令：不登录时审查行为与以前完全相同；设置 `OCRA_CLOUD=off` 后这几个命令拒绝运行。

```bash
ocra login                                    # 显示一个验证码，并打开浏览器确认
ocra whoami                                   # 当前登录的 GitHub 账号
ocra logout                                   # 在服务器上结束会话，并删除本地保存的会话
```

`ocra login` 使用 OAuth 设备授权流程（RFC 8628）：它打印一个验证码（如 `BCDF-GHJK`），打开服务器上的确认页（加 `--no-browser` 则只打印链接；不在当前服务器上、或不是 https（本机可为 http）的页面只打印，不会打开），然后等待你在已用 GitHub 登录的浏览器里批准。只批准你自己刚刚发起的验证码。之后这个终端持有一个会话：可以用服务器上保存的 key 调用模型、上传审查结果，但不能读取这些 key，也不能修改账号；它会显示在服务器的会话页面上，可以在那里撤销。

会话保存在 `~/.config/ocra/credentials.json`（或 `$XDG_CONFIG_HOME/ocra/`，Windows 上为 `%APPDATA%\ocra\`），只有你本人可读。它和旁边保存的盐都先写入临时文件再改名替换，所以其他 ocra 进程不会读到写了一半的文件。文件里没有有效会话（被截断、清空或被改动）时按未登录处理：审查会警告一次并指出该文件，然后不连接 ocra Cloud 继续运行；`ocra logout` 会删除它。访问令牌有效期一小时，用刷新令牌续期，刷新令牌每次使用后都会更换。同时运行的多个 ocra 进程共用这个会话：同一时刻只有一个进程续期，续期时持有旁边的 `credentials.json.lock`（超过 30 秒的锁视为进程异常退出后留下的，会被打破），其他进程直接使用它保存的新令牌。令牌仍在有效期内却被服务器拒绝（401）时，会续期一次并重试一次。服务器拒绝续期即表示会话已结束：审查会警告 `your ocra Cloud session ended: run ocra login`，`ocra whoami` 以 1 退出。连不上 ocra Cloud（网络错误、5xx 或 429）时，会话仍保留到下次运行；审查只警告一次，然后在没有你账户的规则、限额（含 `maxCostUsd`）、模型和记忆的情况下继续，也不上传任何内容；指定了 `ocra-` 模型的审查则以错误停止，说明连不上 ocra Cloud，`ocra whoami` 以 2 退出。服务器没有账户设置（404）等同于没有设置，不会警告。`ocra login` 拿到令牌却读不到你的登录名时，仍会保存会话，并说明登录名未知。登录后，名为 `ocra-<provider>/<model>` 的模型会经由 ocra Cloud、使用服务器上为 `<provider>` 保存的 key 调用（走服务器列出的 OpenAI 兼容对话接口），例如：

```json
{ "runtime": "direct", "models": { "standard": "ocra-openrouter/qwen/qwen3.8-27b:free" } }
```

这类模型没有价格：报告中的费用和 `--max-cost-usd` 不计入它们，ocra 会给出警告。此时提示词及其中引用的代码会经过 ocra Cloud 再到达模型服务商；ocra Cloud 只记录每次调用的模型、状态码、token 数和耗时，从不记录请求和回答内容。没有使用 `ocra-` 模型的审查不会读取会话，也不会连接 ocra Cloud；配置中自己以 `ocra-` 名称声明的 provider 保持原有声明。如果 ocra Cloud 列出了某个 provider 接收[推理强度](./configuration#推理强度)的方式（`openai`，即 `reasoning_effort`；或 `openrouter`，即 `reasoning.effort`），ocra 就按这种方式发送；没有列出时使用 `openai`，不认识的方式会被忽略并给出警告。ocra Cloud 的回答如果不是一份 provider 列表，审查会以错误停止。这些调用带着会话的访问令牌，它的有效期是一小时。使用 `"runtime": "direct"` 时，ocra 会在令牌过期前五分钟续期，直到运行结束（续期失败时警告一次）。`opencode` 运行时只在启动时读取一次令牌，所以 ocra 会给它一个比 `runTimeoutMinutes` 再多十分钟仍有效的令牌；如果运行可能比任何令牌都长，ocra 会警告：大约一小时后，经由 ocra Cloud 的模型调用会失败。

已登录时，`ocra review` 会读取你账户中的设置：运行时、各档位以及各审查员与角色的模型和思考强度、各项限制（`concurrency`、超时、`maxCostUsd`、`maxTasks`）、`verify`、`judge`、`sampling`、`include`、`exclude` 和路径规则。它们位于配置之下：配置写了的优先，`include`、`exclude` 和规则会合并，账户永远不能设置 providers、`extends` 或 `github`（见[账户设置](./configuration#账户设置)）。账户还可以开启 `ultra`：审查会像传了 `--ultra` 一样运行，`ultra` 会和其他项一起打印出来；命令行上的 `--ultra` 始终生效，没有办法在单次运行中关闭它。补充了哪些会打印出来（`From your ocra Cloud settings: …`）。每个键都按配置文件自己的规则校验，不符合的键会被忽略，并给出点名该键的警告。`--plan` 也会读取这些设置，并在末尾列出 Settings，标明每项设置的来源：`shared`（配置文件 extends 的共享配置）、`file`（配置文件）、`env`（`OCRA_MODEL_*` 或 `OCRA_EFFORT_*` 环境变量）、`account`，会合并的列表（`include`、`exclude` 和规则）用 `+` 连接其来源（例如 `shared+account`），或 `default`，账户开启的 `ultra` 会列为 `account`；无法连接 ocra Cloud 时会给出警告，计划只显示配置本身。

每次审查结束后，已登录的 CLI 会把审查的统计数据发送给 ocra Cloud：结论、是否审完所有文件、各级别问题数、文件和任务数、token、费用和耗时、来源（本地、GitHub、GitLab）以及 ocra 版本；每个审查员的任务数和失败任务数、各级别问题数、费用，以及本次审查看到它早先的问题有多少已修复或被驳回；已确认、不确定和未检查的问题各有多少；以及早先的问题一共有多少已修复或被驳回（已修复或被驳回的问题计入上次审查随它记录的审查员；记录审查员之前的问题，只有本次审查仍有同一指纹的问题时才会计入某个审查员）。除非你的账户开启了共享问题（见下文），它从不发送路径、标题、指纹、问题描述或代码。仓库以其地址加盐后的 SHA-256 发送。地址是 `https://host/owner/repo`，与远程地址的写法无关：`git@host:owner/repo.git`、`ssh://git@host:22/owner/repo`、`https://user:token@host/owner/repo/` 都得到同一个值，用户名、凭据、端口、末尾的 `/` 和 `.git` 会被去掉，大小写统一。使用 `--pr` 或 `--mr` 时，它是从平台读取的 PR 或 MR 所在的仓库，而不是本地检出的 origin；本地审查使用 origin（本地路径形式的远程按原样使用，没有 origin 的检出按其目录）。加盐哈希让服务器可以把同一仓库的审查归在一起，却无法知道是哪个仓库。ocra 0.5.0 及更早的版本按远程地址原样计算哈希，所以远程是 SSH 形式、或带端口或末尾 `/` 的仓库会得到一次新的哈希：旧哈希下记录的审查和 memory 要重新记录后才能对上。盐是保存在凭据旁 `upload-salt` 里的随机值，所以同一仓库在另一台机器上会得到不同的哈希；但如果你的账户开启了共享问题，盐就是账户的：登录时和每次审查前从 ocra Cloud 读取，保存在凭据旁的 `account-salt`（只有你可读），这样同一仓库在你的所有机器上哈希相同，它的问题和 memory 也能对上。`--no-upload` 跳过单次上传，`OCRA_CLOUD=off` 完全关闭 ocra Cloud；上传失败只会给出警告。

当你在账户的 Settings 页面打开“Send findings and the code they quote to ocra Cloud”（默认关闭）后，上传还会带上每个问题：指纹、审查员、级别、类别、核查结果、文件、行范围、标题、描述、建议以及它引用的代码，让网页可以完整展示这次审查。发送前，ocra 会把文件路径、类别、标题、描述、建议和代码中看起来像密钥的内容替换为 `[redacted]`，并把这个问题标记为已脱敏：PEM 私钥块、AWS key id（`AKIA…`、`ASIA…`）、GitHub token（`ghp_`、`gho_`、`ghs_`、`ghu_`、`ghr_`、`github_pat_`）、GitLab token（`glpat-`）、`sk-` 开头的 key（包括 `sk-ant-`、`sk-or-`、`sk-proj-`）、Slack token（`xoxb-` 等）、Google API key（`AIza…`）、npm token（`npm_…`）、Slack 和 Discord 的 webhook URL、URL 中的密码（`postgres://user:…@`）、赋给 `password`、`secret`、`token`、`api_key` 这类名字的带引号的值、32 个字符以上的十六进制串（可能是 key，也可能是摘要），以及 32 个字符以上、含数字且看起来随机的 base64 字符串（路径不受影响）。这只能识别模式，不能识别所有密钥；服务器会再做一遍同样的处理。最多发送 200 个问题、共 256 KB 文本，每个文本字段截断到 4 KB（此时问题标记为已截断）。终端随后打印 `Sent this review's counts and N finding(s) to ocra Cloud`。只有服务器返回了账户的盐时 ocra 才发送问题，而服务器只在开关打开时返回它；如果审查前无法连接 ocra Cloud，会给出警告，本次审查使用保存在 `account-salt` 中的账户的盐计算哈希（没有保存时使用本机的盐）、不发送问题，也不应用账户的 memory。`--no-upload` 和 `OCRA_CLOUD=off` 仍然什么都不发送。

## ocra plugins

在这台机器上允许你的 ocra Cloud 设置所列出的插件（见[来自 ocra Cloud 账户的插件](./plugins#来自-ocra-cloud-账户的插件)）。这些命令不会连接 ocra Cloud；`allow` 和 `deny` 会运行 npm。

```bash
ocra plugins allow <name>@<version>   # 精确版本：先显示这个包，再安装
ocra plugins deny <name>              # 移除它：之后不再加载
ocra plugins list                     # 已允许的插件及其 integrity
```

`allow` 会运行 `npm view <name>@<version> --json`，显示包的名称、版本、发布者、维护者和 integrity，然后运行 `npm install --ignore-scripts --no-audit --no-fund --save-exact --prefix <dir> <name>@<version>`，安装到 `~/.config/ocra/plugins/`（`$XDG_CONFIG_HOME/ocra/plugins/`，Windows 上为 `%APPDATA%\ocra\plugins\`）。只有当 npm 安装的正是这个版本、且 integrity 与 registry 所列一致时，才会把插件记录到该目录的 `plugins.json`。npm 以参数列表的方式作为子进程运行，从不经过 shell，并使用你自己的 npm 配置中的 registry 和凭据。不是 npm 包名的名称、或者是范围或标签的版本，会在运行 npm 之前被拒绝（退出码 2）。
