审查员会结合四层指引。

## 内置规则

正确性审查员会拿到通用正确性规则（逻辑错误、调用双方不一致的契约、被掩盖的失败、资源与并发问题、数据完整性，以及改动中可见的安全缺陷），并根据分组里的文件加入对应的语言规则；安全和性能审查员则使用各自的规则集：

| 语言 | 扩展名 |
|---|---|
| TypeScript / JavaScript | `.ts` `.tsx` `.mts` `.cts` `.js` `.jsx` `.mjs` `.cjs` |
| Python | `.py` `.pyi` |
| Go | `.go` |
| Java | `.java` |

每个审查员的提示词里还列出了**不该报**的内容：代码风格和格式、拿不出可触发输入的推测、缺少测试或文档、重构建议，以及本次改动没有涉及的代码里的问题。

## AGENTS.md

仓库根目录的 `AGENTS.md` 会作为仓库规范交给审查员，超过 20,000 个字符的部分被截断。它读取被审查的版本（审查 PR 时读 base 提交，PR 无法改写它）。适合写要执行的约定：架构边界、错误处理规范、禁用的 API。

## .ocra/rules.json

按路径生效的规则，只有分组里包含匹配的文件时才会生效：

```json
{
  "rules": [
    {
      "id": "idempotency-key",
      "path": "services/billing/**",
      "rule": "Every write must carry an idempotency key. Flag handlers that retry without one."
    },
    {
      "path": ["**/*.sql", "db/migrations/**"],
      "rule": "Migrations must be backward compatible with the previous release."
    }
  ]
}
```

- `path`：一个 glob，或一组 glob。
- `rule`：交给审查员的规则文本。
- `id`（可选）：小写字母、数字和 `-`，最多 64 个字符。依据这条规则的问题会在报告的 `rule` 里写出它，ocra Cloud 据此按规则统计问题。不写时规则以 `rule-` 加其文本的 8 个十六进制字符命名，文本改了它也会变。

`rules.json` 不合法时审查会报错停止。审查 PR 时从 base 提交读取。

## .ocra/rules.md

同样的规则，用自然语言写，团队不必写 JSON 也能读写。标题里写了路径的小节只对该路径下的文件生效（和 `guidelineScope: "matched"` 时的 `AGENTS.md` 小节一样），其余小节对所有文件生效：

```markdown
# Review rules

Every finding names the input that breaks the code. Do not flag missing log lines.

## services/billing/

Every write must carry an idempotency key. Flag handlers that retry without one.

## db/migrations/

Migrations must be backward compatible with the previous release.
```

- 标题里包含带斜杠的路径（`## services/billing/`、``### `web/src` ``）就算写了路径；子小节沿用上一级标题的路径。
- 每个有正文的小节是一条规则（含标题），交给文件匹配的审查任务，排在 `rules.json` 的规则之后。报告里它的 `source` 是 `repository`，`id` 是标题转成小写、词之间用 `-` 连接（`services-billing`）；标题里没有拉丁字母或数字时，按文本得到 `rule-` 开头的 id。
- glob（`**/*.sql`）仍写在 `rules.json` 里；一个仓库可以两个文件都有。

文件超过 20,000 个字符时审查会报错停止。审查 PR 时和 `rules.json` 一样从 base 提交读取。

## .ocra/learnings

learning 是团队从以往改动中学到的东西：一次修复补上的 bug、评审者拒绝某种写法的原因。每条是 `.ocra/learnings/` 下的一个 Markdown 文件，文件名就是它的 id（小写字母、数字和连字符），开头是 YAML frontmatter：

```markdown
---
title: Release pooled connections on every exit path
paths: ["src/db/**"]
symbols: [acquire]
keywords: [connection pool]
critical: true
source: { kind: fix-commit, ref: 3f2a9c1 }
created: 2026-11-21
---

`acquire()` hands out a connection that only `release()` returns. An early
`return` or a `throw` between them leaks it, and the pool runs dry under load.
```

- `title`、`paths`（glob，至少一个）和 `created`（日期）必填；正文写要检查什么、为什么，最多 4,000 个字符。路径按 `.gitignore` 的方式理解：`*.sql`、`Dockerfile` 匹配任意深度，`services/billing/` 匹配其下所有文件，开头的 `/` 表示从仓库根目录算起，不区分大小写。
- `symbols`：补丁里用到这些标识符时，不论路径都适用；按完整标识符匹配。由两个及以上单词组成的名字不论命名风格都能匹配（`createCharge` 能匹配 `create_charge` 和 `CREATE_CHARGE`），`pool.connect` 也能匹配 `pool?.connect`、`pool->connect` 和 `pool::connect`。
- `keywords`：在补丁里匹配的词或短语，不管写法（`connection pool` 能匹配 `ConnectionPool`、`connection_pool` 和 `connection pools`）。中文或日文关键词在文本中任意位置出现即匹配，不要求前后有空格。
- `critical`：路径匹配时一定交给审查员。
- `source`：来源（`kind`：`fix-commit`、`review-feedback`、`document`、`remember`、`incident` 或 `manual`；`ref`：提交、PR 或链接）。

每个审查任务拿到适用于它那些文件的 learning，在任何模型调用之前选好：路径匹配的 critical 条目排第一，其次是路径匹配且补丁中出现其符号或关键词的，再次是路径匹配且改动所在的函数或类中出现其符号或关键词的，接着是只有符号匹配的，然后是只有路径匹配的，最后是只有关键词匹配的。只有适用的条目多于能给出的数量时，ocra 才会读取被改动的函数。最多给 5 条，正文合计不超过 8,000 个字符；路径匹配的 critical 条目另外全部给出（最多 10 条）。适用但放不下的条目只列 id 和标题，最多 10 条，其余给出条数；审查员可以用 `read_learning` 读取其中一条，内容同样来自可信版本。审查员把它们当作数据读，只报告这次改动本身的问题。报告的 `learnings` 列出给过的每一条，以及它去了哪些分组；依据其中一条（给出的或列出的）的问题会在 `rule` 里写出它的 id。

learning 读取被审查的版本，审查 PR 时和 `rules.json` 一样从 base 提交读取，所以 PR 无法加一条来影响对它自己的审查。不合法的文件会被跳过并给出警告；最多读 500 个文件，每个不超过 16 KB。

`ocra learn mine` 从你的修复提交起草 learning，`ocra learn feedback` 从你带理由接受或拒绝的问题起草，`ocra learn import` 从你的事故复盘和规范起草，`ocra learn remember` 从 PR 上的 `@ocra remember` 备注起草（[CLI](./cli#ocra-learn)）。
