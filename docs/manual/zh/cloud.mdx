ocra Cloud 是建立在同一个引擎之上的网页控制台和模型网关。它在 https://app.ocracloud.com ，早期体验期间免费，模型 key 由你自带。公司也可以自己运行服务器（[自托管](https://github.com/ocrahq/ocra-cloud/blob/main/docs/self-hosting.md)）。CLI 只有在你[登录](./cli#ocra-loginocra-logoutocra-whoami)后才会使用它；它会收到什么，见[威胁模型](./threat-model#ocra-cloud)。

有些页面需要 bot：服务器自己的一个账号，以 ocra 的身份在平台上审查和写入。下面把这些页面标为*需要 bot*。

- **托管的控制台**在 GitHub 上有 bot：名为 Ocra Cloud 的 GitHub App，在你安装了它的仓库里以 `ocra-cloud[bot]` 的身份发布。在 GitLab 上还没有。
- **你自己的服务器**可以在 GitHub、GitLab 或两边都配上 bot（见[自己运行服务器](#自己运行服务器)）。只有这样的服务器才能做的事标为*自托管*。

## Pull Request

收件箱显示你的 GitHub Pull Request 和 GitLab Merge Request。尚未保存视图时，默认显示 **Needs my review**（等我审查）、**My open PRs**（我尚未关闭的 PR）、**Waiting on others**（等他人审查）、**Assigned to me**（分配给我的 PR）和 **Recently merged**（近期合并）；你也可以自定义并保存视图。上次打开之后有新动态的 PR 会标为未读，同一个[栈](./cli#ocra-stack)里的 PR 排在一起。命令菜单（Ctrl 或 ⌘ K）可以去任何页面，并搜索 PR、审查、发现和仓库。PR 页面以你的身份实时读取 diff，并以你的身份把评论、审查和合并发送到平台；读到的内容都不保存。

- **审查。** ocra 对它最新一次审查的结论和发现；账户共享发现时，还有[改动导读](./how-it-works#改动导读)，按阅读顺序列出文件，并附上时序图。
- **修复。** 带有修复的发现（CLI 0.10.0 及以后，且开启了 [`fixes`](./configuration)，账户设置也可以开启它）可以以你的身份提交到 PR 的分支上，前提是分支仍停在被审查的提交上，且文件没有改过；之后这个发现会被标记为已修复。
- **上次看过之后。** diff 可以只显示你上次看过或审查过的 head 之后的改动。
- **审查讨论。** PR 的审查讨论：其中的建议可以合成一个提交一起应用，每条讨论可以解决或重新打开，都以你的身份进行。
- **描述。** “撰写 PR 描述”根据 ocra 的审查起草描述，你编辑后保存到平台。只会重写 ocra 负责的那一段，其余仍是你写的内容。
- **审查人。** 推荐的审查人：改动文件的 code owner、审查过相同目录的人，以及仓库最近的审查人，并附上他们手上已有的审查请求。
- **从发现创建 issue。** 一条发现可以先生成草稿、经你编辑后，作为 issue 开在被审查的仓库里。
- **可以合并了吗。** 一张实时读取的清单，列出 PR 合并前还差什么：草稿、冲突、批准、code owner、必需的检查、未解决的讨论，以及 ocra 的合并前检查。
- **合并。** 合并、squash 或 rebase，或者放进平台自己的合并队列（GitHub 的 merge queue、GitLab 的 merge train），也可以再拿出来；页面会显示它在队列中的位置。合并会带上你读到的那个提交：之后又有新提交的会被拒绝。“就绪后合并”以你的身份开启平台自己的自动合并；平台没有开启它时，自托管服务器会记下这个请求，等上面的清单都满足后再合并。
- **立即审查与生成。** *需要 bot。* 对登记了[自动审查](#自动审查与-ocra)的仓库，可以请求审查当前 head，或者请 bot 把测试或文档注释（[`ocra generate`](./cli#ocra-generate)）提交到分支上。
- **栈。** 用 [`ocra stack`](./cli#ocra-stack) 建立的栈里的 PR，会显示整个栈，并从底部开始合并到你选的那一个。合并由服务器作为一个任务来执行，所以你可以关掉页面：它以你的身份合并最底下的一层，把上一层改到主干上，在仓库要求时更新它的分支，等它的检查通过后合并，依次往上。检查失败、有冲突、被拒绝、某一层有了新提交或被关闭时，它会停下并说明原因，三天后也会停下；栈里任何一层的页面都能看到进度，也可以取消。
- **影响范围。** 服务器保存了这个仓库的[代码图](#代码图)时，发现旁边会有一栏，列出改动的符号以及其他代码在哪里使用它们（按名字匹配）。
- **合并前检查。** 仓库设置的[检查](#合并前检查)，以及每项在当前 head 上的结果。

## 审查

已登录的 CLI 上传的每次审查；账户共享发现时，还有它的发现、改动导读和它拿到的[关联任务](./how-it-works#关联的任务)。服务器自己运行的审查，不论你是否共享发现，都会连同发现一起列出（见[自动审查](#自动审查与-ocra)）。同一个 PR 后来的审查看到已修复的发现，会被标记为已修复（CLI 0.14.0 及以后）。

- **问 ocra。** 审查页面可以回答关于这次审查和它的 PR 的问题（“这条发现为什么是严重的？”），使用你自己的模型 key。改动对模型来说只是数据，不是指令。
- **追踪。** CLI 0.25.0 及以后连同发现一起上传的审查带着它的追踪（CLI 的 `trace.json`，见[会话记录](./cli#会话记录)）：审查页面把这次运行画成阶段、任务、尝试和模型调用的时间线，说明每条报告过的发现去了哪里、为什么，并可以把追踪下载为 JSON，作为证据交给 reviewer。标题、原因和路径与发现经过同样的脱敏；不发送代码、提示词、模型回答或搜索的文字。
- **规则。** CLI 0.26.0 及以后连同发现一起上传的审查带着这些发现引用的每条[规则](./rules)的原文，与发现经过同样的脱敏，最多 2,000 个字符；学习只发送 id。账户规则可以像 `rules.json` 的规则一样写 `id`，发现用它引用规则。
- **实时。** CLI 0.11.0 及以后运行的审查会在运行中转发进度；实时页面显示这次运行，你可以让指定的人、或这台服务器上任何已登录的人观看并评论发现。你同意之前什么都不会共享。

## Learnings

Learnings 页面按审查读取的方式，列出仓库默认分支上的 [learnings](./configuration#learnings)（`.ocra/learnings/*.md`），审查会跳过的文件附上原因，同时列出来自 `ocra/learnings-*` 分支的未合并提案。新增、编辑或删除一条，会以你的身份开一个 PR，或在平台允许时直接提交到默认分支；你打开之后又被改过的文件会被拒绝，而不是被覆盖。

## 合并前检查

每个仓库最多可以设置 20 项检查，每项可以关闭、警告或阻塞：关联的 issue（处于打开状态，或带某个标签）、标题前缀或模式、填写了描述并包含指定的小标题、大小上限、head 上没有未解决的 ocra 严重发现，以及用自然语言写的检查。自然语言检查由服务器自己对这个 PR 的审查来评判（*需要 bot*），就像你自己运行的审查评判 [`mergeChecks`](./how-it-works#合并前检查) 一样；改过的检查要等下一次审查。关联 issue 检查要等 CLI 0.11.0 或更高版本的审查，它会上传关联的 issue。无法判断的检查会如实说明，而不是直接通过。

PR 页面会显示结果。bot 还会把它发布出来：GitHub 上是名为 `ocra / pre-merge` 的 check run，GitLab 上是同名的提交状态；阻塞检查不通过时它也不通过。

## 自动化

*需要 bot。* 最多 50 条规则，每条是一组条件，以及条件全部满足时执行的动作。规则在 PR 进入审查队列时运行（匹配仓库、作者、目标分支、标题或标签），或在审查上传时运行（匹配严重发现或结论）。动作可以加标签、请求审查人、以 bot 身份发评论、通知某个渠道，或者跳过审查。试运行可以告诉你哪些规则会匹配你描述的 PR，每次运行的记录保留 30 天。

## 自动审查与 @ocra

*需要 bot。* 你在自动审查页面登记仓库，服务器就用你账户的模型、key、预算和规则审查它的 PR。PR 里的任何东西都不会运行。

- **自动。** 每个已登记的仓库有一个 Automatic（自动）开关。打开时，PR 在打开、转出草稿或有新提交时被审查。关闭时，只运行你在 PR 页面上请求的审查。
- **档位。** Balanced（均衡，默认）按你的设置审查。Quiet（安静）只发布改动行上的正确性和安全发现。Thorough（彻底）让每个审查者各跑两遍，花费大约翻倍。
- **每日上限。** 审查的模型调用都经过网关，托管的控制台限制每个账户每个 UTC 日 500 次调用；你自己的服务器自行设定上限。调用用完后，排队的审查等到 UTC 零点，被上限打断的审查届时重新运行，自动审查页面会显示“Daily limit reached”。
- **发现会保留。** 从服务器为你运行的第一次审查起，它会保留这些审查的发现和每条发现引用的代码（和其他上传一样先脱敏），这样 PR 页面、审查页面和通知才能显示它们。这不会为你自己机器上的审查开启共享。可以在“账户与隐私”里关闭，并删除已保留的内容；之后的审查不会把它重新打开。
- **@ocra。** 有人在已登记仓库的 PR 上发表提到 `@ocra` 的评论，会在原讨论里得到回答（[`ocra reply`](./cli#ocra-reply)）。

在托管的控制台上，审查在远程 runner 上运行：这些机器向服务器领取下一个任务，克隆仓库，运行已发布的 CLI。runner 不持有模型 key，每个任务只拿到一个仓库的令牌。你自己的服务器可以自己运行审查，交给 [runner](https://github.com/ocrahq/ocra-cloud/blob/main/docs/runner.md)，或两者都用。没有服务器时，[Action](./github#向-ocra-提问) 可以在你自己的 workflow 里做同样的事。

## 审查设置

仓库的 [`.ocra/config.json`](./configuration) 没有写到的地方由这些设置补上：各层级的模型、规则、插件、花费上限、修复（`fixes`）和关联任务（`linkedTasks`，v0.12.0）。审查配置页面直接编辑仓库的 `.ocra/config.json`，先按它的 schema 检查，再以你的身份开 PR 或直接提交。账户与隐私页面包括是否共享发现、是否保留服务器所运行审查的发现、已登录的浏览器和终端，以及账户关键变更的审计日志（保留 90 天）。

## 通知

渠道可以是 Slack 或企业微信群、你自己的 webhook，或者邮件地址（需要配有邮件账号的服务器，*自托管*）；一个账户最多 10 个。

- **审查。** 每次审查、有发现的审查，或只有严重发现时。只有发现被保留时，消息里才会出现发现的标题。
- **你的 PR。** *需要 bot。* 在已登记的仓库上，渠道还可以在这些时候通知你：有人请你审查；有人审查、评论、合并或关闭了你写的 PR；它的合并前检查失败；有人提到你；有人在你发起的讨论里回复。
- **向团队请求的审查。** 向你所在的 GitHub 团队请求的审查，每个 PR 通知你一次，并以团队的名字显示在收件箱里；任何一位成员审查后即结束。App 需要组织权限 Members: Read。GitLab 的审查人只能是用户。
- **提醒。** 渠道可以在 4、8、24 或 48 小时后提醒你还欠着的审查，或你自己还没人审查的 PR。免打扰时段按你的时区计算，其间的提醒和评论通知会攒起来，之后合成一条消息发送。
- **摘要与周报。** 前一天的每日摘要，以及在你选定的星期和时间发送的周报：审查、按严重程度统计的发现、后续运行看到已修复或已驳回的发现、已合并的 PR 及合并时间的中位数，以及审查最多的仓库。没有内容的一天或一周不会发送。
- **投递记录。** 每条消息都是一次投递。因为可能恢复的原因而失败的（没有应答、限流、服务器错误）会隔越来越长的时间重试；被接收方明确拒绝的会立即放弃。点击渠道的最后一条消息可以打开它的投递记录：每条消息是什么、是否送达，以及等待中的消息下次何时重试。投递记录保留 30 天。

## 洞察

按天统计的用量、花费和审查次数，以及周期时间：你在过去 90 天内合并的 PR，或某个仓库所有作者的 PR，从打开到别人第一次审查或评论、再到合并各用了多久。数据从平台实时读取，不保存。

## 代码图

服务器为每个添加的仓库保存默认分支的代码图，每次 push 后只解析改动的文件来更新：符号名、类型和行号，从不保存代码。ocra Cloud 运行的审查会读取它来追踪改动影响到的调用方，仓库的第一次这样的审查会自动添加它。PR 页面的影响范围栏和 [`ocra graph --cloud`](./cli#ocra-graph) 都从它读取。在 app.ocracloud.com 上由审查 runner 构建代码图，影响范围栏在 ocra 审查过这个 PR 之后显示；每个账号最多保存 5 个仓库，每个仓库只保留最新的代码图。

## 自己运行服务器

公司可以在自己的机器上运行 ocra Cloud，比如放在内部 GitLab 和内部模型旁边；[自托管指南](https://github.com/ocrahq/ocra-cloud/blob/main/docs/self-hosting.md)列出了所有变量。它是 Docker 里的一个 Node 服务器，不依赖任何 Cloudflare 服务。

- **数据库。** 默认 Postgres（13 及以上；compose 文件会在服务器旁边运行 Postgres 17）；试用时可以用一个 SQLite 文件。
- **登录。** GitHub App，或 OpenID Connect：公司的 SSO（Keycloak、Azure AD、Okta）或自托管的 GitLab。用 GitLab 作为登录提供方时，同一次登录也会连接 GitLab。
- **谁可以登录。** 默认是登录提供方认可的任何人；设置 `SIGN_IN_ALLOW` 后只有名单里的人：`org:`（GitHub 组织的成员）、`user:`（GitHub 登录名）、`domain:`（该域名下已验证的邮箱）和 `group:`（SSO 给出的组），例如 `org:acme,domain:acme.com`。不匹配任何一项的登录会在创建账户之前被拒绝。会话和 API token 每小时内会重新检查一次，名单变化时立即检查，所以离开组织后访问随之结束。
- **代码平台。** GitLab.com 或自托管的 GitLab（`GITLAB_URL`，也支持装在相对路径下的实例，比如 `https://example.com/gitlab`）；github.com 或一台 GitHub Enterprise Server（`GITHUB_URL`），之后 API、登录、bot 和链接都指向那台服务器。一台服务器只对应一个 GitHub。
- **公司模型。** `MODEL_ENDPOINTS` 声明公司的端点，可以是 OpenAI 的 chat completions 协议或 Anthropic 的 Messages 协议，并可写上每个模型的价格，用于报告的花费；`BUILTIN_PROVIDERS=off` 隐藏公共供应商，`DEFAULT_MODELS` 给每个新账户设好模型；一个模型就够了，没写的层级会取最接近的已写层级。服务器的环境里写了公司的证书颁发机构（`NODE_EXTRA_CA_CERTS`）和代理（`HTTPS_PROXY`、`NO_PROXY`）时，服务器和它运行的评审都会使用。拒绝函数调用的模型服务也能评审（[不支持函数调用的端点](./providers#不支持函数调用的端点)）。
- **审查。** 服务器在自己的进程里运行审查，或者交给其他机器上的远程 runner（`RUNNER_TOKEN`）。
- **邮件。** 设置 `SMTP_URL` 和 `SMTP_FROM` 后可以发邮件通知。

上面标为*自托管*的内容都需要这样一台服务器。
