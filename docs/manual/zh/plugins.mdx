ocra 里的一切都是插件：本地 Git 和 GitHub 适配器、OpenCode 运行时、correctness、security、performance、docs 和 agents-md 五个审查员，以及会话记录，都是内置插件。你写的插件使用的是同一套接口。

## 编写插件

插件是一个模块，以 `default`（或 `plugin`）导出一个对象：

```js
// tools/ocra-team-rules.mjs
export default {
  name: "team-rules",
  configure(ctx) {
    ctx.registerRules([
      {
        path: "services/**",
        rule: `Owned by ${ctx.settings.team}: check idempotency keys on every write.`,
      },
    ]);
  },
};
```

在 `.ocra/config.json` 里注册：

```json
{
  "plugins": ["./tools/ocra-team-rules.mjs"],
  "pluginSettings": { "team-rules": { "team": "payments" } }
}
```

插件从仓库自己的依赖（按包名）或文件路径加载，路径相对仓库根目录解析（也可以指向仓库之外：配置由你自己信任）。插件会执行代码，所以只在本地审查时从仓库自己的配置加载；审查 PR 时或使用 `--no-repo-config` 时都不会加载。

## 来自 ocra Cloud 账户的插件

[登录](./cli#ocra-loginocra-logoutocra-whoami)后，你的 ocra Cloud 设置可以按 npm 包名列出插件，并为它们提供 `pluginSettings`。插件会在你的机器上执行代码，所以账户只能列出它的名字：只有你在某台机器上用 [`ocra plugins allow`](./cli#ocra-plugins) 允许之后，它才会在这台机器上加载。

```bash
ocra plugins allow ocra-plugin-team-rules@1.4.0   # 显示这个包及其发布者，然后安装
ocra plugins list
ocra plugins deny ocra-plugin-team-rules
```

`allow` 要求精确版本，不接受范围或标签。它会显示 registry 中该包的名称、版本、发布者、维护者和 integrity，然后在关闭安装脚本的情况下把这个精确版本安装到 `~/.config/ocra/plugins/`（`$XDG_CONFIG_HOME/ocra/plugins/`，Windows 上为 `%APPDATA%\ocra\plugins\`），并把名称、版本和 integrity 记录在该目录的 `plugins.json` 中（只有你可读）。npm 在该目录中运行，所以你运行 ocra 所在项目的 npm 配置不会生效；registry 中没有列出 integrity 的包会被拒绝。记录的 integrity 只覆盖这个包本身的 tarball，不覆盖它的依赖：依赖由 npm 在安装时按当时的解析结果安装。允许一个插件是你自己的供应链决定，就像添加一个依赖。

审查只在以下条件下加载账户列出的插件：

- 这台机器允许了它：只从上述目录加载，从不从被审查代码的 `node_modules` 加载，并且已安装的包仍然是允许时记录的版本和 integrity；
- 仓库的插件也能加载的场合：本地审查；`--pr`、`--mr` 和 `--no-repo-config` 时从不加载。

账户列出、但这台机器没有允许的插件会被跳过，并给出一条警告，列出它的名字和 `ocra plugins allow <name>@<version>`。仓库配置已经列出的包按仓库的插件加载；插件名已被占用的会被跳过。来自账户的插件加载失败时会被跳过并给出警告，不会让审查失败。

账户的 `pluginSettings` 只作用于账户自己列出、并且这台机器加载了的插件，按账户列出的 npm 包名对应（例如 `@acme/ocra-team-rules`，而不是它导出的插件名 `team-rules`），与 ocra Cloud 的存储方式一致；插件随后按自己的插件名收到这些设置，和来自配置的设置一样；配置自己的 `pluginSettings` 优先，仓库插件的设置只来自仓库。

## 生命周期

| 阶段 | 执行方式 | 失败时 |
|---|---|---|
| `bootstrap(ctx)` | 所有插件并发执行 | 只打印警告，审查继续 |
| `configure(ctx)` | 按加载顺序执行 | 审查停止，并指出是哪个插件 |
| `postConfigure(ctx)` | 所有注册完成后并发执行 | 审查停止 |

`bootstrap` 适合做失败了也无妨的事，比如拉取远程设置。

## 插件可以注册什么

| 方法 | 提供的能力 |
|---|---|
| `registerVcs(name, factory)` | 代码托管平台适配器 |
| `registerRuntime(name, factory)` | agent 运行时 |
| `registerReviewer(definition)` | 有自己提示词和模型层级的审查员 |
| `registerRules(rules)` | 按路径生效的审查规则 |
| `registerTool(tool)` | 审查员可以调用的工具，输入用 Zod schema 定义 |
| `onEvent(listener)` | 审查过程中每个事件的监听器（遥测、通知）。监听器抛出异常时会被停用，并给出一次警告，审查继续进行 |

运行时工厂会收到模型链、环境变量、声明的供应商，配置了的话还有 `sampling`（`temperature`、`seed`）；运行时用自己的 `sampling` 属性说明它实际发送什么，并在 `notApplied` 里列出没法传下去的设置。没有这个属性的运行时会被报告为一项都没应用。任务的 spec 带有它的审查员要求的[推理强度](./configuration#推理强度) `effort`；补全请求带有 `agent`（计划调用对应的审查员，或 `verifier`、`judge`、`helper`）和 `effort`；没有配置推理强度时两者都不存在。会发送推理强度的运行时实现 `appliedTo(agent)`，返回这个 agent 的每次调用是否都发送了它；`unsupported`：因为模型不接受该级别而没有发送的模型（运行会按 agent 给出一次警告）；以及 `notApplied`：这些调用没有发送的采样设置。`@open-cr-agent/core` 的 `effortCapability(model)` 提供 ocra 关于模型能接受什么的表：参数形式和级别。没有实现它的运行时会被报告为不发送推理强度，运行会给出一次警告。有[自己的模型链](./configuration#按-agent-指定模型)的 agent 会在任务 spec 和补全请求的 `models` 中带上它，工厂也会在 `agentModels` 中按 agent id 收到所有这样的模型链，供需要在第一次调用前准备供应商的运行时使用；忽略这两者的运行时会用层级的模型链执行这些调用。

运行时不必自己在模型之间做故障切换：`@open-cr-agent/core` 的 `ChainRunner` 可以替它实现 `runTask` 和 `complete`。它决定一次调用用哪条模型链（agent 自己的，否则是层级的），对没有配置模型的层级给出 `CONFIG_INVALID` 错误，在整次运行中记录每个模型的健康状况（短时限流会等待，配额用尽的模型在本次运行中不再使用，持续失败的模型由熔断器跳过），并在一次尝试失败时换下一个模型。运行时提供 `ModelAttempts`：`task` 和 `complete` 在一个模型上执行一次尝试，返回 `AttemptOutcome`（发现、步数、工具调用、文本和用量，以及一个 `error`，说明换个模型是否可能成功，带 `QuotaError` 时说明是否需要等待、等多久）；`task` 可以返回 `TaskAttempt`：带有 `wrapUp()` 的 `AttemptOutcome`，它把这次尝试的对话再继续一轮（`WRAP_UP_MESSAGE`，只提供 `WRAP_UP_TOOLS`，最多 `WRAP_UP_STEPS` 次请求，使用这次尝试的 signal 和 `onUsage`），返回这次尝试到目前为止的结果；尝试没有出错、也没有调用 `task_done` 时，除非任务的 signal 已中止，runner 会调用它。可选的 `refuse` 在发出任何请求之前说明一条模型链为什么无法使用，可选的 `ready` 启动这些尝试需要的东西。每个运行时实例创建一个 runner，这样它记录的健康状况覆盖整次运行。两个内置运行时都是这样实现的。

运行时需要的其余部分也在 `@open-cr-agent/core` 中，你自己的运行时可以按内置运行时的方式执行审查：`reviewTools`，和 `RuntimeOptions.tools` 一起提供给 agent 的只读审查工具，以及 `REVIEW_TOOLS`，它们的名字（一次尝试的发现就是 agent 传给 `report_finding` 的内容；`task_done` 结束尝试）；`MAX_AGENT_STEPS`，每次审查尝试的模型请求上限；`RESUME_MESSAGE`，agent 在还有步数、没有回答也没有调用 `task_done` 时停下，会收到一次这条消息；`parseModel(model)`，拆分 `provider/model`，其他写法抛出 `CONFIG_INVALID`；`parseQuotaError(message, status?)`，把供应商的限流或配额错误读成 `QuotaError`；`withoutSecrets(text, secrets)`，在引用供应商的错误之前去掉其中的密钥；`emptyUsage()` 和 `addUsage()`；`EFFORT_LEVELS` 和 `thinkingBudget(capability, level, outputLimit?)`，ocra 为某个级别推算的思考预算；以及 `proxiedFetch(env)`，按给定环境中的 `HTTP_PROXY`、`HTTPS_PROXY` 和 `NO_PROXY` 走代理的 `fetch`。

每个插件只能拿到自己的设置（`ctx.settings`），并由可选的 `settingsSchema` 校验。同一个名字重复注册、使用保留的工具名，或在 `configure` 阶段之后再注册，都会报错并指出是哪个插件。

## 安全

插件会执行代码，只从你信任的仓库加载插件，并且只在确认发布者之后才允许账户列出的插件；审查别人的分支时，请使用 `ocra review --no-repo-config`，它会忽略仓库的配置和插件。在 CI 中，配置应当从受保护的 base 分支读取，绝不能从被审查的 PR 里读取。
