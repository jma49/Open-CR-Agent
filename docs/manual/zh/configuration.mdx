ocra 从被审查仓库根目录的 `.ocra/config.json` 读取配置。所有字段都可选；未知字段直接报错，拼写错误不会被悄悄忽略。

`ocra review --config <文件>` 改为读取你自己的文件，放在哪里都行。它是你信任的，所以和 `--no-repo-config` 一起用也生效：审查不信任的代码（比如评测工具）时，声明的[模型端点](./providers#你自己的端点)和上限就是这样传进去的。它列出的插件从文件所在目录解析。与 `--pr`、`--mr` 一起用时，它代替 base 分支的文件；插件在那里照样不加载。

```json
{
  "$schema": "https://raw.githubusercontent.com/ocrahq/Open-CR-Agent/main/docs/schema/config.v1.json",
  "models": {
    "top": "google/gemini-3.1-pro-preview",
    "standard": ["google/gemini-3.5-flash", "google/gemini-flash-lite-latest"],
    "light": "google/gemini-flash-lite-latest"
  },
  "concurrency": 8,
  "taskTimeoutMinutes": 10,
  "runTimeoutMinutes": 25,
  "verify": true,
  "judge": true,
  "maxCostUsd": 1,
  "include": [],
  "exclude": ["legacy/**"],
  "runtime": "opencode",
  "plugins": [],
  "reviewers": {},
  "pluginSettings": {}
}
```

`$schema` 让编辑器用这个文件的 [JSON Schema](https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/schema/config.v1.json)（draft 2020-12，由代码生成并经测试核对）做补全和校验；ocra 忽略它。

## 模型

模型写成 `provider/model`，provider 使用 OpenCode 的供应商 ID（例如 `google`、`anthropic`、`openai`）。每个层级可以写一个模型，也可以写一条降级链：

| 层级 | 用途 |
|---|---|
| `standard` | 审查员 agent |
| `light` | 辅助调用，比如给改动文件分组 |
| `top` | Judge（最终裁决） |

模型过载或拒绝请求时，任务换到链上的下一个模型重试。限流给出的等待不超过 90 秒时，所有任务暂停使用这个模型，等完再重试；没给出等待的限流依次暂停 15、30、60 秒。使用 `direct` 运行时时，任务保留已经做完的部分：暂停结束后只重发被拒的那次请求，之前的步骤不会再问一遍、再付一次钱（v0.16.0 新增）；使用 `opencode` 时，因限流结束的任务在暂停后从头开始；OpenCode 自己的重试若要等超过 90 秒（比如按天限流要等到午夜），会话会在几秒内被停下，按这次限流处理。暂停期间到达的限流（比如同时运行的任务一起被拒）算作同一次暂停。按天限流、等待更长，或连续暂停三次后再次限流，这个模型在本次运行里就不再使用。每个模型都有熔断器：连续失败两次后跳过一分钟，再放行一个请求试探；成功就恢复，失败则暂停时长加倍（最多十分钟）。凭证错误立即停止，因为该供应商的其他模型也会失败。

环境变量会覆盖配置文件，降级链用逗号分隔：

```bash
export OCRA_MODEL_STANDARD="google/gemini-3.5-flash,google/gemini-flash-lite-latest"
export OCRA_MODEL_LIGHT="google/gemini-flash-lite-latest"
export OCRA_MODEL_TOP="google/gemini-3.1-pro-preview"
```

## 按 agent 指定模型

`reviewers.<id>.models` 为单个审查员指定自己的模型或降级链（审查任务和计划调用），`roles.<role>.models` 为 `verifier`、`judge`、`helper`（给文件分组、重新定位引用的代码）、`writer`（[改动导读](./how-it-works#改动导读)）或 `fixer`（[修复](./how-it-works)）指定；`judge` 的链也用于判断[合并前检查](./how-it-works#合并前检查)。写法与层级相同。没有设置的 agent 用所在层级的链；verifier 和 judge 从不沿用审查员的链，核查因此保持独立。

```json
{
  "models": { "standard": "google/gemini-3.5-flash", "top": "google/gemini-3.1-pro-preview" },
  "reviewers": { "security": { "models": ["anthropic/claude-sonnet-5-5", "google/gemini-3.5-flash"] } },
  "roles": { "helper": { "models": "google/gemini-flash-lite-latest" } }
}
```

降级、限流暂停和熔断器都按模型计算，同一个模型出现在两条链里时共用一个熔断器。审查前的检查也覆盖这些链：供应商的 key 必须已设置，[自行声明的供应商](./providers#你自己的端点)的模型必须有价格，`ocra-<provider>/` 模型经由 ocra Cloud。忽略 agent 模型链的插件运行时使用层级的链。JSON 报告的 `provenance.agents` 记录每条实际使用的链，`--plan` 显示每个任务的链，配置哈希也覆盖它们。

## 推理强度

即模型回答前推理多少：`effort` 按层级设置，`reviewers.<id>.effort` 按审查员设置（审查任务和计划调用），`roles.<role>.effort` 设置 `verifier`、`judge`、`helper` 或 `writer` 调用。级别：`none`、`minimal`、`low`、`medium`、`high`。agent 先用自己的设置，没有就用所在层级的（审查员按自己的层级，verifier 和 writer 为 `standard`，judge 为 `top`，helper 为 `light`）；verifier 和 judge 从不沿用审查员的。不设置时什么都不发送，用供应商的默认值。

```json
{
  "effort": { "standard": "medium", "top": "high" },
  "reviewers": { "security": { "effort": "high" } },
  "roles": { "helper": { "effort": "minimal" } }
}
```

`OCRA_EFFORT_TOP`、`OCRA_EFFORT_STANDARD` 和 `OCRA_EFFORT_LIGHT` 会覆盖对应层级的设置。

- **`direct`** 发送 `reasoning_effort`；对声明了 `"effort": "openrouter"` 的供应商发送 `reasoning: { effort }`（见[模型供应商](./providers#你自己的端点)）；`none` 按 `none` 发送。带其他级别的调用不发送 `temperature` 和 `seed`，推理模型会拒绝或忽略它们。端点返回 HTTP 400 并点名该参数时，去掉它重试一次（不算失败），这个模型之后的调用都不再带它，并给出警告。用 `"type": "anthropic"` 声明的供应商则收到 `output_config.effort` 加自适应思考，`minimal` 和 `none` 按 `low` 发送（见[模型供应商](./providers#使用-anthropic-api-的端点)）。
- **`opencode`** 把级别写进模型的供应商参数：OpenAI 推理模型（GPT-5、o 系列）用 `reasoningEffort`，Claude 4 及以后和 Gemini 2.5 用思考预算（thinking budget），Gemini 3 用 `thinkingLevel`；OpenRouter 模型和[声明的供应商](./providers#你自己的端点)按各自的 `effort` 接收。思考预算取 OpenCode 目录中该模型输出上限的一定比例（`minimal` 1/32、`low` 1/16、`medium` 1/4、`high` 1/2；Claude 至少 1,024 个 token，Gemini 不超出它自己的范围），没有上限时按 32,000 个 token 计算；`none` 关闭思考（Claude 不思考，Gemini 2.5 Flash 预算为 0）。每个模型的每个级别是独立的 OpenCode variant，共用一个模型的 agent 可以用不同级别。和 `direct` 一样，`none` 以外的级别不带配置的 `temperature`。其他供应商（Azure、Bedrock、Groq 等）不发送推理强度。
- 模型接受哪些级别来自 ocra 内置的一张表（`@open-cr-agent/core` 的 `effortCapability`），可能跟不上新模型：在 `opencode` 上，表里没为某模型列出的级别（例如 o3 的 `minimal`、Gemini 3 的 `medium`）或不认识的模型不带推理强度，每个 agent 警告一次。审查不会因此失败。启动时读不到 OpenCode 的模型目录时，不发送任何级别，警告里会给出原因。
- JSON 报告的 `provenance.agents` 列出每个 agent 的层级、推理强度、`applied` 和 `notApplied`；`--plan` 显示每个任务的推理强度；配置哈希也覆盖它。

## 供应商 key

key 只从环境变量读取，变量名用 OpenCode 期望的（`ANTHROPIC_API_KEY`、`OPENAI_API_KEY`；Google 可用 `GEMINI_API_KEY`、`GOOGLE_API_KEY` 或 `GOOGLE_GENERATIVE_AI_API_KEY`）。各供应商的变量，以及如何在 `providers` 下声明你自己的端点，见[模型供应商](./providers)。

agent 运行时只拿到 `PATH`、`HOME`、语言区域、代理和 CA 设置，以及模型链里供应商的凭据（ocra 不认识的供应商，拿到所有以其大写 id 开头的变量，例如 `GROQ_`）。云服务凭据、`GITHUB_TOKEN` 等其余变量都不会传过去；供应商还需要的变量，写进 `OCRA_RUNTIME_ENV`，用逗号分隔。

对一定需要 key 的供应商（Google、Anthropic、OpenAI、OpenRouter、Groq、Mistral、DeepSeek、xAI、Azure），ocra 在启动前检查，并指出缺少的变量。

## 执行参数

| 字段 | 默认值 | 含义 |
|---|---|---|
| `concurrency` | `8` | 同时运行的审查任务数（1–32）；v0.16.0 之前是 `4`。一次审查的耗时大约是模型请求总数除以这个数，只有供应商的限流总让运行暂停时才需要调低 |
| `taskTimeoutMinutes` | `10` | 单个审查任务的时间上限，最多 `35791`（约 24.8 天，计时器能保持的最长时间） |
| `runTimeoutMinutes` | `25` | 整次运行的时间上限，最多 `35791` |
| `maxCostUsd` | 无 | 本次运行的花费上限：审查任务最多用到 80%，剩下的留给核查和裁决（见 `--max-cost-usd`） |
| `maxTasks` | `60` | 一次运行最多启动的审查任务数。超出时先去掉 `--ultra` 的第二遍，再去掉排在后面的审查员，尽量让每个文件至少保留第一个审查员，敏感路径上的文件保留得最久；被跳过的文件报告为未审查（退出码 `3`） |
| `judge` | `true` | 跨审查员合并、过滤并校准问题（每次有问题的运行调用一次 top 档位模型） |
| `ultra` | `false` | 以成本换召回率，同 [`--ultra`](./how-it-works#模式)；设为 `false` 时，即使你的 ocra Cloud 账户开启了 `ultra`，审查也保持默认模式。`--ultra` 和 `--no-ultra` 会覆盖它 |
| `showPreExisting` | `true` | 报告 Verify 判断为改动之前就已存在的问题，标为*已有问题*。它们从不计入结论；设为 `false` 则不显示，只在警告里给出数量 |
| `verify` | `true` | 报告前逐条核查问题（每个有问题的文件调用一次 standard 档位模型） |
| `walkthrough` | `--pr` 和 `--mr` 时开启 | 把[改动导读](./how-it-works#改动导读)写进摘要评论和报告（每次运行一次 standard 档位的调用）；`false` 不写，`true` 在本地审查时也写 |
| `mergeChecks` | 无 | 用自然语言写的[合并前检查](./how-it-works#合并前检查)，`[{ "id": …, "instruction": … }]`，每条都对照改动判断（每次运行一次 top 档位的调用）；最多 20 条，id 不能重复 |
| `fixes` | `false` | 为局部改动这些行就能修好的问题给出经过检查的[修复](./how-it-works)（每个有候选的文件最多一次 standard 档位的调用）；`--fixes` 只在本次运行开启 |
| `guidelineScope` | `"all"` | 每个审查任务拿到 `AGENTS.md` 的哪些章节；总是按文件顺序给出完整章节，最多 20,000 个字符，其余章节列出标题供审查员自行读取：`all`（所有章节给所有审查员）、`matched`（标题里写了路径的章节，如 `## web/`，连同其下的子章节，只给改动涉及该路径的任务；其余章节给所有任务）或 `reviewer`（只给 `agents-md` 审查员）。`agents-md` 审查员总是拿到所有章节。`--guidelines` 会覆盖它 |
| `linkedTasks` | `true` | 把 Pull Request 或 Merge Request [关联的 issue](./how-it-works#关联的任务) 交给审查员，每个都裁到固定大小；`false`（或 `--no-linked-tasks`）让提示词保持原样 |
| `sampling` | 无 | `{ "temperature": 0–2, "seed": n }`，用于每次模型调用，两项都可省略（不设置时用供应商默认值）；`--temperature` 和 `--seed` 会覆盖它。`direct` 两项都发送，但用 `"type": "anthropic"` 声明的供应商两项都不接受。`opencode` 只把温度传给目录标明接受温度的模型（[声明的模型](./providers#你自己的端点)都标明了），种子报告为未应用。`provenance.sampling` 写明实际应用了什么。种子只有在供应商遵守时才能让运行可重复 |

某个任务失败或超时不会导致整次运行失败，它负责的文件会被标记为 `failed`。

## 审查深度

`depth` 用一个词选审查有多深入：`quick`、`standard`（ocra 的默认值）或 `deep`。它只填补下面这些没有任何一层自己设置的项：配置里的键、账户设置、`OCRA_EFFORT_*` 变量或命令行参数总是优先于深度。`--depth` 对单次运行覆盖它。

| 设置 | `quick` | `standard` | `deep` |
|---|---|---|---|
| 审查员 | `correctness` 在所有风险档运行，`security` 只在 `full` 档运行；关闭 `performance`、`docs` 和 `agents-md` | 按风险档（见[审查员](#审查员)） | 所有审查员在所有风险档运行，每个跑两次（`ultra`） |
| `effort.standard` | `low` | 不设置 | `high` |
| `effort.top` | 不设置 | 不设置 | `high` |
| `minInlineSeverity` | `warning` | 不设置 | 不设置 |
| `showPreExisting` | `false` | 不设置 | 不设置 |

每种深度都会做验证和 judge。你自己为某个审查员写的条目会整体替代深度对它的设置。`--plan` 会把深度填补的项标为来源 `depth`。

## 行内评论

在 Pull Request 或 Merge Request 上，没有设置策略时，每条落在 diff 行上的问题都会成为一条行内评论。下面的键可以少发一些；没发出的问题会列在摘要评论里一个折叠的 *not posted inline* 小节中并注明原因，仍保留在 [JSON 报告](./cli#json-输出)里（`inline.held` 列出它们），也照旧计入结论。

| 键 | 默认值 | 含义 |
|---|---|---|
| `minInlineSeverity` | 无 | 只把严重程度不低于此值的问题发成行内评论：`critical`、`warning` 或 `suggestion`。`--min-inline-severity` 会覆盖它 |
| `maxInlineComments` | 无 | 本次审查的问题最多发这么多条行内评论（0 到 1000；0 表示一条都不发）。最严重的优先，其次是 Verify 确认过的，再次是它拿不准的，然后是未核查的，低置信度问题排最后；相同时按文件、行号和 fingerprint 排序，所以每次留下的都是同样的问题。上限按每次审查自己的问题计算（之前审查已评论过、这次又报告的问题占一个名额，但不会重复发），所以经过多次 push 的改动累计的行内评论可能超过上限。`--max-inline-comments` 会覆盖它 |

git 及其启动的程序（ssh、凭据助手、代理）只拿到 ocra 环境变量的一部分，永远拿不到模型 key 或平台 token：所有 `GIT_*` 和 `SSH_*` 变量、`PATH`、`HOME`、`XDG_CONFIG_HOME`、`TMPDIR`、代理变量（`HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY`）、`SSL_CERT_FILE`、`SSL_CERT_DIR`、`CURL_CA_BUNDLE`，以及 Windows 上 git 需要的系统变量（`PATHEXT`、`SYSTEMROOT`、`TEMP`、`USERPROFILE`、`APPDATA` 等）。fetch 还会拿到凭据助手读取的变量：`GH_*`、`GLAB_*`、`GITLAB_*`、`GCM_*`、`GITHUB_TOKEN` 和 `GITHUB_ENTERPRISE_TOKEN`。如果你的环境需要给 git 传其他变量（Kerberos、Nix 的证书包），可以通过 git 自身的配置传入，例如 `GIT_SSH_COMMAND` 或 `GIT_CONFIG_*`。

## 文件选择

ocra 会跳过：二进制文件、疑似密钥文件（`.env`、私钥、证书、云服务和镜像仓库凭据、Terraform 变量和状态文件）、已删除的文件、媒体和压缩包、锁文件、第三方和生成的代码，以及过大的 diff。超过 1 MB 的文件按二进制处理并跳过。名字看起来是文本（`.ts`、`.py` 等）却按二进制跳过的文件会给出警告。审查提交区间、单个提交和 PR 时，`.gitattributes` 从 base 提交读取（git 2.41 及以上），被审查的改动无法把自己的文件标成二进制。数据库迁移文件从不被当作生成代码；迁移工具写在它们旁边的文件则算生成代码（Drizzle 的 `meta/` 快照和 journal、Prisma 的 `migration_lock.toml`、EF Core 的 `*.Designer.cs` 和模型快照）。

- `exclude`：额外要跳过的 glob。
- `include`：即使会被当作生成代码或按扩展名跳过，也要审查的 glob。密钥文件永远无法被 include。

## 审查员

`reviewers.<id>` 可以关闭某个审查员，设置它开始运行的风险档位，或设置它的[模型](#按-agent-指定模型)或[推理强度](#推理强度)。风险档位从低到高：`trivial`（改动 ≤10 行）、`lite`（≤100 行）、`full`（更大的改动、超过 20 个文件，或涉及敏感路径：CI workflow，或目录名、文件名中含有 `auth`、`oauth`、`jwt`、`password`、`credential`、`secret`、`login`、`permission`、`acl`、`identity`、`crypto`、`security` 等单词）。

```json
{ "reviewers": { "correctness": { "minTier": "lite" }, "security": { "enabled": false } } }
```

被 Matrix 跳过的组合会列在 JSON 报告的 `skipped` 里；没有任何审查员覆盖的文件在覆盖情况里显示为 `unreviewed`。

## Learnings

`learnings.requireReview`（默认 `false`）：`ocra learn mine --propose` 开的 pull request 或 Merge Request 留给人来合并，而不是检查通过后自动合并（[CLI](./cli#通过-pull-request-写回)）。共享配置也可以设置它。

## 任务跟踪系统

`trackers` 通过你的跟踪系统的 MCP 服务器，从 Jira 或 TAPD 读取改动所提到的任务，与平台关联的 issue 一起交给审查员（[关联的任务](./how-it-works#关联的任务)）：

```json
{
  "trackers": {
    "jira": {
      "projects": ["PAY", "AUTH"],
      "server": { "url": "https://mcp.example.com/jira", "tokenEnv": "JIRA_MCP_TOKEN" },
      "tool": "jira_get_issue",
      "keyArgument": "issue_key"
    },
    "tapd": {
      "workspace": "20001234",
      "server": { "url": "https://mcp.example.com/tapd", "tokenEnv": "TAPD_MCP_TOKEN" },
      "tools": { "story": "get_story", "bug": "get_bug", "task": "get_task" },
      "keyArgument": "id"
    }
  }
}
```

| 键 | 含义 |
|---|---|
| `jira.projects` | 你的 Jira 项目 key：标题、描述或分支名中的 `PAY-12`（包括 `feature/pay-12-retry`）指向一个任务；其他项目的 key 会被忽略 |
| `tapd.workspace` | 你的 TAPD 项目 id：`--story=1001234`、`--bug=…`、`--task=…`，以及指向该项目需求、缺陷和任务的链接，都指向一个任务 |
| `server.url` | MCP 服务器（Streamable HTTP），使用 https，或本机上的 http。ocra 从不启动服务器进程 |
| `server.tokenEnv` | 环境变量名，其值作为 `Authorization: Bearer …` 发送；不能是 `GITHUB_`、`GITLAB_`、`AWS_` 等平台变量 |
| `tool`、`tools` | 读取一个任务的工具；TAPD 按类型各配一个（没有配置的类型会跳过） |
| `keyArgument`、`arguments` | 放 key（TAPD 为数字 id）的参数，以及随之发送的固定字符串参数；TAPD 还会收到 `workspace_id` |

返回结果按常见字段读取（`summary`、`title` 或 `name`，`description`，`status`，`labels`，可以在 `fields` 下或一层包装对象里），否则作为纯文本，最多 64,000 个字符。每个任务一次连接，每个请求最多 20 秒。读取需要 MCP SDK，它随 ocra 的可选依赖安装。共享配置可以设置 `trackers`，账户设置不行。v0.11.0 新增。

## 项目文档

`projectDocs` 列出审查员应当对照的设计文档：Markdown 文件（`.md`、`.mdx`），或目录（读取其中直接包含的 Markdown 文件），写仓库内的路径（[项目文档](./how-it-works#项目文档)）：

```json
{ "projectDocs": ["docs/architecture.md", "docs/design/"] }
```

它们和 `AGENTS.md` 一样从可信版本读取：最多 50 个文档，每个最多 200,000 字节；路径不存在、过大或在仓库之外时只产生一条警告。共享配置可以设置 `projectDocs`，账户设置不能。v0.11.0 新增。

## 共享配置

仓库可以继承组织的通用设置：

```json
{ "extends": "https://config.example.com/ocra.json#sha256=<hex>" }
```

共享文件可以设置 `models`、`concurrency`、超时、`verify`、`judge`、`showPreExisting`、`ultra`、`depth`、`minInlineSeverity`、`maxInlineComments`、`walkthrough`、`fixes`、`mergeChecks`、`linkedTasks`、`guidelineScope`、`trackers`、`projectDocs`、`maxCostUsd`、`maxTasks`、`include`、`exclude`、`effort`、`reviewers`、`roles`、`github`、`providers`（仅在固定内容时）和 `rules`（格式同 `.ocra/rules.json` 的条目）。它不能列出插件或选择运行时，因为它不能执行代码。仓库自己的设置优先；`include`、`exclude` 和 `rules` 合并，`models`、`effort`、`reviewers`、`roles`、`github` 和 `providers` 按键合并。

只接受 `https` 地址，不跟随重定向，最大 256 KB。`#sha256=` 固定文件内容；声明了 `providers` 的文件必须固定，因为供应商决定了你的代码发往哪里（见[模型供应商](./providers#你自己的端点)）。文件无法加载或无效时，ocra 警告后只用仓库自己的设置，只写在共享文件里的限制（例如 `maxCostUsd`）就不生效；必须始终生效的限制请在仓库里也写一份。

## ocra Cloud

| 字段 | 默认值 | 含义 |
|---|---|---|
| `cloud.shareRepoName` | `false` | [登录](./cli#ocra-loginocra-logoutocra-whoami)后，每次上传还会说明是哪个仓库：它的路径（`owner/name`，GitLab 上可以有更多层）和为计算哈希而规范化后的地址，让 ocra Cloud 可以显示审查属于哪个仓库。没有主机的仓库（本地路径形式的远程，或没有 origin）从不说明，脱敏会改动其地址的仓库也不说明。只能在仓库的配置文件或 `--config` 指定的文件里设置；共享配置和账户都不能设置 |

## 账户设置

登录 [ocra Cloud](./cli#ocra-loginocra-logoutocra-whoami) 后，`ocra review` 把账户设置放在配置之下。优先级从高到低：命令行参数、配置（仓库的文件或 `--config`、它 `extends` 的共享配置、`OCRA_*` 环境变量）、账户设置、ocra 的默认值。

| 账户中的键 | 如何生效 |
|---|---|
| `runtime`（`opencode`、`direct` 或 `codex`）、`models.<tier>`、`effort.<tier>`、`reviewers.<id>`、`roles.<role>` | 只补充配置没有写的部分；配置中某个审查员或角色的条目整体优先 |
| `concurrency`、`taskTimeoutMinutes`、`runTimeoutMinutes`、`maxCostUsd`、`maxTasks`、`verify`、`judge`、`fixes`、`linkedTasks`、`sampling`、`ultra`、`depth`、`minInlineSeverity`、`maxInlineComments` | 只在配置没有设置时生效（`sampling` 算一个整体）：账户可以给没有上限的运行加上限，但不能放宽限制 |
| `include` | 合并：先是配置中的模式，再是账户的 |
| `exclude` | 只在配置没有设置时生效：账户排除的文件既不审查，也不算作未审查，所以配置里写了 `exclude`（哪怕是 `[]`）就不再采用账户的 |
| `rules` | 追加在仓库规则和共享规则之后：最多 50 条，格式与 [`.ocra/rules.json`](./rules) 的条目相同，每条规则最多 2,000 个字符，以同样的方式嵌入提示词 |

每个键都按本文件的 schema 校验；不符合的、或当前版本不认识的键会被忽略，并给出点名它的警告，其余照常生效。模型必须是 `ocra-<provider>/<model>`，经由 ocra Cloud 使用其中保存的 key。账户永远不能设置 `providers`、`extends`、`github`（`botLogin` 决定信任谁的评论）或插件：ocra 会忽略并给出警告。

账户设置同样适用于 `--pr` 和 `--mr`，位于基准提交的配置之下，从不来自被审查的代码。补充了哪些会打印出来（`From your ocra Cloud settings: …`），`--plan` 列出每项设置的来源，`provenance.accountSettings.version` 记录所用的版本。配置哈希覆盖它和账户规则，因此未登录时哈希不变。连不上 ocra Cloud 时会给出警告，只使用配置。

## 插件

`runtime` 选择已注册的运行时：`opencode`（默认）、`direct` 或 `codex`（见[选择运行时](./providers#选择运行时)）。`plugins` 按包名或路径列出额外的插件，`pluginSettings.<插件名>` 存放各插件的设置。详见[插件](./plugins)。
