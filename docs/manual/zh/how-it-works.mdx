按领域分工的审查员和一个负责协调的裁决者做判断；所有不能出错的步骤都交给确定性代码。

```text
Ingest → Select → Triage → Bundle → Matrix → Execute → Anchor → Filter → Verify → Judge → Report
```

| 阶段 | 做什么 |
|---|---|
| **Ingest** | 通过代码托管平台适配器读取改动和仓库规范。 |
| **Select** | 逐个文件决定：审查，或者排除并记录原因（二进制、密钥、生成代码、过大……）。 |
| **Triage** | 根据改动规模和 `auth/`、`PasswordHasher.cs`、CI workflow 这类敏感路径，给出风险档位（trivial、lite、full）。 |
| **Bundle** | 把相关文件分组：改动少时合成一组，否则由 light 模型按文件编号分组。没有它时，20 个文件以内每个文件一个任务，更多时按目录分组。 |
| **Matrix** | 根据风险档位和每个审查员的适用范围，决定哪个审查员审查哪个分组。被跳过的组合会写进报告。 |
| **Execute** | 每个计划好的（分组，审查员）组合作为一个隔离的 agent 任务运行，只有只读工具。在 Pull Request 或 Merge Request 上，同时还有一次 standard 档位的调用写出[改动导读](#改动导读)；配置了[合并前检查](#合并前检查)时，再有一次 top 档位的调用判断它们。 |
| **Anchor** | 把每条问题引用的代码解析成准确的行号。 |
| **Filter** | 去掉仓库记忆已接受的和维护者驳回的问题，并与同一 PR 的上一次评审对比，不为它们花模型调用。 |
| **Verify** | standard 档位的模型对照每个文件的 diff 和附近代码核查问题，还会看到每条问题引用的代码里的名字在仓库其他地方的定义和用法。只有代码证明它错了才丢弃；拿不准或核查失败都保留。被丢弃的问题和原因写进报告。核查判断问题在这次改动之前就已存在时，会标为*已有问题*（pre-existing），从不计入结论；设置 [`showPreExisting: false`](./configuration) 则不在报告里显示这类问题。 Verify 在审查任务还在运行时就开始：一个文件的所有审查任务结束后，它的问题立即核查，每条只核查一次，所以 Verify 确认的 critical 问题在审查结束前就已确定，并展示给正在观看这次运行的人（[ADR-0074](https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/adr/0074-early-findings.md)）。 |
| **Judge** | 一次 top 档位的调用看到所有问题，连同审查员引用的代码和 Verify 是否确认了它：合并不同审查员对同一根因的报告，丢弃臆测和吹毛求疵，校准严重程度，写一段简短总结，每项调整在报告里附上原因。 |
| **Fix** | 默认关闭，需要时开启（[`fixes`](./configuration)、`--fixes`）。对锚定在改动新增或保留的行上的问题（最多 30 行，每次运行最多 10 条，严重的优先），每个文件一次 `fixer` 角色（standard 档位）的调用，不带任何工具，给出正好替换这些行的代码，或者不给。代码只在以下条件都满足时才保留修复：这些行仍是问题在被审查的 head 上引用的内容；修复确实改动了它们；不含控制字符或双向文本字符；最多新增 20 行、4,000 个字符；tree-sitter 在打补丁后的文件里发现的语法错误不比之前多。没有语法文件（grammar）的语言不给修复，也不发调用。被拒绝的修复连同原因列在报告里，问题本身保持不变。保留下来的修复会成为[可提交的建议](./github#可提交的建议)，也可以在 [ocra Cloud](./cloud) 里提交。修复是模型给出的、能通过语法检查的提议，并未被证明正确：提交前请先看一遍。 |

## 改动导读

在 Pull Request 或 Merge Request 上，摘要评论带有一份改动导读，写给即将审查这次改动的人：几句话说明改动做了什么；把改动的文件按它们在改动中的作用分组，按建议阅读的顺序排列（默认折叠）；改动新增或修改了三个及以上组件之间的调用时，再附一张 Mermaid 时序图（默认折叠）。它是 `writer` 角色（standard 档位）的一次调用，与审查员同时进行，读取标题、描述、每个审查文件的文件名，以及在 24,000 个字符内放得下的补丁（从小到大）。每次审查都重新写，所以描述的是整个改动，而不只是增量审查看过的部分。

模型只负责分组和描述：有哪些文件由 diff 决定（它编造的路径会被丢弃，漏掉的文件列在 *Other changes* 下）；时序图只有每一行都是普通的时序图语句时才显示，因此指令、链接、点击处理和标记都到不了页面上。调用失败或回答无效只会少一份导读并给出警告，不影响审查。[`.ocra/config.json`](./configuration) 中的 `walkthrough` 可以关闭它，也可以为本地审查打开，这时 JSON 报告里会带上它。

## 合并前检查

[`.ocra/config.json`](./configuration) 中的 `mergeChecks` 用自然语言列出团队对改动的要求，每条都有自己的 id：

```json
{
  "mergeChecks": [
    { "id": "user-impact", "instruction": "The description says how users are affected." },
    { "id": "migration-test", "instruction": "A new database migration comes with a test." }
  ]
}
```

`judge` 角色（top 档位）的一次调用与审查员同时进行，读取标题、描述、每个审查文件的文件名，以及在 40,000 个字符内放得下的补丁（从小到大），为每条检查给出结果和一句理由：`passed`（满足，或不适用于这次改动）、`failed`，或 `inconclusive`（看到的内容不足以判断）。检查以配置为准：配置里没有的 id 的结果会被丢弃，模型漏掉的检查记为 inconclusive。改动请求和 diff 对它来说只是数据，所以描述里写"检查都通过"不起作用。调用失败、回答无效或[花费上限](./configuration)用完时，每条检查都记为 inconclusive 并给出警告，不影响审查。

结果写进摘要评论和报告的 `mergeChecks`。它们从不改变结论或退出码：失败的检查是否阻止合并，由读取结果的一方决定，例如 ocra Cloud 会把它们作为一项检查发布。最多 20 条检查，每条要求最多 500 个字符。

## 关联的任务

审查 Pull Request 或 Merge Request 时，每个审查任务还会拿到这次改动所针对的 issue，审查员可以据此检查改动是否做了要求的事：漏掉的验收条件、没做完的子任务、修错了场景。这些是平台关联到改动上的 issue：GitHub 上是 Pull Request 要关闭的 issue（`Closes #12` 这样的关闭关键字，或在侧栏关联的 issue），GitLab 上是 Merge Request 要关闭的 issue；都没有时，取分支名所对应的 issue（`12-fix-login`，两个平台从 issue 创建分支时都这样命名）。只算被审查仓库自己的 issue，因此来自 fork 的 Pull Request 无法把其他仓库的 issue 带进审查。设置了 [`trackers`](./configuration#任务跟踪系统) 时，标题、描述或分支名中按 key 提到的 Jira 或 TAPD 任务排在其后，通过你的跟踪系统的 MCP 服务器读取。v0.11.0 新增。

最多 3 个 issue，每个带标题、状态、标签、正文的前 4,000 个字符、父任务的标题和前 1,500 个字符（GitHub 的父 issue，GitLab 的 epic），以及最多 10 个子 issue 的标题；不做搜索，也不由模型挑选。这些文字放在所有任务共享的提示词部分，每次运行只缓存一次。查询失败（令牌无权读取 issue）只产生一条警告，审查照常进行。报告的 `linkedTasks` 列出交出去的内容。在 [`.ocra/config.json`](./configuration) 中设置 `linkedTasks: false` 或使用 `--no-linked-tasks` 可以关闭。

## 项目文档

设置了 [`projectDocs`](./configuration#项目文档) 时，每个审查任务还会拿到团队设计文档中提到其文件的段落，审查员可以据此对照预期设计检查改动。文档按标题（1 到 3 级，代码块之外）切分成段落；段落提到文件的路径、文件名或所在目录（只有 `src` 这类通用目录不算）即算提到该文件，提到完整路径的权重最高。每个任务最多拿到 3 个段落，每段取前 3,000 个字符，另外列出最多 10 个可自行读取的段落标题；不做搜索，也不由模型挑选。没有提到任务中任何文件的段落不会进入其提示词。报告的 `projectDocs` 列出交出的每个段落以及它交给了哪些分组。v0.11.0 新增。

## 结论（verdict）

结论由一套固定规则根据最终的问题决定，而不是由模型决定，所以相同的问题总会得到相同的结论：

| 问题 | 结论 |
|---|---|
| 没有问题 | `approved` |
| 只有 suggestion，或少于三个 warning | `approved_with_comments` |
| 三个及以上 warning，或未经核查确认的 critical | `minor_issues` |
| 任何经核查确认的 critical | `significant_concerns` |

每条问题都标明核查（Verify）的结果：**已确认**、**不确定**或**未核查**（被跳过、失败或预算不足）。未经确认的 critical 照常显示为 critical 并标为未核实，但结论最高只到 `minor_issues`，一个模型未经核查的判断不能拦下改动。某条 critical 的核查失败或预算不足时，运行算作不完整（退出码 `3`），绝不会被当成通过；`verify: false` 时不算。Judge 既不能丢弃、也不能降级已确认的 critical；这类尝试会被忽略并记入警告。如果 Judge 被关闭、没有 `top` 模型或调用失败，问题不经裁决直接报告，规则照样适用。

什么都没审查的运行没有结论：终端和 PR 摘要会写 “Not reviewed” 及原因（模型服务拒绝了全部调用时，说明是每日上限还是限流；JSON 报告里这些任务带有 `quota`：`daily_limit` 或 `rate_limit`），上传到 ocra Cloud 的记录也不带结论。

结论**只是参考意见，不是安全门禁**（[原因](./security#结论不是安全门禁)）。

## 模式

默认模式偏重准确率。`--ultra` 用成本换召回率：

| | 默认 | `--ultra` |
|---|---|---|
| 审查员 | 按风险档位和适用范围 | 所有审查员在所有档位都运行，包括通过 `reviewers.<id>.minTier` 设置的档位（超出审查员适用范围的文件仍会跳过，`enabled: false` 仍然生效） |
| 采样 | 每个审查员、每个分组跑一次 | 跑两次，按 fingerprint 合并 |
| 计划 | 只针对大分组（5 个文件及以上，或 diff 超过 40,000 字符），且审查员按分组分任务时才做 | 每个任务都有。先用一次简短的模型调用列出优先要查的地方；失败时任务照常运行 |
| 调用方 | 风险档位为 `full` 时和 `--ultra` 一样提供；低于它时审查员自己搜索 | 把分组里定义或改动的符号在分组之外的用法提供给审查员 |
| Judge | 丢掉臆测和吹毛求疵 | 保留它们并标为*低置信度*，不计入结论 |
| 成本 | 基准 | 约两倍或更多，外加每个任务一次计划调用 |

两种模式下的核查（Verify）完全一样。[`depth`](./configuration#审查深度) 在这些设置之上给出三个预设：`quick`、`standard` 和 `deep`（`deep` 会开启 `--ultra`）。

调用方用 [tree-sitter](https://tree-sitter.github.io/) 查找，支持 TypeScript、JavaScript、Python、Go、Rust 和 Java：符号体内任何一行改动都算这个符号改了，不只是签名；签名改动的排在前面，最多 8 个符号。用法指代码里出现的名字（注释和字符串不算），附上它所在的函数或类，每个符号最多 10 处。其他语言退回到按改动行匹配定义模式、再整词搜索。每个文件解析出的内容按文件内容缓存在 `~/.cache/ocra/symbols/`（`$XDG_CACHE_HOME/ocra/`，Windows 上是 `%LOCALAPPDATA%\ocra\`，或 `$OCRA_CACHE_DIR`，CI 可以在多次运行之间保留它，[GitHub Action](./github) 就是这样做的）；删掉它只会多花解析时间。

加上 `--scip <文件>` 时，仓库的 [SCIP](https://github.com/scip-code/scip) 索引（由 `scip-typescript`、`scip-java`、`scip-python` 等在仓库根目录生成）优先回答：它认识的符号得到的是编译器解析出的确切用法，两个同名的 `run` 方法不再共用调用方。索引描述的是它生成时的版本，通常是主分支；某处用法所在的行已不再出现这个符号时会被去掉，它不认识的符号（改动里新增的，或它不覆盖的语言）照上面的方式搜索。读不了的索引（最大 512 MB）只给一条警告，审查照常进行。ocra 自己从不生成索引。

加上 `--graph <文件>` 时，由 [`ocra graph`](./cli#ocra-graph) 生成的代码图接着回答：给出这个名字在它所描述版本的每个文件里的用法，每次审查不必再搜索。它和搜索一样按名字匹配，所以分不开同名的符号。和索引一样，它描述的是自己的版本：已不再出现这个符号的行会被去掉，不在图里的文件中的符号照常搜索。

## 审查员与工具

审查员是一个带有专门提示词的 agent，有自己的规则，以及告诉 Matrix 在哪里运行它的适用范围：

| 审查员 | 关注 | 运行档位 | 跳过 |
|---|---|---|---|
| `correctness` | 逻辑错误、契约被破坏、错误处理 | 所有档位 | 无 |
| `security` | 能被不可信输入触达、可被利用的问题：注入、授权、密钥、加密、不安全的解析、CI | `lite` 和 `full` | 文档、测试 |
| `performance` | 重要路径上可度量的性能退化：复杂度、N+1、阻塞操作、内存 | `full`；分组里有热路径上的文件（如 cache、query、queue、pool、stream、cluster）时从 `lite` 起 | 文档、测试、配置数据、CI workflow |
| `docs` | 被这次改动弄错的文档：被删除或改名的参数、配置项、接口或默认值，而 README、文档或帮助文字还在描述旧的（用 light 模型） | `lite` 和 `full` | 测试 |
| `agents-md` | `AGENTS.md` 里被这次改动弄错的内容：命令、目录结构、模块职责、需要的工具和环境变量（用 light 模型；仅当仓库有 `AGENTS.md` 时运行） | `lite` 和 `full` | 测试 |

`docs` 和 `agents-md` 拿改动去对照改动之外的文档，所以它们审查的是整个改动，而不是逐个分组：一个任务；改动超过 20 个文件或 120,000 字符的 diff 时分成几个。`security` 和 `performance` 把相邻的分组合在一个任务里看，不超过分组的大小上限（10 个文件、120,000 字符），敏感路径单独成任务。每个审查员只看自己的领域，并写明哪些不该报。审查员只能读：`read_file`、`read_diff` 和 `code_search` 返回被审查的那个版本（区间或单个 commit 模式下是对应的 commit，不是你的工作区），`read_learning` 返回团队的 learning（见[规则](./rules#ocralearnings)），问题通过 `report_finding` 提交。返回有上限（每行 2,000 字符、每次 50,000 字符、每个文件最多读 2 MB），压缩过的打包文件塞不满上下文。审查员不能修改文件、执行命令或访问网络。

## 行号定位

模型给出的行号不可靠，所以让模型引用代码，由 ocra 解析：

1. 在该文件改动过的代码段里做规范化匹配；
2. 在整个文件里匹配；
3. 在其他改动文件里匹配（模型写错了文件），只接受整行引用，而且只能在一处找到；
4. 把问题和该文件的 diff 交给 light 模型，让它指出对应的代码行，再像普通引用一样去匹配（每条没匹配上的问题一次小调用）；
5. 以上都不行，问题就挂在它自己的文件上，作为文件级问题。

如果问题最终落到本次改动中、但属于别的分组的文件上，会被保留：bug 常常出现在一个分组的改动与另一个分组的改动相交的地方。那个文件的审查员也报告了同一个问题时，只保留一份。落到改动之外的文件、或增量审查没有覆盖的文件上的问题，会被丢弃并记一条警告。

优先按整行匹配。引用只是一行的一部分时，只有不少于 12 个字符、且只有一行包含它才算匹配，所以 `err` 这样的片段不会落到第一个包含它的行上。同样适合多个位置的引用（比如三行一样的 `return err;`）留在文件级别，并计入 `anchoring.ambiguous`。JSON 报告（`--format json`、会话的 `report.json`）给出整次运行的 `anchoring`：每种方式（`hunk`、`file`、`cross_file`、`relocated`、`file_level`）的问题数、有歧义的数量，以及重新定位调用的次数。

## 稳定性

- 单个任务和整次运行都有超时，即使模型不再响应也生效。任务五分钟没有进展（没有新的步骤、文字或工具调用）会提前停止，交给模型链里的下一个模型。
- 任务失败不会让整次运行失败，它的文件标记为 `failed`。
- 每个层级都有模型降级链，每个模型都有熔断器（反复失败后打开，冷却后放行一次试探）。
- 供应商要求短时间后重试（最多 90 秒）的限流，会让所有任务暂停这个模型再重试；没有给出等待的限流依次暂停 15、30、60 秒，暂停期间到达的限流算作同一次暂停。使用 `direct` 运行时时，暂停结束后只重发被拒的请求，任务保留已经走过的步骤。按天计算的限流、更长的等待、连续暂停三次后再次限流，会让这个模型在本次运行里不再使用。
- 每个审查 agent 最多 30 步，因为每一步都会重发整个对话；大多数任务约 15 步结束。
- 审查提示词里的每个上下文来源都有上限，大改动不会把代码挤出去：改动文件列表最多 150 个文件，已接受的问题取打包文件上的最近 20 条，仓库规则最多 12,000 个字符，任务和 learning 的标题最多 300 个字符；更小的输入完整呈现。`ocra review --plan --format json` 按来源给出每个任务的首个提示词（token 数、截断和重复的行），[`--without`](./cli#ocra-review) 去掉某些来源，用来衡量每个来源的价值。v0.12.0 新增。
- agent 提前停下（没有完成信号、没有结论、步数没用完）时，会在同一会话里被提示一次，审完剩下的文件；进度行会写"resumed after stopping early"。
- 仍然没有完成信号就结束的 agent（用完步数，或又一次停下）会在同一会话里再得到一轮，这一轮只能报告问题和结束，用来报告它已经确认的问题。这一轮最多两次模型请求，计入花费、花费上限和超时；运行已取消或已超过花费上限时不会开始，这一轮失败时保留它报告的问题，任务不会因此失败。进度行会写"wrap-up turn reported N finding(s)"，[JSON 报告](./cli#json-输出)里的任务带有 `wrapUp`。
- 没有完成信号就结束的任务（用完 30 步、填满[声明的上下文窗口](./providers#上下文窗口较小的模型)，或又一次停下）不算审查过：它的文件报告为只审查了一部分（`incomplete`），运行退出码为 `3`，PR 或 MR 的下一次审查会包含它们。收尾的一轮不改变这一点：它只报告 agent 已经确认的问题，不会再读任何内容。
