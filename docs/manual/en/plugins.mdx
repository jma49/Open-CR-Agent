Everything in ocra is a plugin: the local Git and GitHub adapters, the OpenCode runtime, the correctness, security, performance, docs and agents-md reviewers and the session log ship as built-in plugins. Your plugins use the same contract.

## Writing a plugin

A plugin is a module that exports an object as `default` (or `plugin`):

```js
// tools/ocra-team-rules.mjs
export default {
  name: "team-rules",
  configure(ctx) {
    ctx.registerRules([
      {
        path: "services/**",
        rule: `Owned by ${ctx.settings.team}: check idempotency keys on every write.`,
      },
    ]);
  },
};
```

Register it in `.ocra/config.json`:

```json
{
  "plugins": ["./tools/ocra-team-rules.mjs"],
  "pluginSettings": { "team-rules": { "team": "payments" } }
}
```

Plugins are resolved from the repository's own dependencies (package names) or from file paths, resolved from the repository root (they may point outside it: the configuration is yours to trust). Plugins run code, so they load only from a repository's own config in local reviews, never for pull requests or with `--no-repo-config`.

## Plugins from your ocra Cloud account

When you are [signed in](./cli#ocra-login-ocra-logout-ocra-whoami), your ocra Cloud settings may name plugins by npm package name, with `pluginSettings` for them. A plugin runs code on your machine, so the account only names it: it loads on a machine only after you allow it there with [`ocra plugins allow`](./cli#ocra-plugins).

```bash
ocra plugins allow ocra-plugin-team-rules@1.4.0   # shows the package and its publisher, then installs it
ocra plugins list
ocra plugins deny ocra-plugin-team-rules
```

`allow` needs an exact version, never a range or tag. It shows the package's name, version, publisher, maintainers and integrity as the registry lists them, installs that exact version with install scripts off into `~/.config/ocra/plugins/` (`$XDG_CONFIG_HOME/ocra/plugins/`, or `%APPDATA%\ocra\plugins\` on Windows), and records its name, version and integrity in `plugins.json` there (readable only by you). npm runs in that directory, so the npm configuration of the project you run ocra from does not apply, and a package whose registry entry lists no integrity is refused. The recorded integrity covers the package tarball itself, not its dependencies: those are installed by npm as it resolves them at that time. Allowing a plugin is your own supply-chain decision, like adding a dependency.

A review loads a plugin your account names only:

- if this machine allowed it, from that directory alone, never from the reviewed checkout's `node_modules`, and only while the installed package still has the version and integrity recorded when you allowed it;
- where a repository's plugins could load: local reviews, never `--pr` or `--mr`, never with `--no-repo-config`.

A plugin your account names that this machine has not allowed is skipped with one warning naming it and `ocra plugins allow <name>@<version>`. A plugin the repository's configuration already lists loads as the repository's, and one whose plugin name is already taken is skipped. A plugin from the account that fails to load is skipped with a warning; it never fails the review.

The account's `pluginSettings` apply only to the plugins it lists and this machine loads, keyed by the npm package name the account lists (for example `@acme/ocra-team-rules`, not the `team-rules` plugin it exports), as ocra Cloud stores them; the plugin then receives them under its own name, as from the configuration; the configuration's own `pluginSettings` win, and a repository plugin's settings come from the repository alone.

## Lifecycle

| Hook | Runs | On failure |
|---|---|---|
| `bootstrap(ctx)` | All plugins concurrently | Warning; the review continues |
| `configure(ctx)` | In load order | The review stops, naming the plugin |
| `postConfigure(ctx)` | Concurrently, after all registrations | The review stops |

Use `bootstrap` for work that may fail harmlessly, such as fetching remote settings.

## What a plugin can register

| Method | Contributes |
|---|---|
| `registerVcs(name, factory)` | A code host adapter |
| `registerRuntime(name, factory)` | An agent runtime |
| `registerReviewer(definition)` | A reviewer with its own prompt and model tier |
| `registerRules(rules)` | Path-scoped review rules |
| `registerTool(tool)` | A tool reviewers can call, with a Zod input schema |
| `onEvent(listener)` | A listener for every review event (telemetry, notifications). A listener that throws is disabled with one warning; the review continues |

A runtime factory receives the model chains, the environment, the declared providers and, when configured, `sampling` (`temperature`, `seed`); a runtime says what it sends in its `sampling` property, listing in `notApplied` what it cannot pass on. A runtime without that property is reported as applying none of it. A task's spec carries the [`effort`](./configuration#effort) its reviewer asks for, and a completion request names its `agent` (the reviewer of a plan call, or `verifier`, `judge` or `helper`) and `effort`; both are absent when no effort is configured. A runtime that sends the effort implements `appliedTo(agent)`, returning whether every call of that agent sent it, in `unsupported` the models it left the level out for because they do not take it (the run warns once per agent), and in `notApplied` the sampling settings those calls left out. `effortCapability(model)` from `@open-cr-agent/core` gives ocra's table of what a model takes: the parameter style and the levels. A runtime without it is reported as sending no effort, and the run warns once. An agent with [its own model chain](./configuration#models-per-agent) sends it as `models` on its task specs and completion requests, and the factory receives every such chain, by agent id, in `agentModels`, for a runtime that prepares its providers before the first call; a runtime that ignores both runs those calls on the tier's chain.

Plugins receive only their own settings (`ctx.settings`), validated by an optional `settingsSchema`. Registering a name twice, using a reserved tool name, or registering after `configure` fails with an error naming the plugin.

## Security

A plugin runs code. Load plugins only from repositories you trust, and allow a plugin your account names only after checking who publishes it; to review someone else's branch, run `ocra review --no-repo-config`, which ignores the repository's config and plugins. In CI, read configuration from the protected base branch, never from the pull request under review.
