Reviewers combine four layers of guidance.

## Built-in rules

The correctness reviewer gets general correctness rules (logic errors, broken contracts, hidden failures, resource and concurrency bugs, data integrity, security defects visible in the change), plus language rules for the files in its bundle; the security and performance reviewers get their own rule sets instead:

| Language | Extensions |
|---|---|
| TypeScript / JavaScript | `.ts` `.tsx` `.mts` `.cts` `.js` `.jsx` `.mjs` `.cjs` |
| Python | `.py` `.pyi` |
| Go | `.go` |
| Java | `.java` |

Each reviewer prompt also lists what it must **not** flag: style, formatting, speculation without a reachable input, missing tests or docs, refactoring ideas, and issues in code the change does not touch.

## AGENTS.md

A root `AGENTS.md` goes to reviewers as repository guidelines, truncated at 20,000 characters. It is read at the revision under review (for pull requests, the base commit, so a pull request cannot rewrite it). Use it for conventions to enforce: architecture boundaries, error-handling policy, forbidden APIs.

## .ocra/rules.json

Path-scoped rules apply only when a bundle contains a matching file:

```json
{
  "rules": [
    {
      "id": "idempotency-key",
      "path": "services/billing/**",
      "rule": "Every write must carry an idempotency key. Flag handlers that retry without one."
    },
    {
      "path": ["**/*.sql", "db/migrations/**"],
      "rule": "Migrations must be backward compatible with the previous release."
    }
  ]
}
```

- `path`: one glob or a list of globs.
- `rule`: free text given to the reviewer.
- `id` (optional): lowercase letters, digits and `-`, at most 64 characters. A finding that applies the rule names it in the report's `rule`, so ocra Cloud can count findings per rule. Without one, the rule is named `rule-` and 8 hex characters of its text, which change when the text does.

An invalid `rules.json` stops the run with an error. For pull requests it is read from the base commit.

## .ocra/rules.md

The same rules in plain language, for the team to write and read without JSON. A section whose heading names a path applies to files under it, as an `AGENTS.md` section does with `guidelineScope: "matched"`; every other section applies to every file:

```markdown
# Review rules

Every finding names the input that breaks the code. Do not flag missing log lines.

## services/billing/

Every write must carry an idempotency key. Flag handlers that retry without one.

## db/migrations/

Migrations must be backward compatible with the previous release.
```

- A heading names a path when it contains one with a slash (`## services/billing/`, ``### `web/src` ``); a subsection takes the path of the heading above it.
- Each section that has text becomes one rule, heading included, and goes to the tasks whose files it applies to, after the rules of `rules.json`. The report lists it with `source: "repository"`, and its `id` is its heading in lowercase with `-` between words (`services-billing`); a heading without Latin letters or digits gives the `rule-` id of its text.
- Globs (`**/*.sql`) stay in `rules.json`; a repository can keep both files.

A file over 20,000 characters stops the run with an error. For pull requests it is read from the base commit, like `rules.json`.

## .ocra/learnings

A learning is something the team learned from an earlier change: the bug a fix repaired, why a reviewer rejected a pattern. Each one is a Markdown file in `.ocra/learnings/`, named by its id (lowercase letters, digits and hyphens), with YAML frontmatter:

```markdown
---
title: Release pooled connections on every exit path
paths: ["src/db/**"]
symbols: [acquire]
keywords: [connection pool]
critical: true
source: { kind: fix-commit, ref: 3f2a9c1 }
created: 2026-11-21
---

`acquire()` hands out a connection that only `release()` returns. An early
`return` or a `throw` between them leaks it, and the pool runs dry under load.
```

- `title`, `paths` (globs, at least one) and `created` (a date) are required; the body says what to check and why, in at most 4,000 characters. Paths read like `.gitignore`: `*.sql` or `Dockerfile` match at any depth, `services/billing/` matches everything under it, a leading `/` anchors to the root, and case is ignored.
- `symbols`: identifiers whose use in a patch makes the learning apply anywhere, matched as whole identifiers. A name of two words or more matches in any naming convention (`createCharge` matches `create_charge` and `CREATE_CHARGE`), and `pool.connect` matches `pool?.connect`, `pool->connect` and `pool::connect`.
- `keywords`: words or phrases matched in the patch whatever their spelling (`connection pool` matches `ConnectionPool`, `connection_pool` and `connection pools`). A Chinese or Japanese keyword matches anywhere in the text, spaces or not.
- `critical`: always given when a path matches.
- `source`: where it came from (`kind`: `fix-commit`, `review-feedback`, `document`, `remember`, `incident` or `manual`; `ref`: a commit, pull request or link).

Each review task gets the learnings that apply to its files, chosen before any model runs: a critical learning whose path matches ranks first, then a path match with a symbol or keyword in the patch, then a path match whose symbol or keyword is in the function or class the change touches, then a symbol alone, then a path alone, then a keyword alone. ocra reads the touched functions only when more learnings apply than fit. At most 5 are given, within 8,000 characters of body, plus every critical one whose path matches (up to 10). Learnings that apply but do not fit are listed by id and title, up to 10, with a count of the rest; a reviewer reads one with `read_learning`, which answers from the same trusted revision. Reviewers read them as data and report only what the change itself gets wrong. The report's `learnings` lists each one given, with the bundles it went to, and a finding that applies one, given or listed, names its id in `rule`.

Learnings are read at the revision under review, and for pull requests from the base commit, like `rules.json`, so a pull request cannot add one that steers its own review. A file that is not a valid learning is skipped with a warning; at most 500 files of up to 16 KB are read.

`ocra learn mine` drafts learnings from your fix commits, `ocra learn feedback` from the findings you accepted or declined with a reason, `ocra learn import` from your postmortems and guidelines, and `ocra learn remember` from `@ocra remember` notes on pull requests ([CLI](./cli#ocra-learn)).
