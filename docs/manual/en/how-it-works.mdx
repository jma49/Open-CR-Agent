Domain-specialized reviewers and a coordinating judge make the judgment calls; deterministic code does every step that must not fail.

```text
Ingest → Select → Triage → Bundle → Matrix → Execute → Anchor → Filter → Verify → Judge → Report
```

| Stage | What happens |
|---|---|
| **Ingest** | Read the change set and repository guidelines through a VCS adapter. |
| **Select** | Decide per file: review it, or exclude it with a reason (binary, secret, generated, too large…). |
| **Triage** | Assign a risk tier (trivial, lite, full) from size and sensitive paths such as `auth/`, `PasswordHasher.cs` or CI workflows. |
| **Bundle** | Group related files: one bundle for small change sets, otherwise a light model groups them by file index. Without it, up to 20 files are reviewed one per task, more by directory. |
| **Matrix** | Pick which reviewer runs on which bundle from the risk tier and each reviewer's scope. Skipped pairs are listed in the report. |
| **Execute** | Run each planned (bundle, reviewer) pair as an isolated agent task with read-only tools. On a pull or merge request, one standard-tier call beside them writes the [walkthrough](#walkthrough), and one top-tier call judges the [pre-merge checks](#pre-merge-checks) when any are configured. |
| **Anchor** | Resolve every finding's quoted code to exact lines. |
| **Filter** | Drop findings the repository's memory accepts or a maintainer dismissed, and compare with the previous review of the same pull request, before spending a model call on them. |
| **Verify** | A standard-tier model checks each file's findings against its diff and surrounding code, and against where the names in each finding's quoted code are defined and used elsewhere in the repository. A finding is dropped only when the code proves it wrong; doubt or a failed check keeps it. Drops are listed in the report with the reason. A finding the verifier traces to code the change did not bring in is marked *pre-existing* and never counts towards the verdict; [`showPreExisting: false`](./configuration) leaves such findings out of the report. Verify starts while review tasks still run: a file's findings are checked as soon as every task reviewing that file has ended, each finding once, so a critical finding the verifier confirmed is known, and shown to anyone watching the run, before the review ends ([ADR-0074](https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/adr/0074-early-findings.md)). |
| **Judge** | One top-tier call sees every finding, with the code its reviewer quoted and whether Verify confirmed it: merges the same root cause across reviewers, drops speculation and nitpicks, recalibrates severity and writes a short summary, with a reason for each change in the report. |
| **Fix** | Off unless asked ([`fixes`](./configuration), `--fixes`). For findings anchored to lines the change added or kept, at most 30 lines and 10 findings a run, most severe first, one standard-tier call per file on the `fixer` role, without tools, proposes a replacement of exactly those lines, or none. Code keeps a fix only if the lines are still what the finding quoted at the reviewed head, it changes them, it holds no control or bidirectional character, it adds at most 20 lines and 4,000 characters, and tree-sitter finds no more syntax errors in the patched file than before; a language without a grammar gets no fix and costs no call. A rejected fix is listed in the report with its reason, and the finding stays as it was. Kept fixes become [committable suggestions](./github#committable-suggestions) and can be committed from [ocra Cloud](./cloud). A fix is a model's proposal that parses, not a proven one: read it before committing. |

## Walkthrough

On a pull or merge request the summary comment carries a walkthrough for the people about to review the change: a few sentences on what it does, the changed files grouped by what they do for it in the order to read them (folded), and, when the change adds or changes calls between three or more components, a Mermaid sequence diagram (folded). It is one call on the `writer` role (standard tier), made while the reviewers run, from the title, the description, every reviewed file's name and as much of the patches as fits in 24,000 characters, smallest first. It is written again on every review, so it describes the whole change, not only what an incremental review looked at.

The model only groups and describes: which files there are comes from the diff (a path it invents is dropped, a file it leaves out is listed under *Other changes*), and a diagram is shown only when every line is a plain sequence-diagram statement, so no directive, link, click handler or markup reaches the page. A failed or invalid answer costs the walkthrough, with a warning, never the review. `walkthrough` in [`.ocra/config.json`](./configuration) turns it off, or on for local reviews, whose JSON report then carries it.

## Pre-merge checks

`mergeChecks` in [`.ocra/config.json`](./configuration) lists the team's rules for a change in plain words, each with an id of its own:

```json
{
  "mergeChecks": [
    { "id": "user-impact", "instruction": "The description says how users are affected." },
    { "id": "migration-test", "instruction": "A new database migration comes with a test." }
  ]
}
```

One call on the `judge` role (top tier), made while the reviewers run, reads the title, the description, every reviewed file's name and as much of the patches as fits in 40,000 characters, smallest first, and gives each check an outcome with a one-sentence reason: `passed` (met, or not applicable to this change), `failed`, or `inconclusive` (what it was shown cannot settle it). The checks are the configuration's: an outcome for an id it does not list is dropped, and a check the model leaves out is inconclusive. The change request and the diff are data to it, so a description that says the checks pass decides nothing. A failed call, an invalid answer or a spent [limit](./configuration) leaves every check inconclusive with a warning, never the review.

The outcomes go into the summary comment and the report's `mergeChecks`. They never change the verdict or the exit code: whether a failed check blocks the merge is for whoever reads them, such as ocra Cloud, which posts them as a check. At most 20 checks, each instruction at most 500 characters.

## Linked tasks

On a pull or merge request, every review task is also given the issues the change was written for, so a reviewer can check that it does what was asked: a missed acceptance criterion, an unfinished subtask, a fix for the wrong case. They are the issues the platform links to it: on GitHub the pull request's closing issues (a closing keyword such as `Closes #12`, or an issue linked in the sidebar), on GitLab the issues the merge request closes; without any, the issue its branch is named after (`12-fix-login`, the name both platforms give a branch made from an issue). Only issues of the reviewed repository count, so a fork's pull request cannot pull another repository's issues into a review. With [`trackers`](./configuration#trackers) set, the Jira or TAPD tasks the title, description or branch name by key come after them, read through your tracker's MCP server. New in v0.11.0.

At most 3 issues, each with its title, state, labels, the first 4,000 characters of its body, its parent's title and first 1,500 characters (GitHub's parent issue, GitLab's epic) and up to 10 sub-issues by title; nothing is searched and no model chooses. The text goes into the part of the prompt every task shares, so it is cached once per run. A failed lookup (a token without access to issues) is a warning, and the review goes on. The report's `linkedTasks` lists what was given. `linkedTasks: false` in [`.ocra/config.json`](./configuration) or `--no-linked-tasks` turns it off.

## Project documents

With [`projectDocs`](./configuration#project-documents) set, each review task is also given the sections of the team's design documents that name its files, so a reviewer can check the change against the intended design. A document is split at its headings (levels 1 to 3, outside code blocks); a section names a file when it mentions the file's path, its name, or its directory (a generic one such as `src` alone does not count), and the path counts most. Each task gets at most 3 sections, the first 3,000 characters of each, and the headings of up to 10 more it can read; nothing is searched and no model chooses. A section that names none of a task's files adds nothing to its prompt. The report's `projectDocs` lists each section given and the bundles it went to. New in v0.11.0.

## Verdict

A fixed rubric over the final findings, not a model, decides the verdict, so the same findings always give the same verdict:

| Findings | Verdict |
|---|---|
| none | `approved` |
| suggestions, or fewer than three warnings | `approved_with_comments` |
| three or more warnings, or critical findings the verifier did not confirm | `minor_issues` |
| any critical finding the verifier confirmed | `significant_concerns` |

Every finding shows whether Verify **confirmed** it, was **unsure**, or did **not check** it (skipped, failed, or out of budget). Unconfirmed critical findings are shown as critical, marked unverified, and cap the verdict at `minor_issues`, so one model's unchecked claim cannot block a change. When verification of a critical finding failed or ran out of budget, the run is incomplete (exit code `3`) and never reads as a pass; with `verify: false` it is not. The judge can neither drop nor downgrade a confirmed critical finding; an attempt is ignored and listed as a warning. If the judge is disabled, has no `top` model or fails, findings are reported unjudged under the same rubric.

A run that reviewed nothing reaches no verdict: the terminal and the pull request summary say "Not reviewed" and why (when the model provider refused every call, whether a daily limit or a rate limit did it; in the JSON report those tasks carry `quota`: `daily_limit` or `rate_limit`), and the upload to ocra Cloud carries no verdict.

The verdict is **advice, not a security gate** ([why](./security#the-verdict-is-not-a-security-gate)).

## Modes

The default mode favors precision. `--ultra` trades cost for recall:

| | Default | `--ultra` |
|---|---|---|
| Reviewers | By risk tier and scope | Every reviewer at every tier, including tiers set with `reviewers.<id>.minTier` (files outside a reviewer's scope are still skipped, and `enabled: false` still applies) |
| Samples | One run per reviewer and bundle | Two runs, merged by fingerprint |
| Plan | Only for large bundles (5 or more files, or 40,000 characters of diff), and only for a reviewer that has a task per bundle | Every task. One short model call lists what to check first; if it fails, the task runs without it |
| Callers | At the `full` risk tier, as under `--ultra`; below it, reviewers search themselves | Uses of the symbols a bundle defines or changes, found outside the bundle, are shown to its reviewers |
| Judge | Drops speculation and nitpicks | Keeps them, marked *low confidence*; they do not count towards the verdict |
| Cost | Baseline | About twice or more, plus one plan call per task |

Verification works the same in both modes. [`depth`](./configuration#depth) names three presets over these settings: `quick`, `standard` and `deep`, which turns `--ultra` on.

Callers are found with [tree-sitter](https://tree-sitter.github.io/) for TypeScript, JavaScript, Python, Go, Rust and Java: a symbol counts as changed when any line of its body changes, not only its signature; changed signatures come first, eight symbols at most. A use is a name in code (comments and strings do not count), shown with the function or class it sits in, ten per symbol at most. Other languages fall back to definition patterns on changed lines and a whole-word search. What each file holds is cached by its content in `~/.cache/ocra/symbols/` (`$XDG_CACHE_HOME/ocra/`, `%LOCALAPPDATA%\ocra\` on Windows, or `$OCRA_CACHE_DIR`, which a CI job can keep between runs, as the [GitHub Action](./github) does); deleting it costs only parsing time.

With `--scip <file>`, a [SCIP](https://github.com/scip-code/scip) index of the repository (from `scip-typescript`, `scip-java`, `scip-python` and the like, run at the repository root) answers first: a symbol it knows gets exactly the uses the compiler resolved, so two methods named `run` no longer share callers. The index describes the revision it was built from, typically the main branch; a use whose line no longer names the symbol is left out, and a symbol it does not know (new in the change, or in a language it does not cover) is searched for as above. An index that cannot be read (512 MB at most) gives one warning and the review goes on without it. ocra never builds an index itself.

With `--graph <file>`, a code graph that [`ocra graph`](./cli#ocra-graph) wrote answers next: the uses of the name in every file of the revision it describes, without a search per review. It matches names as the search does, so it does not keep same-named symbols apart. Like an index, it describes its own revision: lines that no longer name the symbol are left out, and a symbol in a file it does not hold is searched for.

## Reviewers and tools

A reviewer is an agent with a focused prompt, its own rules, and a scope that tells the matrix where to run it:

| Reviewer | Looks for | Runs at | Skips |
|---|---|---|---|
| `correctness` | Logic errors, broken contracts, error handling | every tier | nothing |
| `security` | Exploitable issues reachable from untrusted input: injection, authorization, secrets, crypto, unsafe parsing, CI | `lite` and `full` | documentation, tests |
| `performance` | Measurable regressions on paths that matter: complexity, N+1, blocking work, memory | `full`; `lite` on a bundle with a file on a hot path, such as a cache, query, queue, pool, stream or cluster | documentation, tests, config data, CI workflows |
| `docs` | Documentation the change makes wrong: a removed or renamed flag, key, endpoint or default that the README, docs or help text still describe (light model) | `lite` and `full` | tests |
| `agents-md` | Statements in `AGENTS.md` the change makes false: commands, layout, module responsibilities, required tools and variables (light model; only when the repository has `AGENTS.md`) | `lite` and `full` | tests |

`docs` and `agents-md` compare the change with documents outside it, so they get the change as a whole rather than bundle by bundle: one task, or a few when it has more than 20 files or 120,000 characters of diff. `security` and `performance` take neighbouring bundles together, up to the bundle size limits (10 files, 120,000 characters), keeping sensitive paths in tasks of their own. Each reviews only its own domain and states what not to flag. Reviewers can only read: `read_file`, `read_diff` and `code_search` answer from the revision under review (a commit in range or commit mode, not your working tree), `read_learning` answers from the team's learnings ([Rules](./rules#ocralearnings)), and findings go through `report_finding`. Answers are capped (2,000 characters per line, 50,000 per answer, 2 MB per file read), so a minified bundle cannot flood the context. Reviewers cannot edit files, run commands or browse the web.

## Anchoring

Models are unreliable with line numbers, so they quote code, and ocra resolves the quote:

1. normalized match in the file's changed hunks;
2. match in the whole file;
3. match in another changed file (the model named the wrong file), only for a whole-line quote found in exactly one place;
4. a light model is shown the finding and the file's diff and answers with the lines it means, which are matched like any quote (one small call per unmatched finding);
5. otherwise the finding stays attached to its file, as a file-level finding.

A finding that resolves to another changed file, outside the reviewer's bundle, is kept: a bug often shows where a change in one bundle meets a change in another. When the reviewer of that file reports the same issue, the run keeps one copy. A finding on a file outside the change, or on a file an incremental review left out, is dropped with a warning.

Whole lines are matched first. Part of a line counts only when it is at least 12 characters long and only one line contains it, so a fragment like `err` does not land on the first line containing it. A quote that fits several places equally well (three identical `return err;` lines) stays at file level and is counted under `anchoring.ambiguous`. The JSON report (`--format json`, a session's `report.json`) gives `anchoring` for the run: findings per method (`hunk`, `file`, `cross_file`, `relocated`, `file_level`), the ambiguous ones, and the number of relocation calls.

## Robustness

- A per-task and a whole-run timeout, enforced even if a model stops responding. A task with no progress for five minutes (no new step, text or tool call) is stopped earlier and handed to the next model in the chain.
- A failed task never fails the run; its files are reported as `failed`.
- Model failback chains per tier, with a circuit breaker per model (open after repeated failures, half-open probe after a cooldown).
- Rate limits with a short retry-after (up to 90 seconds) pause that model for every task, then retry; one without a retry-after pauses it for 15, 30, then 60 seconds. Limits that arrive during a pause count as that pause. On the `direct` runtime the refused request is sent again after the pause and the task keeps the steps it has taken. A daily limit, a longer wait, or a limit after three pauses in a row takes the model out of the chain for the rest of the run.
- Every review agent is capped at 30 steps, since each step resends the conversation; most tasks finish in about 15.
- Every context source in a review prompt has a bound, so a large change cannot crowd out the code: the changed-files list holds 150 files, accepted findings the last 20 on the bundle's files, the repository's rules 12,000 characters, and task and learning titles 300 characters; smaller inputs render in full. `ocra review --plan --format json` gives each task's first prompt by source (tokens, cuts and duplicated lines), and [`--without`](./cli#ocra-review) leaves sources out to measure what each is worth. New in v0.12.0.
- An agent that stops early (no done signal, no answer, steps to spare) is told once, in the same session, to finish its remaining files; the progress line says "resumed after stopping early".
- An agent that still ends without the done signal (at the step cap, or after stopping again) gets one more turn in the same session in which it can only report findings and finish, to report what it has already confirmed. The turn is at most two model requests and counts toward cost, the spend limit and the timeouts; it does not start once the run is cancelled or past its spend limit, and a turn that fails keeps what it reported without failing the task. The progress line says "wrap-up turn reported N finding(s)", and the task in the [JSON report](./cli#json-output) has `wrapUp`.
- A task that ends without the done signal (all 30 steps used, a [declared context window](./providers#a-model-with-a-small-context-window) filled, or stopped again) does not count as a review: its files are reported as partly reviewed (`incomplete`), the run exits `3`, and the next review of the pull or merge request includes them. The wrap-up turn does not change that: it reports what the agent already confirmed and reads nothing more.
