## ocra init

Writes `.ocra/config.json` for the repository you are in (with `--github`, also `.github/workflows/ocra.yml` and `.github/workflows/ocra-commands.yml`) and prints what is left to do. It calls no model or network service, never runs `gh`, and runs `git` only to find the repository's root (`git rev-parse --show-toplevel`).

```bash
ocra init                          # .ocra/config.json for the key in your environment
ocra init --github                 # also the GitHub workflow, safe for pull requests from forks
ocra init --github --same-repo-only
ocra init --provider anthropic     # a provider whose key is not in this shell
```

| Option | Meaning |
|---|---|
| `--github` | Also write `.github/workflows/ocra.yml`, the [fork recipe](./github#pull-requests-from-forks) on `pull_request_target`: members' and collaborators' pull requests are reviewed on every push, others' each time a maintainer adds the `ocra-review` label; only the base branch is checked out, and nothing from the pull request runs. And `.github/workflows/ocra-commands.yml`, the [comment workflow](./github#the-comment-workflow): `@ocra review` reviews a pull request again, any other `@ocra` mention is answered |
| `--same-repo-only` | With `--github`, the plain [`pull_request` workflow](./github#github-action) instead. It skips pull requests from forks, which get no secrets there |
| `--provider <name>` | `gemini`, `anthropic`, `openai` or `openrouter`, in place of the key found in the environment |
| `--force` | Replace existing files. Without it, an existing file is kept, and ocra init says so |

**The model.** Without `--provider`, ocra init takes the first of `GEMINI_API_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` and `OPENROUTER_API_KEY` that is set, and names any other it found; OpenRouter is chosen only when no other key is there. It writes one model per tier:

| Provider | `top` | `standard` | `light` | Runtime |
|---|---|---|---|---|
| `gemini` | `google/gemini-3.1-pro-preview` | `google/gemini-3.5-flash` | `google/gemini-flash-lite-latest` | `opencode` |
| `anthropic` | `anthropic/claude-opus-5-5` | `anthropic/claude-sonnet-5-5` | `anthropic/claude-haiku-4-5` | `opencode` |
| `openai` | `openai/gpt-6-sol` | `openai/gpt-6-sol` | `openai/gpt-6-luna` | `opencode` |
| `openrouter` | `router/openrouter/free`, OpenRouter's router over its [free models](./providers#free-models-through-openrouter) | the same | the same | `direct` |

For OpenRouter it warns that quality varies, that free models are not for private code, and that without credits a large review may run out of daily requests.

When `--github` keeps an existing configuration whose active model chains use declared providers and require just one supported key, it uses that secret for the new workflows even if its value is not in your shell. Disabled reviewers and declared endpoints that need no key do not affect this choice. If the configuration extends another file or the key cannot be inferred, it falls back to the shell. An explicit `--provider` overrides this choice.

**The runtime.** Only OpenRouter, tested live on the `direct` runtime, is set up on it: the configuration sets `"runtime": "direct"` and declares the endpoint at a price of 0, and the workflow passes `opencode: false`, so ocra installs in about 11 MB instead of 175 MB. The others stay on the default `opencode` runtime, with catalog models OpenCode prices itself; ocra init links to [Choosing the runtime](./providers#choosing-the-runtime). When `--github` keeps an existing configuration that does not set `direct`, the workflow installs OpenCode.

For Gemini, the file is:

```json
{
  "$schema": "https://raw.githubusercontent.com/ocrahq/Open-CR-Agent/main/docs/schema/config.v1.json",
  "models": {
    "top": "google/gemini-3.1-pro-preview",
    "standard": "google/gemini-3.5-flash",
    "light": "google/gemini-flash-lite-latest"
  }
}
```

The key is never written; OpenCode reads it from `GEMINI_API_KEY`. Change the models like any [configuration](./configuration).

**The workflows** are the [GitHub](./github) recipes with the key as a secret, `--max-cost-usd 2` per review, `opencode: false` on the direct runtime, and the Action pinned to this release's commit (`actions/checkout` by commit too). `ocra init --github` then prints:

```text
Wrote .ocra/config.json: Gemini models through GEMINI_API_KEY, on the OpenCode runtime.
  OpenCode makes the install about 175 MB; to switch to the 11 MB direct runtime later, see https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/manual/en/providers.mdx#choosing-the-runtime
Wrote .github/workflows/ocra.yml: pull requests from members are reviewed on every push, anyone else's once each time a maintainer adds the ocra-review label.
Wrote .github/workflows/ocra-commands.yml: a comment @ocra review by someone who can write reviews the pull request again, and ocra answers any other @ocra mention in its thread.

Next:
  1. Store the key as a repository secret (gh asks for its value):
       gh secret set GEMINI_API_KEY
  2. Create the label that starts a review of an outside pull request:
       gh label create ocra-review --description "Review this pull request with ocra"
  3. Commit .ocra/config.json, .github/workflows/ocra.yml, .github/workflows/ocra-commands.yml, and merge them into the default branch:
       ocra reads its configuration from a pull request's base branch,
       and GitHub runs comment workflows from the default branch.
```

In a private repository, remove `persist-credentials: false`, as the workflow's comment says. ocra init writes to the repository root from any subdirectory and never through a symbolic link. Outside a Git repository, or when it can't choose a provider, it exits `2` and writes nothing.

## ocra review

Reviews code changes in the current Git repository.

```bash
ocra review [options]
```

| Option | Meaning |
|---|---|
| *(none)* | Review uncommitted changes: staged, unstaged and untracked files |
| `--from <ref>` | Review `--to` since it diverged from `<ref>` (merge base) |
| `--to <ref>` | End of the range; defaults to `HEAD`; requires `--from` |
| `--commit <sha>` | Review a single commit against its parent |
| `--format text\|json\|sarif` | Output format; default `text`. `sarif` writes [SARIF 2.1.0](#sarif-output) |
| `--output <file>` | Write the result to a file instead of stdout. The file is replaced whole; a symbolic link at that path, or at a directory on the way inside the repository, is refused (exit `2`, before any model call), and so is a path that exists but is not a regular file. So `/dev/stdout`, a named pipe and process substitution (`>(…)`) do not work: leave `--output` out to write to stdout |
| `--pr <number>` | Review a GitHub pull request; see [GitHub pull requests](./github) |
| `--repo <owner/name>` | Repository of `--pr` (default: `GITHUB_REPOSITORY` or `origin`) |
| `--mr <iid>` | Review a GitLab merge request; see [GitLab merge requests](./gitlab) |
| `--project <id\|path>` | Project of `--mr` (default: `CI_PROJECT_ID` or `origin`) |
| `--publish` | With `--pr` or `--mr`: post the review to the pull or merge request |
| `--full` | With `--pr` or `--mr`: review every file, not only what changed since the previous review |
| `--max-cost-usd <n>` | Spend limit for the run. At 80%, review tasks still running stop, keeping what they found; their files count as not reviewed (exit `3`), unless the task had already finished its review. Verification and judging use the rest; past it, remaining findings are *not verified* and cannot block. Tasks report spend about every 10 seconds, so a run can overshoot by that much per task plus its step in progress. Tasks run bundle by bundle, those on sensitive paths (`auth/`, CI workflows and the like) first, so a limited run finishes some files, the riskiest first; with `--pr` the next review continues with the rest |
| `--plan` | Free, no model call: show selected and excluded files, bundles, review tasks and each first prompt's size (with the plan call a task makes under `--ultra`, or for a large bundle when its reviewer has a task per bundle). Where a task's chain is known, estimate those prompts' input cost at the first model's price, per task and in total: a [declared provider's](./providers#your-own-endpoint) price, `input unpriced` for a price of 0 or ocra Cloud, else `input price unknown`. Output, later turns, verification and judging are not estimated. The JSON plan also gives each task's first prompt by source (`context`): tokens, texts held to a limit or lists cut short (`cut`), and lines an earlier source of the same prompt already holds (`duplicateTokens`). Light-model grouping is skipped, so a large change shows one file per bundle (by directory past 20 files). With `--pr` or `--mr` it plans what the review would cover: only what changed since the previous review when it can tell, as the review does, and it says so (`--full` plans everything). No session log |
| `--import-sarif <file>` | Add the results of an analyzer's SARIF 2.1.0 log (Semgrep, CodeQL and others) to the review; repeatable. See [SARIF input](#sarif-input). Not with `--plan` |
| `--no-linked-tasks` | With `--pr` or `--mr`: do not give the reviewers the [issues the change is linked to](./how-it-works#linked-tasks) (`linkedTasks` in configuration) |
| `--guidelines <scope>` | Which sections of `AGENTS.md` each review task is given: `all`, `matched` or `reviewer` (see [`guidelineScope`](./configuration)); overrides the configuration |
| `--without <sources>` | Leave these context sources out of every review prompt (comma-separated), to measure what each is worth against a run with it: `description` (the change request's description; the title stays), `changed_files`, `linked_tasks`, `guidelines` (also skips reviewers that need them), `rules` (the repository's, not the reviewer's own), `accepted`, `learnings`, `project_docs`, `callers`, `analyzer`. Recorded in the configuration hash. `--plan` shows the prompts without them |
| `--sarif-evidence <file>` | Show the reviewers an analyzer's SARIF 2.1.0 results on and near the change as evidence to confirm, not as findings; repeatable. See [SARIF as evidence](#sarif-as-evidence) |
| `--graph <file>` | Find the callers of changed symbols in this [code graph](#ocra-graph), after `--scip` and before searching. Not with `--plan` |
| `--scip <file>` | Find the callers of changed symbols in this [SCIP](https://github.com/scip-code/scip) index first (see [Modes](./how-it-works#modes)). Not with `--plan` |
| `--ultra` | Favor recall over cost; see [Modes](./how-it-works#modes) |
| `--depth <depth>` | `quick`, `standard` or `deep`: a preset of the settings the configuration leaves unset; overrides [`depth`](./configuration#depth) |
| `--no-ultra` | Do not use `--ultra`, even where the configuration or your ocra Cloud account turns it on ([`ultra`](./configuration#execution)) |
| `--min-inline-severity <severity>` | With `--publish`: post only findings at least this severe (`critical`, `warning` or `suggestion`) as inline comments; overrides [`minInlineSeverity`](./configuration#inline-comments) |
| `--max-inline-comments <n>` | With `--publish`: post at most `n` (0 to 1000) of the review's findings as inline comments; overrides [`maxInlineComments`](./configuration#inline-comments) |
| `--fixes` | Propose checked fixes for findings, as [`fixes: true`](./configuration) does |
| `--reviewers <ids>` | Run only these reviewers, comma-separated (for example `security`) |
| `--temperature <n>` | Sampling temperature, 0 to 2; overrides `sampling.temperature` ([Configuration](./configuration#execution)) |
| `--seed <n>` | Sampling seed where runtime and provider support one (not `opencode`); overrides `sampling.seed` |
| `--resume <run-id>` | Retry an earlier run of this review without paying again for what it finished: its completed tasks are reused when their inputs are unchanged (same commits, configuration, prompts, ocra version and sampling), and only the rest run; a task that failed or was cut off before it finished (partly reviewed) runs again. Reads [the session](#sessions) `.ocra/sessions/<run-id>`, and only what ocra on this machine wrote there: a session from another machine or user, or one that came with the change, is refused (exit `2`), and lines added to it are ignored with a warning. A task that cannot be reused runs and a warning says how many. Reused tasks cost nothing, so a spend limit never keeps them out; they show `reusedFrom` in the [JSON output](#json-output), and the run's `usage` is only what it paid. Not with `--plan` |
| `--config <file>` | Use this configuration file instead of `.ocra/config.json` (the base branch's with `--pr` or `--mr`); it applies with `--no-repo-config` too. See [Configuration](./configuration) |
| `--no-repo-config` | For code you do not trust: ignore `.ocra/config.json` and its plugins (with `--pr`, the base branch's too); models come from `OCRA_MODEL_*` or `--config`; memory, rules and `AGENTS.md` from the `--from` commit, or none |
| `-h, --help` | Show help |

`--commit` cannot be combined with `--from` or `--to`.

### Progress

Progress goes to stderr, so `--format json` on stdout stays machine-readable:

```text
[ocra] Reviewing: Working tree changes
[ocra] 4 file(s) selected, 1 excluded · risk tier: lite
[ocra] 2 bundle(s) (grouped)
[ocra] 2 review task(s)
[ocra] correctness-1 started: auth session handling (2 file(s))
[ocra] correctness-1 reviewing with google/gemini-3.5-flash
[ocra] correctness-1 google/gemini-3.5-flash: 3 step(s), 3 tool call(s) (read_file 2, task_done 1), 19558 in / 118 out / 0 reasoning tokens, $0.0062
[ocra] correctness-1 completed in 5.9s · 0 finding(s)
```

When a model is quiet for 30 seconds, ocra prints `Model is thinking...`.

### Exit codes

| Code | Meaning |
|---|---|
| `0` | Review finished; verdict `approved`, `approved_with_comments` or `minor_issues` |
| `1` | Verdict `significant_concerns`: at least one critical finding the verifier confirmed (unconfirmed ones give `minor_issues` and `0`). The verdict is advice and can be influenced by the change under review; see [How it works](./how-it-works#verdict). With `--pr`, a maintainer's `@ocra override` for the head commit turns this into `0` ([GitHub](./github#overriding-a-blocking-verdict)) |
| `2` | Usage, Git or configuration error, or no review task completed. The error line names its code, as in `ocra [VCS_REF_UNKNOWN]: Unknown commit: nope` ([codes](./embedding#errors)) |
| `3` | Review incomplete: a selected file was not reviewed (task failed, timed out, hit the spend or task limit, or no reviewer covers it) or only partly (its reviewer used all 30 steps, or stopped, before the done tool; the message says what to do), or a critical finding could not be verified. Wins over `1`, so CI cannot pass an incomplete review |
| `130` | Interrupted with Ctrl-C or SIGTERM; the partial report is still printed and nothing is published |

### JSON output

`--format json` prints the full report, the same shape as a session's `report.json`:

- change request, risk tier, verdict, summary;
- coverage per changed file: reviewed, failed, unreviewed (no task started), incomplete (task ended without the done tool; `ended`: `step_cap`, `context_window` or `stopped_early`), unchanged since the previous review, or excluded with a reason; for pull requests, incremental or full and why (`scope`);
- bundles, task outcomes, reviewer/bundle pairs the matrix skipped;
- `refuted` (findings verification dropped, with the reason), `unverifiedCriticals` (critical findings it failed to check), `judgement` (what the judge merged, dropped or recalibrated), `fixes` when fixes were on (`asked`, `proposed`, and each `rejected` finding's `fingerprint` and `reason`: `declined`, `failed`, `stale`, `unchanged`, `unsafe`, `too_large`, `no_parser` or `syntax`);
- findings, and `rereview`: earlier findings fixed, not reproduced, not re-checked, unchanged or dismissed, each with its `reviewer` when recorded;
- `remembered`: findings a memory accepted, with `source` (`repository` for `.ocra/memory.json`, `account` for your [ocra Cloud memory](#memory-in-your-ocra-cloud-account)); a maintainer's override in `changeRequest.override`;
- `learnings`: each [learning](./rules#ocralearnings) a task was given, with its `title`, `critical`, `source` and the `bundles` it went to;
- `projectDocs`: each [project document section](./how-it-works#project-documents) the tasks were given, with its `path`, `heading` and the `bundles` it went to; absent when none was;
- `linkedTasks`: each [linked issue](./how-it-works#linked-tasks) the tasks were given, with its `tracker`, `key`, `url`, `title`, `state`, `labels` and whether its text was `cut`; empty when none is linked, absent for a local review or with the switch off;
- `mergeChecks`: each [pre-merge check](./how-it-works#pre-merge-checks) with its `id`, `instruction`, `outcome` (`passed`, `failed` or `inconclusive`) and `reason`, in the configured order; absent when none is configured;
- `analyzerEvidence`: each tool whose results tasks were given with [`--sarif-evidence`](#sarif-as-evidence), with its `version`, the number of `results` and the `bundles` they went to;
- `inline`, with an [inline comment policy](./configuration#inline-comments): its `minSeverity` and `maxComments`, and in `held` each finding it keeps out of the inline comments (`fingerprint`, `reason`: `below_floor` or `over_cap`), in the order it ranked them; the findings themselves stay in `findings`;
- token usage and cost; `spendLimit` with a spend limit (`reached`: `review` when review tasks stopped, `total` when it all ran out); warnings.

The format is a contract (`"version": 1`): later releases only add optional fields and new values of a listed set, or change the version. Treat an unknown coverage status as not reviewed.

**Each finding** has `fingerprint` (stable across runs; `ocra memory add` takes a prefix), `reviewer`, `category`, `severity`, `verification` (`confirmed`, `uncertain` or `unchecked`), `file`, `lines` (`{ start, end }`, absent when not tied to lines), `inDiff`, `status` (`new`, or `unfixed` when reported before), `title`, `body`, optional `suggestion`, optional `fix` (`{ startLine, endLine, replacement }`, set by the [Fix stage](./how-it-works) when it is on, and offered as a [committable suggestion](./github#committable-suggestions)), `evidence`, optional `rule` (`{ kind, id }`: the [repository rule](./rules) or learning, `kind` `rule` or `learning`, that the finding applies, when the reviewer named one it was given), `code` (the quote), `lowConfidence` under `--ultra`, `preExisting` when Verify found the problem already in the code the change touches, and `provenance` (its `task`, and `model` when known). Each task in `tasks` has its `usage` (tokens and cost; a finding costs what its task did) and, if it ended without the done tool, `ended`: its files count as partly reviewed. A task whose reviewer was then given the [wrap-up turn](./how-it-works) also has `wrapUp` (`{ findings }`, how many it reported there); its files still count as partly reviewed.

**The report's `provenance`** records:

- `ocraVersion`;
- `promptHash`: of the system prompts this configuration sends (reviewers and helper stages; never the change);
- `configHash`: of the effective configuration plus `--reviewers`, `--ultra` and `--max-cost-usd`; without sampling or secrets (keys are only named);
- `sampling`: the `temperature` and `seed` applied, and in `notApplied` those that could not be;
- `agents`: per enabled reviewer and the `verifier`, `judge`, `helper` and `writer` roles, its `tier`, chain in `models` (its [own](./configuration#models-per-agent) or its tier's), [`effort`](./configuration#effort) when set, `applied` (absent when it made no call), and `notApplied` sampling settings;
- `rules`: each path rule's `id` (what a finding's `rule` names), `path`, `rule` and `source` (`repository` for `.ocra/rules.json` and `.ocra/rules.md`, `shared`, `account` or `plugin`);
- `accountSettings`: the [account settings](./configuration#account-settings) `version`, when signed in.

The report's [JSON Schema](https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/schema/report.v1.json) (draft 2020-12) is generated from the code and tested against it; `reportJsonSchema()` in `@open-cr-agent/core` returns it.

**`--plan` JSON** is versioned the same way and has its own [JSON Schema](https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/schema/plan.v1.json): change request, risk tier, `scope` with a previous review (`incremental` with `since`, or `full` with `reason`, as in the report), selected and excluded files, bundles, tasks (estimated prompt size, `models`, `effort` when set, `inputCost` when the chain is known: `model`, the chain's first, and `status` `priced` with `usd`, `unpriced` or `unknown`), skipped pairs, `groupingSkipped`, `promptTokens` (total), `inputCost` when any task has one (`usd` over priced tasks and the count per status), warnings, `settings` (each `key`, `value`, absent for a default, and `source`), and `accountSettings` when read.

### SARIF output

`--format sarif` writes the review as a [SARIF 2.1.0](https://docs.oasis-open.org/sarif/sarif/v2.1.0/sarif-v2.1.0.html) log, the format code scanning and security dashboards read. To upload it to GitHub, see [Code scanning](./github#code-scanning).

- **Rules and results.** One rule per reviewer category (`correctness`, `security` and so on) and one result per finding:
  - level from severity: `critical` is `error`, `warning` is `warning`, `suggestion` is `note`;
  - message: the title, body and suggestion; region: the finding's lines;
  - `partialFingerprints` holds its fingerprint (`ocra/v1`);
  - a finding's `fix` goes in `fixes`, replacing its whole lines;
  - reviewer, severity, verification, status, task and, when known, model are properties.
- **Findings without lines** apply to the whole file: no region.
- **Carried-over findings.** In a pull request, still-open findings from an earlier review in files this run did not review again are results under the rule `ocra-carried-over`, marked `unchanged` and without lines.
- **Incomplete reviews.** A review that exits `3` is marked unsuccessful; the count of files not reviewed and the warnings are notifications; the verdict, risk tier, files not reviewed and cost are run properties.

Text from the change and models stays text: brackets and backslashes are escaped, braces doubled, and web addresses broken with a zero-width space. `--plan` cannot write SARIF.

### SARIF input

ocra runs no analyzer: run Semgrep, CodeQL or another tool and pass its SARIF 2.1.0 log with `--import-sarif <file>` (repeatable; 20 MB each at most). Each run in the log becomes a task `sarif-<tool>-<n>`, with the tool as reviewer and no cost; its findings name it in `provenance.task`.

- **Only results on the change are kept**: on a reviewed file, on lines inside a diff hunk. The rest, and results without a file and lines, outside the repository or without a message, are counted in a warning. At most 200 results per run.
- **Severity** from the result's level, else the rule's default: `error` is `critical`, `warning` is `warning`, `note` and `none` are `suggestion`. Title: the rule's short description, name or id. Body: the message, the rule's description, and the tool, version, rule and help link.
- **The quote decides the lines.** The result's snippet, or the file's lines, is anchored like a reviewer's quote; one that no longer matches makes the finding file-level.
- **Then it is a finding like any other**: memory and dismissals apply, Verify checks it, the judge merges it with reviewers' duplicates, and it counts toward the verdict.

Tested with Semgrep 1.178.0's log; other tools' logs follow the same standard.

### SARIF as evidence

`--sarif-evidence <file>` (repeatable; 20 MB each at most) hands a log to the reviewers instead: a result is a lead the reviewer checks in the code, not a finding. It suits linters and rule sets too noisy to post as they are. The same log may go to both flags.

- **Results on and near the change**: on a reviewed file, on a diff hunk's lines or within 10 lines of one. A result two logs repeat is shown once.
- **At most 20 per bundle**, on the change first, then `error` before `warning` before `note`, results tagged `security` first, then by file and line; each message is cut to 300 characters. What is left out is counted in a warning.
- **Every reviewer of the bundle sees those on its files**, except that a result tagged `security` goes only to the security reviewer when one reviews that file (to every reviewer when none does). One line each with the file and lines, tool, rule, severity and whether it is on or near the change, and is told to report one only when it is in its focus and the change introduces or worsens it.
- **What a reviewer reports from one is its own finding**, verified, judged and counted like any other. A result no reviewer confirms is not reported; with `--import-sarif` it would have been.
- **The report says what was given**: [`analyzerEvidence`](#json-output). Prompts grow only when a log is given, so a run without the flag reviews exactly as before.

### Sessions

Every review (not `--plan`) writes `.ocra/sessions/<id>/events.jsonl` (one event per line, as the run progresses) and `report.json`. The run id `<id>` is in the first progress line, the JSON report (`runId`), the summary comment (Coverage and cost) and the SARIF log (`automationDetails.id`, `ocra/<id>`). Each task attempt's event records in `attempt` the files the reviewer read, its searches and its final text (bounded), so you can tell a file never opened from one read without findings; none of it goes into the report. Beside them, `trace.json` lays the run out in time: when each stage started, each task and each of its attempts (model, steps, calls per tool, files read, how many searches, tokens, cost, time, how it ended), every plain model call (plan, grouping, walkthrough, Verify, Judge, relocation) with its model, time and spend, and where each reported finding ended up: kept, outside the review, refuted by Verify or merged or dropped by the judge, with their reasons, or filtered. It holds no code, prompt, answer or searched text, so it can go to a reviewer as the review's evidence. The report object (`report.trace` in the [library](./embedding)) carries it too; the JSON report does not. The directory has its own `.gitignore`.

Each line of `events.jsonl` ends with a `seal`: an HMAC keyed by a secret of yours that ocra makes on first use in `~/.config/ocra/session-key` (`$XDG_CONFIG_HOME/ocra/`, or `%APPDATA%\ocra\` on Windows), readable only by you. `--resume` reads only lines with a valid seal, so it resumes a session only on the machine and account that wrote it; deleting the key makes earlier sessions impossible to resume, nothing else. If ocra cannot make or read the key, a review warns and its session cannot be resumed; a key file it cannot read (another user's, say, after `sudo ocra`) is left as it is.

## ocra graph

Writes the code graph of a commit: each source file's definitions and the lines its names are used on, as [How it works](./how-it-works#modes) describes, for `ocra review --graph`. It reads git objects only and runs nothing from the repository.

```bash
ocra graph --out ~/.cache/ocra/graph.json             # HEAD
ocra graph --out graph.json --rev origin/main         # another commit
ocra graph --out graph.json --cloud                   # start from ocra Cloud's graph
```

An existing graph at `--out` is updated: a file whose content it already holds is not read again, so after the first run an update costs only the files that changed. A graph it cannot read (another format, or more than 512 MB) is built again with a warning. Files over 1 MB, and files that are not UTF-8 text, are left out. The graph holds names, kinds and line numbers, never code. Build it on the main branch after each push, keep the file between runs (an Actions cache, for example), and pass it to reviews of pull requests against that branch.

With `--cloud`, the graph starts from the newest one a self-hosted ocra Cloud server built of the repository's default branch (it keeps one per push, as `CODE_GRAPH` sets), instead of from the file at `--out`: only the files the commit changed since are read and parsed. The server is the one `ocra login` signed in to, and the repository is the one whose host and path match `origin`'s. When there is no graph to use (not signed in, a server that keeps none, a repository it does not keep, a graph of another format), ocra warns and builds from the file at `--out`, or from scratch, as without `--cloud`; the command still succeeds. The graph is read only by the parser: nothing from it runs.

## ocra learn

Drafts [learnings](./rules#ocralearnings) from the fix commits in your history, so reviews remember what the team already fixed once:

```bash
ocra learn mine                    # the 20 newest fixes on HEAD's first-parent line
ocra learn mine --max 50           # more of them
ocra learn mine --max-cost-usd 0.5 # stop drafting at a spend limit
```

A fix is a commit whose subject says so (`fix:`, `revert`, "fixes", "bug") and that changes at most 5 source files; docs, tests and data files are left out. For each one, one call on the helper role reads its subject, message and diff (cut to fixed sizes, as data) and drafts a title, a body, symbols and keywords, or answers that the fix holds no lesson for other changes. ocra then checks the draft without a model:

- symbols must appear in the diff; the paths are the directories the fix touched, never the model's;
- a fix an existing learning records in `source.ref` is not drafted again, and a draft that covers a path of an existing learning with mostly the same title words is dropped; so are the learnings on origin's `ocra/learnings-*` branches (the 20 newest), which an open or closed proposal leaves there: what waits for review is not drafted twice, and what a person closed without merging is not drafted again until its branch is deleted;
- the draft is kept only if the selection would give it to the fix it came from.

Each kept learning is written to `.ocra/learnings/<title>.md` in the working tree, with `source: { kind: fix-commit, ref: <sha> }` and never `critical`, and its path printed. The name is the title in lowercase letters, digits and hyphens, at most 60 characters and ending at a whole word. Read, edit and commit them like any file. The last line counts what was written, declined, duplicate or left by the spend limit, and what the calls cost. `ocra learn` uses the runtime and models of `.ocra/config.json` (the helper role's), or of the file `--config <file>` names in its place, reviews nothing and writes no session.

### From accepted findings

`ocra learn feedback` drafts from the findings the team accepted with [`ocra memory add`](#ocra-memory), newest first, read from `.ocra/memory.json` at the same revision a review reads it. Each call is given the finding's title, the reason the team gave and the file it is in, and writes a lesson only when the reason holds beyond that one finding (a pattern that is intended here, a risk handled elsewhere); the learning then tells reviewers what not to report there. Its paths are the file's directory, its `source` is `{ kind: review-feedback, ref: <finding id> }`, and the same checks, limits and `--propose` apply as for `mine`.

`ocra learn feedback --pr <n>` (or `--mr <iid>`, with `--repo` or `--project` as for a review) also drafts from the findings of the pull or merge request's review that someone with write access declined in their thread: a reply that declines it (`@ocra dismiss`, "won't fix", "by design"), or their last reply in a thread someone with write access resolved. Each call is given the finding's title, what they said and the file as the change has it. The author may decline here too, as with `@ocra remember`: nothing leaves the verdict, and `--propose` leaves the learning to a pull request. A reply someone else edited, a reply by someone without write access, and a thread nobody answered give nothing.

### From documents

`ocra learn import docs/postmortems/*.md` drafts from the team's own writing: postmortems, guidelines, design notes. Each `##` section of each Markdown file (the text before the first one under the document's title) is one candidate, given with up to 5 repository files it names by path (`src/db/pool.ts`), read at the trusted revision. A section that names no file of the repository is not drafted: no review could be given it. A lesson is written only for what a reviewer can check in a diff of those files; its paths are their directories and its `source` is `{ kind: document, ref: <file>#<section> }`. A file is at most 256 KB.

### From pull request notes

`ocra learn remember --pr <n>` (or `--mr <iid>`, with `--repo` or `--project` as for a review) drafts from each [`@ocra remember <note>`](./github#asking-ocra-to-remember) on the pull or merge request by someone with write access, unedited by anyone else (at most 20). Each call is given the pull request's title, the note, and the files of its diff the note names by path, else the whole diff when it has at most 5 files; a note about neither is not drafted. Configuration comes from the base, as for a review. A note asking for anything but a lesson (to approve, to change settings) is declined. Its `source` is `{ kind: remember, ref: <repository>#<number>/<comment id> }`.

### Writing them back by pull request

`ocra learn mine --propose` writes nothing to the working tree: it opens a GitHub pull request or a GitLab merge request with the kept learnings instead, one commit on a new `ocra/learnings-<time>` branch from the default branch, made through the platform's API (nothing is pushed from the checkout). `--repo <owner/name>` picks GitHub and `--project <id|path>` GitLab; without either, the platform is that of `--pr` or `--mr` (with `remember`), else the CI it runs in (GitHub Actions or GitLab CI), else origin's host (github.com or gitlab.com), else the one platform a token is set for. On GitHub it needs `GITHUB_TOKEN` (or `GH_TOKEN`) with contents and pull request write access; the repository is `--repo`, else `GITHUB_REPOSITORY`, else origin's. On GitLab it needs `GITLAB_TOKEN` with the api scope and the Developer role, sent where a [review](./gitlab) sends it; the project is `--project`, else `CI_PROJECT_ID`, else origin's. The change request lists each learning and where it came from, and the command prints its address.

The pull request is set to merge once its checks pass (squash, else rebase, else a merge commit, whichever the repository allows); when nothing is required of it, it is merged at once. With `"learnings": { "requireReview": true }` in `.ocra/config.json`, or `--require-review` on the command line, it is left for a person to review and merge. When the repository has auto-merge turned off, or GitHub refuses, ocra warns and leaves the pull request open. A pull request opened with a workflow's own `GITHUB_TOKEN` starts no workflows, so required checks never report on it: use a GitHub App or personal token if your branch protection requires checks ([the Action](./github#learning-from-history-and-notes) leaves such a pull request for a person).

On GitLab the merge request is set to merge when its pipeline succeeds, with the project's merge method, and deletes its branch when merged. GitLab merges at once a merge request with no running pipeline, so ocra first waits up to about 15 seconds for the pipeline the new branch starts; with none by then, nothing is required of it and it is merged at once. When the project allows no merge without a successful pipeline and has none, or GitLab refuses, ocra warns and leaves the merge request open. A commit made with `GITLAB_TOKEN` starts the project's pipelines as any push does.

`ocra learn check` makes no model call: it lists each learning with a path that matches no file at HEAD, as `<id>: no file matches <paths>`, and exits 1 when there is one. After a module moves or is renamed, reviews no longer give such a learning by that path, only by its symbols and keywords; edit its paths. Run it in CI to catch that. ocra Cloud's Learnings page shows the same on the default branch.

## ocra reply

Answers a comment that mentions `@ocra` on a pull or merge request, in its thread:

```bash
ocra reply --pr 7 --comment 2154873301            # a conversation comment
ocra reply --pr 7 --comment 1891230045 --inline   # a comment on a line of the diff
ocra reply --mr 12 --comment 4811                 # a GitLab note
```

`--repo` and `--project` name the repository as for a review, with the same tokens, and `--config <file>` reads that file instead of the base's `.ocra/config.json` (for example to set `github.botLogin`). ocra answers only a comment that is on that change request, mentions `@ocra` outside code, asks something, comes from someone with write access (on GitLab the Developer role or higher), was not edited by anyone else and is not ocra's own; each comment is answered once (the answer carries `<!-- ocra:reply <id> -->`). For any other comment it prints `[ocra] Not answering: <reason>` on stderr, calls no model and exits `0`, so a workflow can run it on every comment. It exits `2` on an error, such as a missing token or a model call that failed.

The answer is one call on the writer role, given the description, the last comments of the thread and, for a comment on a line, that file's patch and the lines around it; otherwise the files the question names, else the smallest patches. Files come from the review's selection and are read through the same access policy, so a question cannot reach a secret or an excluded file. The answer is at most about 250 words, rendered as findings are (mentions and commands neutralized). Configuration comes from the base, as for a review. `ocra reply` reviews nothing and writes no session; a deeper look at a section is an `ocra review`. New in v0.10.0.

## ocra stack

Keeps a stack of branches, each a pull or merge request based on the one below it, so a large change can be reviewed in small steps:

```bash
ocra stack create feat/parse -m "feat: parse the input"   # branch from the current one, commit what is staged
ocra stack create feat/apply -m "feat: apply it"          # the next step, on top of feat/parse
ocra stack submit --draft                                  # push both, open #1 on main and #2 on feat/parse
git switch feat/parse && git commit --amend               # change a lower branch
ocra stack restack                                         # rebase feat/apply onto it
ocra stack sync                                            # after #1 merged: delete feat/parse, move feat/apply onto main
ocra stack submit                                          # push, retarget #2 to main
```

| Command | What it does |
|---|---|
| `create <branch>` | Creates the branch from the current one and stacks it on it; `-m <message>` commits what is staged |
| `track [<parent>]` | Stacks the current branch on `<parent>` (default: the trunk), for a branch made without `create` or in another clone |
| `log` | Shows the stack the current branch is in, marking branches that need a restack |
| `restack` | Rebases each branch onto its parent's tip, bottom to top, and returns to the branch you were on |
| `submit` | Pushes every branch (`--force-with-lease`), opens a change request for each one that has none (`--draft` for drafts) with its parent as the base, and updates each base and the stack's list in every description |
| `sync` | Fetches, finds the branches whose change requests merged, moves their children onto the merged branch's parent, deletes them and restacks. It pushes nothing: run `submit` next |

The stack is the tree of branches recorded in this clone's git config (`branch.<name>.ocraParent` and `branch.<name>.ocraParentHead`, the parent's commit the branch is built on), rooted at the trunk, origin's default branch. Restack runs `git rebase --onto <parent> <parentHead> <branch>`, so a parent that was amended or squash-merged is not replayed. A conflict stops it at that branch: resolve it, run `git rebase --continue`, then `ocra stack restack` again. Every command but `create` and `track` needs a clean working tree.

`submit` and `sync` use `GITHUB_TOKEN` (or `GH_TOKEN`) or `GITLAB_TOKEN`, with `--repo` or `--project` as for a review; the token needs pull request (merge request) write access. The stack's list in a description sits between `<!-- ocra:stack -->` markers; what you write outside them is kept. `submit` refuses a stack that holds a branch whose change request merged, before pushing anything: run `sync` first. ocra Cloud shows the stack on the pull request page and merges it from the bottom up to the one you choose, stopping at the first the platform refuses. New in v0.11.0.

## ocra generate

Writes one commit on a pull or merge request's branch: tests for the code it changes, or doc comments on the declarations it adds or alters.

```bash
ocra generate tests --pr 7                   # new test files beside the changed sources
ocra generate docstrings --mr 12             # doc comments in the changed lines
ocra generate tests --pr 7 --dry-run         # print the edits as a diff; commit nothing
ocra generate docstrings --pr 7 --json       # one line of JSON with the outcome
```

`--repo`, `--project` and `--config <file>` work as for `ocra reply`, with the same tokens; the token must be able to write to the branch (GitHub: contents write; GitLab: the api scope and the Developer role), and the commit is made as the token's account.

ocra picks the files: the change's source files that a review would select (never a secret, generated or vendored file), in TypeScript, JavaScript, Python, Go, Java or Kotlin (doc comments also in Rust), never a test, a type declaration, a symbolic link or a submodule; most added lines first, at most 5, each at most 60,000 characters. Each file gets one call on the writer role, which sees the description, the file's patch and the file itself, read through the review's access policy.

- **tests** writes one new test file per source file, at the path the repository's naming gives it: beside the source as `.test` or, where the tests beside it use it, `.spec`; in `__tests__/` when that folder holds tests; `test_<name>.py` or `<name>_test.py`, or under `tests/`; `<name>_test.go`; `src/test/java/…/<Name>Test.java` (and Kotlin's) for a Maven or Gradle layout. The model sees a test beside it, when there is one, to follow its framework and style. A path that already has a file is skipped: ocra never changes an existing file. ocra does not run the tests (it runs no code from the repository, installs and builds nothing), and the commit message says so; the change request's own CI runs them.
- **docstrings** asks for doc comments on the changed declarations that have none, in the language's form (`/** … */`, `//` for Go, `///` for Rust, a `"""` docstring for Python). ocra inserts only comment lines, only in the changed lines, and changes no existing line; a reply that would do anything else is refused for that file.

A file whose call fails, or whose reply is refused, is skipped with its reason on stderr; the run fails only when every call failed. ocra commits only on top of the head it read: if someone pushed in between, on GitHub the branch update is refused as not a fast-forward, on GitLab the branch is compared first and each changed file must still be as it was.

With `--json`, stdout is one line instead of the diff:

```json
{"kind":"tests","outcome":"committed","headSha":"<40 hex>","commitSha":"<40 hex>","files":["src/retry.test.ts"],"usage":{"inputTokens":0,"cachedTokens":0,"outputTokens":0,"reasoningTokens":0,"costUsd":0},"reason":null}
```

| `outcome` | Meaning | Exit |
|---|---|---|
| `committed` | One commit on the branch; `commitSha` names it | `0` |
| `dry_run` | `--dry-run`: the edits were made and printed, nothing committed | `0` |
| `nothing` | No file to write for, or the model added nothing; `reason` lists each skipped file | `0` |
| `head_moved` | The branch moved after ocra read it; nothing committed | `3` |
| `not_writable` | The token cannot write to the branch: a fork's, a protected one, a read-only token | `3` |

`files` lists the paths the edits touch, committed or not; `reason` is `null` for `committed` and `dry_run`. Usage, configuration and model errors exit `2`. The shape is `generateResultSchema` in `@open-cr-agent/cloud-contract`. New in v0.11.0.

## ocra fix

Writes a checked fix for one finding a review already reported, the way `ocra review --fixes` would have, and prints it. ocra Cloud runs it to offer a fix for a stored finding that has none. It commits and pushes nothing.

```bash
ocra fix --pr 7 --finding finding.json --head <sha> --json   # a GitHub pull request
ocra fix --mr 12 --finding - --json < finding.json             # a GitLab merge request, finding on stdin
ocra fix --commit HEAD --finding finding.json                  # a local commit; prints only the replacement
ocra fix --from main --finding finding.json                    # a local range, as review --from
```

| Option | Meaning |
|---|---|
| `--finding <file\|->` | The finding as JSON, in the shape ocra Cloud stores (`sharedFindingSchema` in `@open-cr-agent/cloud-contract`); `-` reads stdin. At most 256 KiB |
| `--head <sha>` | The full commit id the finding was reviewed at. When the change's head is another, ocra calls no model and answers `head_moved` |
| `--pr`, `--repo`, `--mr`, `--project` | The pull or merge request, as for `ocra generate`, with the same tokens (read access is enough) |
| `--from`, `--to`, `--commit` | A local range or commit instead, as for `ocra review`. Uncommitted changes cannot be fixed: a fix names lines of a commit |
| `--config <file>` | Use this configuration file instead of the repository's (the base branch's with `--pr` or `--mr`) |
| `--max-cost-usd <n>` | Spend limit, else `maxCostUsd` in the configuration. ocra checks it before the call; a call in flight is not cut short |
| `--json` | Print one line of JSON with the outcome on stdout |

ocra reads the change and the finding's file at the head through the review's access policy (a secret's path or `.git/` is never read), and finds the finding's quoted code (`code`) again, as the review anchors a finding. Only a finding the [Fix stage](./how-it-works) would ask a fix for gets one: its code fits exactly one place in the lines the change added or kept, at most 30 lines, and it is not low confidence. Whether it already has a fix does not matter. That finding gets one call on the `fixer` role (`roles.fixer` and `models` as for a review, through ocra Cloud's gateway when signed in), which sees the finding's text as data, the file's patch and an excerpt of the file. The answer is checked exactly as in a review: the lines are still the quoted ones, it changes them and nothing else, has no control or bidirectional characters, is at most 4,000 characters and 20 added lines, and the file parses with no more errors (tree-sitter). Without `--json`, stdout is the replacement alone.

With `--json`, stdout is one line:

```json
{"fingerprint":"b491fb26b470419c","headSha":"<40 hex>","outcome":"proposed","fix":{"startLine":3,"endLine":3,"replacement":"  for (let i = 0; i < prices.length; i++) sum += prices[i];"},"reason":null,"cause":null,"usage":{"inputTokens":0,"cachedTokens":0,"outputTokens":0,"reasoningTokens":0,"costUsd":0}}
```

| `outcome` | Meaning | `reason` | Exit |
|---|---|---|---|
| `proposed` | A fix that passed every check, for lines `startLine` to `endLine` of the file at `headSha` | `null` | `0` |
| `rejected` | The fixer answered and a check refused it, or the call failed | `failed`, `unchanged`, `unsafe`, `too_large` or `syntax` | `0` |
| `not_fixable` | Not a finding a fix is asked for, the fixer answered that no local edit fixes it, or no parser knows the file's language | `not_candidate`, `declined` or `no_parser` | `0` |
| `stale` | The finding's code is not in the file at the head, or the file is gone. Review the change again | `stale` | `3` |
| `head_moved` | The head is not `--head` | `null` | `3` |

A finding whose stored text was redacted or cut (`redacted`, `truncated`) and whose code is not found is `not_candidate`, not `stale`: its stored code may not be the file's. Usage, input and configuration errors, and a runtime that cannot start, exit `2`; a failed model call is `rejected` with `failed`, and `cause` says what failed (`null` for every other reason): `timeout` the call's deadline passed, `quota` every model is out of quota or rate limited, `refused` the endpoint refused the request (the key, the model's name, a parameter), `unavailable` it failed or could not be reached, `invalid_output` it answered in a form ocra could not read, or `unknown`; the endpoint's own message goes to stderr only (v0.21.0). The shape is `fixResultSchema` in `@open-cr-agent/cloud-contract` ([ADR-0077](https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/adr/0077-fix-one-finding.md)). New in v0.19.0.

## ocra mend

Runs one round of the fix loop over findings a person accepted: it writes a checked fix for each, and either prints them (`--level propose`, the default) or writes them as one commit on the pull or merge request's branch (`--level commit`). A scheduler (ocra Cloud, or a CI workflow) starts a round when something changed and keeps the state between rounds; no process waits for CI. Nothing from the repository runs: the change's own checks test the commit. ocra never force-pushes, approves or merges.

```bash
ocra mend --pr 7 --findings accepted.json --head <sha> --json              # propose: print the checked edits
ocra mend --pr 7 --findings accepted.json --level commit --state state.json --json
ocra mend --mr 12 --findings - --level commit --json < accepted.json       # a GitLab merge request
ocra mend --pr 7 --checks --level commit --state state.json --json         # the head's failed checks
ocra mend --pr 7 --conflicts --state state.json --json                     # propose a resolution of its merge conflicts
ocra mend --from main --findings accepted.json                             # a local range; propose only
```

| Option | Meaning |
|---|---|
| `--findings <file\|->` | The accepted findings as a JSON array, the most important first, each in the shape ocra Cloud stores (`sharedFindingSchema`); `-` reads stdin. At most 200 findings and 2 MiB |
| `--checks` | Also work on the checks that failed on the head of the pull or merge request (see below). With it, `--findings` may be left out. Needs `--pr` or `--mr` (v0.22.0) |
| `--conflicts` | First resolve the conflicts of merging the base branch into the head (see below). With it, `--findings` may be left out. Needs `--pr` or `--mr`, run in a clone of the repository (v0.22.0) |
| `--level <level>` | `propose` (default): the checked edits are in the result and nothing is committed. `commit`: one commit on the branch |
| `--state <file>` | The `state` the last round printed. Omit it for a change's first round |
| `--head <sha>` | The full commit id the findings were reviewed at. When the change's head is another, ocra calls no model and answers `head_moved` |
| `--protect <glob>` | A path no round may edit, besides the built-in ones; repeatable. It adds paths and removes none |
| `--pr`, `--repo`, `--mr`, `--project` | The pull or merge request, as for `ocra generate`. `--level commit` needs a token that can write to the branch |
| `--from`, `--to`, `--commit` | A local range or commit instead. Nothing is committed there: `--level commit` answers `not_writable` |
| `--config <file>` | Use this configuration file instead of the repository's (the base branch's with `--pr` or `--mr`) |
| `--max-cost-usd <n>` | Spend limit for the change's rounds together, the state's spend included; else `maxCostUsd` in the configuration |
| `--json` | Print one line of JSON with the outcome on stdout |

**What a round does.** It takes the first 5 findings that are still open. Each gets one call on the `fixer` role, with the rules of [`ocra fix`](#ocra-fix): the finding's code is found again at the head, and the answer must change those lines and nothing else, stay small and parse no worse. A finding that lane cannot write (its code is in the file more than once or outside the change's lines, it spans more than 30 lines, or the fixer answered that no local edit fixes it) goes to a task on the `fixer` role instead, on the `direct` runtime: an agent with the review's read tools and one more, `edit`, which replaces whole lines of a file in a copy of the head held in memory. It has no shell, writes nothing to disk and reaches no network; its edits count only when it ends with the done tool, and may span lines and files of the change. On the `opencode` runtime such a finding goes to a person (`not_candidate`). Either way the edit then passes a gate in code and one call on the `verifier` role, which reads the finding, the lines replaced, the replacement and the file around it, and must answer that the edit resolves the finding and adds no defect of its own; "unsure", a failed call or an answer that is not the expected JSON refuses the edit. Edits that pass are put together, the first finding first; one that touches lines an earlier one changes, or would take the round past 10 files or 200 added lines, waits for the next round. The commit is written only on top of the head the round read, never forced, and its message lists the findings it fixes. With the commit, the round leaves one comment on the pull or merge request: what the commit fixed, what it left and why, and the `git revert` that undoes it (v0.22.0); a comment that cannot be posted is a warning, and the commit stands.

**The gate.** A round edits only regular files of the change that a review would read. It never edits CI configuration (`.github/`, `.gitlab/`, `.gitlab-ci.yml`, `.circleci/`, `.buildkite/`, `Jenkinsfile`, Azure and Bitbucket pipelines), `.ocra/`, `AGENTS.md`, `CODEOWNERS`, dependency manifests (`package.json`, `pyproject.toml`, `requirements*.txt`, `Pipfile`, `go.mod`, `Cargo.toml`, `pom.xml`, Gradle build and settings files, `Gemfile`, `composer.json`), `Dockerfile`, `Makefile`, generated files, migrations, or a path `--protect` names. In a test file, an edit may not add a call that turns a test off (`.skip`, `.only`, `.todo`, `xit`, `@Ignore`, `@Disabled`, `pytest.mark.skip`, `skipif`, `xfail`, `unittest.skip`, `t.Skip`, `#[ignore]`). An edit holds no control or bidirectional characters. A finding the gate refuses goes to a person.

**Failed checks.** With `--checks`, a round also reads the checks of the head: on GitHub its check runs, on GitLab the jobs of the merge request's newest pipeline on that commit. A check is worked on when it failed (on GitHub a failure or a timeout, not a cancelled or skipped run; on GitLab a failed job that is not allowed to fail) and does not fail under the same name on the head of the base branch: what is already broken there is not this change's to fix. A round takes at most 3 of them, after the findings, within the same 5 items. Each goes to a fixer task as above, given the check's name, the last 200 lines of the failed step's output in the job's log (at most 20,000 characters, without timestamps and terminal sequences; the step that failed on GitHub Actions, the job's script on GitLab, so what ran after the failure does not push it out) and the paths the change touches; the log is data to it, and ocra runs nothing. On GitHub the log of an Actions job needs a token with `actions: read`; without it, and for a check of another app, the task gets what the check reported of itself, and a check with neither goes to a person (`not_candidate`), as every check does on the `opencode` runtime. The task is told to fix the code, to change a test only when the change altered the behaviour on purpose, and to make no edit when the failure is not the change's (an outage, a timeout, a missing secret); the gate still refuses an edit that turns a test off, and the verifier reads each edit. A failed check is the same item, with the same attempts, while it fails the same way: its name and the first line of its log that names a failure, numbers and ids aside. When checks are still running and nothing else is open, the round does nothing, counts as none and answers `waiting`: start the next one when they finish. A platform whose checks cannot be read leaves the round to its findings, with a warning.

**Merge conflicts.** With `--conflicts`, a round first reads, in the local clone, whether the base branch still merges into the head: `git merge-tree` over the two commits, with nothing checked out and no hook, merge driver or filter of the repository run. When it merges, the round goes on as without the option. When it does not, the round works on the conflicts alone, and every finding is `deferred` with the reason `conflicts` and uses no attempt. Each conflicted file is an item. One call on the `fixer` role reads its conflicted regions (the base text, both sides and 20 lines around each, as data) and answers each region or declines; code puts the answers between the lines git merged, so those cannot change. An answer that leaves a conflict marker, holds a control or bidirectional character or makes the file parse worse is refused, and one call on the `verifier` role must answer that each region keeps what both sides meant. A round resolves at most 5 files, 8 regions a file and 120 lines a region (`too_large` beyond); a file that was deleted, renamed, is binary or changed its mode on a side, and a file the gate protects, is a person's (`needs_human`). The merge is written only when every conflicted file is resolved; otherwise nothing is, and the files not yet tried are `deferred` with `conflicts`. At `--level propose` each item is `proposed` with the file's whole resolved content in `resolved`, and `mergeParent` is the base branch's commit to merge. At `--level commit` the round writes one merge commit, whose parents are the head and that commit, and pushes it from the clone to the change request's branch: an ordinary push, never forced, never a rebase, so a branch that moved answers `head_moved`, and a branch the token cannot push to (a fork, a protected branch) answers `not_writable`. The commit's author is the bot's account address (on GitHub `<id>+<login>@users.noreply.<host>`, so GitHub shows the account), and the round's comment names it a merge of the base branch and undoes it with `git revert -m 1` (v0.23.2). Turn `--level commit` on for conflicts only where the repository's owners want ocra to add merge commits to their branches ([ADR-0079](https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/adr/0079-merge-conflicts-as-a-merge-commit.md)).

**The caps.** A finding gets 2 attempts, a change 6 rounds, and the rounds together the spend limit. The state counts them: pass each round the state the last one printed. A finding that was not tried, or whose edit was not written (the round was full, the head moved), uses no attempt.

With `--json`, stdout is one line:

```json
{"headSha":"<40 hex>","outcome":"committed","stopped":null,"commitSha":"<40 hex>","mergeParent":null,"items":[{"fingerprint":"b491fb26b470419c","check":null,"conflict":null,"resolved":null,"regions":[],"outcome":"fixed","reason":null,"cause":null,"edits":[{"path":"src/total.ts","startLine":3,"endLine":3,"replacement":"  for (let i = 0; i < prices.length; i++) sum += prices[i];"}]}],"state":{"rounds":1,"costUsd":0.06,"items":{"b491fb26b470419c":{"attempts":1}}},"usage":{"inputTokens":0,"cachedTokens":0,"outputTokens":0,"reasoningTokens":0,"costUsd":0}}
```

| `outcome` | Meaning | Exit |
|---|---|---|
| `committed` | One commit, `commitSha`, on the branch; after a round over conflicts it is the merge commit, and `mergeParent` its second parent | `0` |
| `proposed` | `--level propose`: the edits, or the resolved files, are in `items`, nothing committed | `0` |
| `nothing` | No finding got an edit that passed; `items` says why | `0` |
| `stopped` | No round ran: the change reached the cap `stopped` names (`rounds` or `spend`) | `0` |
| `head_moved` | The head is not `--head`, or the branch moved after ocra read it; nothing committed | `3` |
| `not_writable` | The token cannot write to the branch, or the change is a local one | `3` |
| `waiting` | `--checks`: the head's checks are still running and nothing else was open; no round was counted | `0` |

Each entry of `items` is one finding, in the order given, then one failed check each, whose `check` is its name (`null` for a finding) and whose `fingerprint` is the id the loop keeps its attempts under. A round over merge conflicts lists one item per conflicted file instead, whose `conflict` is its path (`null` otherwise), after the findings it deferred:

| Item `outcome` | Meaning | `reason` |
|---|---|---|
| `fixed` | Its edits are in the commit, or its file is resolved in the merge commit | `null` |
| `proposed` | Its edits, or its resolved file (`resolved`), are in the result, for a person to commit | `null` |
| `rejected` | No edit passed this round; another round may try | `failed`, `unchanged`, `unsafe`, `syntax`, `declined`, `unresolved`, `unsure` or `unchecked` |
| `deferred` | Not tried, or not written; no attempt counted | `no_room`, `overlap`, `conflicts`, `head_moved` or `not_writable` |
| `needs_human` | Closed for a person to decide | `not_candidate`, `no_parser`, `out_of_scope`, `protected`, `too_large`, `tamper`, or `attempts` when both attempts are used |
| `gone` | Its code is not at the head any more | `stale` |

`edits` replace whole lines `startLine` to `endLine` of `path` at `headSha`; it is empty unless the item is `fixed` or `proposed`, and always for a conflicted file, whose `resolved` holds the whole file when it is `proposed` (`null` otherwise). Its `regions` then list each conflicted region as it was answered, for a person to read without the whole file: `line` is where the answer starts in `resolved`, `ours` the change request's lines, `theirs` the base branch's and `resolved` the lines written, each joined by newlines; it is empty for every other item (v0.23.0). An item's `cause` says what failed when its `reason` is `failed`, with the values [`ocra fix`](#ocra-fix) gives, and is `null` otherwise (v0.21.0). Usage, input and configuration errors, and a runtime that cannot start, exit `2`. The shapes are `mendResultSchema`, `mendStateSchema` and `mendFindingsSchema` in `@open-cr-agent/cloud-contract` ([ADR-0078](https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/adr/0078-fix-loop.md)). Reviewers' requests are planned. New in v0.20.0; the task with the `edit` tool in v0.21.0; failed checks and merge conflicts in v0.22.0.

## ocra metrics

Counts over the finished reviews in `.ocra/sessions/`, from each session's `report.json`; no model is called:

```bash
ocra metrics                       # a text table
ocra metrics --format json         # for a dashboard or a script; carries "version": 1
ocra metrics --since 2026-10-01    # runs started at or after a date
ocra metrics --sessions /srv/ocra  # another sessions directory, as on a CI runner
```

It reports runs (by verdict; incomplete ones, which left a file unfinished or a critical finding unverified, as their exit code 3 says; sessions without a readable report), cost (total, per run, tokens), findings (reported, unique by fingerprint, by severity and verification), the fate of earlier findings (fixed: the code is gone later; dismissed by a reviewer; their ratio as acceptance rate), and the same per reviewer with tasks, failed tasks and cost. A task that `--resume` reused costs nothing in the run that reused it: its cost counts once, in the run that paid for it. A fixed or dismissed finding counts for the reviewer the earlier review recorded, else the first to report its fingerprint. Only version 1 reports count; the JSON output is a versioned contract like the report.

Prints the version.

## ocra memory

Some findings are correct but accepted: the risk is handled elsewhere, or the team decided to live with it. Remember them so ocra stops reporting them:

```bash
ocra review                                  # every finding shows an id, such as #1a2b3c4d
ocra memory add 1a2b3c4d --reason "Retries are capped by the gateway."
ocra memory list
```

`ocra memory add` finds the id in the newest session under `.ocra/sessions/` (`--session <dir>` picks another) and writes `.ocra/memory.json`; commit it to share. A remembered finding (same reviewer, file and quoted code) is left out and counted, and reviewers see accepted findings for their files. Pull requests read the file from the base commit, so they cannot silence their own findings. An invalid file stops the review with an error.

### Memory in your ocra Cloud account

When you are [signed in](#ocra-login-ocra-logout-ocra-whoami), you can also remember a finding from ocra Cloud's page for a review ("Remember", with a reason). Before each review (local, `--pr` or `--mr`), ocra reads your account's entries for the repository (`GET /api/memory`, by the repository's hash) and applies them with `.ocra/memory.json`: a finding either lists is left out; one both list counts as the repository's. The report names each hidden finding's `source` (`repository` or `account`); the terminal prints `N finding(s) hidden by your ocra Cloud memory`, and a pull request's summary comment gives the count.

- Never read when signed out or with `OCRA_CLOUD=off`; `--no-upload` does not stop it (reading sends nothing about the review).
- If it cannot be read, a warning says so and only the repository's file applies.
- It applies only while the account [shares findings](#ocra-login-ocra-logout-ocra-whoami), since it is keyed by the hash under the account's salt; otherwise a review says once that only the repository's memory applies.
- `ocra memory add` writes only `.ocra/memory.json`.

## ocra login, ocra logout, ocra whoami

**In development.** ocra Cloud ([ADR-0024](https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/adr/0024-ocra-cloud.md)) lives at https://app.ocracloud.com; `OCRA_CLOUD_URL` names another server, such as a company's self-hosted one; when its certificate comes from the company's own authority, give that authority to Node with `NODE_EXTRA_CA_CERTS`, or every call fails naming the certificate error. Reviews work without a login, and with `OCRA_CLOUD=off` these commands refuse to run.

```bash
ocra login                                    # shows a code and opens the browser to confirm it
ocra whoami                                   # the signed-in GitHub account, and whether this machine sends findings
ocra logout                                   # ends the session on the server and deletes it here
```

`ocra login` uses the OAuth device flow (RFC 8628): it prints a code such as `BCDF-GHJK`, opens the server's confirmation page (`--no-browser` only prints the link; a page off the server in use, or not https or local http, is only printed), and waits for you to approve it in a browser signed in to the server. Approve only a code you just asked for. The session can call models with the server's stored keys and upload results, but cannot read those keys or change the account; revoke it on the server's sessions page.

**The session** is saved in `~/.config/ocra/credentials.json` (`$XDG_CONFIG_HOME/ocra/`, or `%APPDATA%\ocra\` on Windows), readable only by you.

- It and the salts beside it are written atomically (temporary file, then rename). A file without a session counts as signed out: a review warns once, naming it, and runs without ocra Cloud; `ocra logout` removes it.
- The access token lasts an hour; the refresh token changes on every use. Concurrent processes share the session: one renews at a time under `credentials.json.lock`, the others wait for it (up to two and a half minutes, printing `Waiting for another ocra process to renew the ocra Cloud session...` after five seconds; a lock older than 90 seconds, or whose process on this machine has exited, was left by a process that died and is broken) and take what it saved. `ocra login` and `ocra logout` take the same lock, and a renewal never saves over a session saved meanwhile. A 401 on a live token renews and retries once.
- A refused renewal ends the session: a review warns `your ocra Cloud session ended: run ocra login`; `ocra whoami` exits 1.
- If ocra Cloud is unreachable (network error, 5xx, 429), the session is kept; a review warns once and runs without your account's rules, limits (`maxCostUsd` included), models and memory, and uploads nothing; a review naming an `ocra-` model stops with an error, and `ocra whoami` exits 2. A 404 for account settings means none, without a warning.
- If `ocra login` cannot read your login after getting tokens, it saves the session and says the login is unknown.

**Models through ocra Cloud.** While signed in, `ocra-<provider>/<model>` goes through ocra Cloud with the key stored there for `<provider>` (a chat completions endpoint the server lists, or its Messages endpoint for a provider that has no other, such as `ocra-anthropic/<model>`):

```json
{ "runtime": "direct", "models": { "standard": "ocra-openrouter/qwen/qwen3.8-27b:free" } }
```

- Priced as ocra Cloud lists the model (input, output and cached input, per million tokens), so the reported cost and `--max-cost-usd` count it. A model ocra Cloud lists no price for is unpriced: they do not count it, with a warning naming the model.
- Prompts and quoted code pass through ocra Cloud, which records each call's model, status, token counts and duration, never the bodies.
- A review naming no `ocra-` model reads no session and never contacts ocra Cloud; a provider your configuration declares under an `ocra-` name keeps its declaration.
- [Effort](./configuration#effort) is sent the way ocra Cloud lists for the provider (`openai`: `reasoning_effort`; `openrouter`: `reasoning.effort`), `openai` when unlisted; an unknown style is ignored with a warning. An answer that is not a provider list stops the review.
- On `"runtime": "direct"`, ocra renews the token five minutes before expiry for the whole run. If it cannot, it warns once and tries again, after one minute and then less often (at most every five minutes), past expiry too, until the run ends. `opencode` reads it once at start, so ocra gives it a token outliving `runTimeoutMinutes` plus ten minutes, and warns when the run may outlast any token: calls through ocra Cloud then fail after about an hour. It renews the saved token for that only when a new one would last longer, not when the saved one is nearly as new.

**Account settings.** When signed in, `ocra review` applies your account's settings under the configuration ([Account settings](./configuration#account-settings)). The account can also turn on `ultra`, as if `--ultra` were given, unless the configuration sets `ultra`; `--ultra` and `--no-ultra` on the command line always apply. What the account filled in is printed (`From your ocra Cloud settings: …`). `--plan` reads them too and ends with a Settings list giving each setting's source: `shared` (an extended configuration), `file`, `env` (`OCRA_MODEL_*`, `OCRA_EFFORT_*`), `account` (`ultra` included), `depth` (what the [depth](./configuration#depth) filled), sources joined with `+` for combined lists (`include`, `exclude`, rules; for example `shared+account`; the account's `exclude` applies only when the configuration sets none), or `default`. If ocra Cloud is unreachable, a warning says so and the plan shows the configuration alone.

**What a review uploads.** After each review, a signed-in CLI sends counts: verdict, whether every file was reviewed, findings per severity, files, tasks, tokens, cost, time, source (local, GitHub, GitLab) and ocra version; per reviewer, tasks, failed tasks, findings by severity, cost (without tasks reused by `--resume`, which this run did not pay for) and earlier findings fixed or dismissed; findings confirmed, uncertain or unchecked; and earlier findings fixed or dismissed in all (counted for the recorded reviewer; one recorded before reviewers were counts only if this review still has its fingerprint). Unless your account shares findings, no path, title, fingerprint, finding text or code is sent.

- The repository is a salted SHA-256 of its normalized address `https://host/owner/repo` (user, credentials, port, trailing `/` and `.git` dropped, case folded, so `git@host:owner/repo.git` and `ssh://git@host:22/owner/repo` match). With `--pr` or `--mr` it is the platform's repository; locally, origin's (a path remote as written; no origin, the directory). A local review's upload does not name the repository: the server can group its reviews without learning which it is. With [`cloud.shareRepoName`](./configuration#ocra-cloud) on, every upload also names it, by path (`owner/name`) and normalised address. On a self-managed GitLab served under a path (`https://host/gitlab/…`) or serving SSH from another host, an SSH clone's address is not the merge request's, so local reviews of that clone count as another repository than `--mr` reviews; an HTTPS clone matches.
- A `--pr` or `--mr` review also names the pull or merge request: its repository's address as above, its number and its head commit, so ocra Cloud can show the verdict on it, each [linked issue](./how-it-works#linked-tasks) by tracker, number, address and state, so it can check one is linked, the id of each [learning](./rules#ocralearnings) the tasks were given, so it can count how often each applies, and each [pre-merge check](./how-it-works#pre-merge-checks)'s id and outcome. A local review sends the learnings' ids only with the findings. Its code, titles and paths, the issues' titles and labels included, still go only as below.
- A remote in SSH form, or with a port or trailing `/`, got a new hash once after 0.5.0 (which hashed the URL as written): earlier reviews and memory match only once recorded again.
- The salt is random, in `upload-salt` next to the credentials, so each machine hashes differently. If your account shares findings, the salt is the account's, read at login and before each review and kept in `account-salt` (readable only by you), so all your machines agree. When a review needs this machine's salt but cannot read `upload-salt` (another user's, say, after `sudo ocra`), or cannot make it (the directory is read-only), it leaves the file as it is, warns, and sends nothing to ocra Cloud. When it cannot keep the account's salt in `account-salt`, it warns and uses the salt it was just sent.
- `--no-upload` skips one upload, `OCRA_CLOUD=off` turns ocra Cloud off, and a failed upload is only a warning.

**Sharing findings.** With "Send findings and the code they quote to ocra Cloud" on in your account's Settings (off by default), the upload also carries each finding's fingerprint, reviewer, severity, category, verification, file, line range, title, body, suggestion and quoted code, so the web can show the full review, its fix (the lines it replaces and the replacement) when it has one, and whether `--ultra` kept it with low confidence (v0.19.0), which [`ocra fix`](#ocra-fix) reads. It carries the finding's evidence too, as a pull request comment shows it: at most 5 entries, each on one line and cut at 300 characters (v0.19.0), and the rule or learning it applies, by kind and id (v0.24.0). It also names, by fingerprint, the earlier findings the review saw fixed or dismissed (at most 200 of each), so the web can mark them. A fix is sent as written or not at all: one the redaction pass or the 4 KB cut would change is left out, since the web can commit it to the pull request. The linked issues' titles and labels, and each pre-merge check's reason, go with them, redacted the same way. A review ocra Cloud runs itself keeps its findings whether or not this switch is on ([auto review](./cloud#auto-review-and-ocra)).

- Before sending, ocra replaces secret-looking tokens in the path, category, title, body, suggestion, code and evidence with `[redacted]` and marks the finding redacted: PEM and PGP private key blocks, AWS key ids (`AKIA…`, `ASIA…`), GitHub tokens (`ghp_`, `gho_`, `ghs_`, `ghu_`, `ghr_`, `github_pat_`), GitLab tokens (`glpat-`), `sk-` keys (`sk-ant-`, `sk-or-`, `sk-proj-` too), Slack tokens (`xoxb-` and the like), Google API keys (`AIza…`), npm tokens (`npm_…`), Slack and Discord webhook URLs, a URL's password (`postgres://user:…@`), the password of `curl -u user:…` or `--user user:…`, and of `mysql -p…`, the credential after `Bearer` or `Basic`, on the same line or the next (a plain word after them, as in prose, stays; written lowercase, as in an HTTP/2 header, they count only before a credential of 16 or more characters with a digit), and a value assigned to a name such as `password`, `passphrase`, `secret`, `secret_key`, `token` or `api_key`: quoted (`password = "…"`, also with its quotes escaped inside a JSON string), unquoted as `NAME=…` (`.env`, a flag, a query string) or at the end of a line (`password: …` in YAML), the lines of a YAML block scalar (`password: |`), or the argument after a flag such as `--password …` or `--api-key "…"` (not a path). An unquoted value of letters only (`changeme`, `string`), or one that reads as code (a call, a dotted name such as `process.env.TOKEN`, `${…}`, a line ending in `,` or `;`), is left alone; after `NAME=` or a flag, a trailing `;`, `,` (or `)` after a flag) ends a shell command instead, so the value before it is still replaced. Also hex runs of 32+ characters (after a prefix such as `dop_v1_` too), and random-looking base64 runs of 32+ characters containing a digit (paths, and file names that end in a hash and an extension such as `index-Bx92KqLm.js`, are left alone). It catches patterns, not every secret; the server runs the same pass again.
- At most 200 findings and 256 KB of text, each field cut at 4 KB before it is redacted (marked truncated; a token the cut falls in is redacted whole). The terminal prints `Sent this review's counts and N finding(s) to ocra Cloud`.
- Findings go only when the server returns the account's salt, which it does only while the switch is on, and this machine agreed: `ocra login` records that in `share-findings` beside the credentials (readable only by you) when it finds the switch on, and says so; a review that finds the switch off removes it. After turning the switch on, or off and on again, run `ocra login` again on each machine; until then its reviews warn and send counts only. So ocra Cloud cannot turn sharing on by itself. If ocra Cloud is unreachable before the review, the review warns, hashes with the salt in `account-salt` (or this machine's), sends no findings and skips the account's memory.
- `--no-upload` and `OCRA_CLOUD=off` still send nothing.

**Watching a review live.** While your account shares findings, a signed-in review also relays its progress to ocra Cloud as it runs: the events `ocra serve` streams ([ocra serve](./serve)), findings included, redacted the same way, sent about once a second (`POST /api/live`). The terminal prints `[ocra] Watch this review live: <address>` once; on that page you can share the run with others, per person or by link, to watch it and comment on its findings. New in v0.11.0.

- The relay never holds up the review: a batch ocra Cloud does not take is sent again a second later, and after three failures in a row ocra warns once (`stopped relaying this review to ocra Cloud live`) and goes on. At the end it waits at most five seconds for the last events.
- A server that relays nothing yet (404), or that stopped taking the run's events (ocra Cloud keeps 5,000 per run), ends the relay without a warning.
- `--no-upload` and `OCRA_CLOUD=off` relay nothing, and neither does an account that does not share findings.

## ocra plugins

Allows, on this machine, the plugins your ocra Cloud settings name ([Plugins from your ocra Cloud account](./plugins#plugins-from-your-ocra-cloud-account)). Nothing here contacts ocra Cloud; `allow` and `deny` run npm.

```bash
ocra plugins allow <name>@<version>   # an exact version: shows the package, then installs it
ocra plugins deny <name>              # removes it: it no longer loads
ocra plugins list                     # the allowed plugins, with their integrity
```

`allow` runs `npm view <name>@<version> --json` and prints the package's name, version, publisher, maintainers and integrity, then `npm install --ignore-scripts --no-audit --no-fund --save-exact --prefix <dir> <name>@<version>` into `~/.config/ocra/plugins/` (`$XDG_CONFIG_HOME/ocra/plugins/`, or `%APPDATA%\ocra\plugins\` on Windows). It records it in `plugins.json` there only if npm installed exactly that version with the registry's integrity. npm runs with an argument list, never a shell, using your npm configuration's registry and credentials. A name that is not an npm package name, or a version that is a range or a tag, is refused before npm runs (exit code 2).
