ocra reads `.ocra/config.json` from the root of the reviewed repository. Every key is optional; unknown keys are rejected, so typos fail loudly.

`ocra review --config <file>` reads a file of your own instead, from anywhere. Since you trust it, it applies with `--no-repo-config` too: that is how reviews of untrusted code (the evaluation harness, for example) get declared [model endpoints](./providers#your-own-endpoint) and limits. Plugins it names resolve from its own directory. With `--pr` and `--mr` it replaces the base branch's file; plugins still do not load there.

```json
{
  "$schema": "https://raw.githubusercontent.com/ocrahq/Open-CR-Agent/main/docs/schema/config.v1.json",
  "models": {
    "top": "google/gemini-3.1-pro-preview",
    "standard": ["google/gemini-3.5-flash", "google/gemini-flash-lite-latest"],
    "light": "google/gemini-flash-lite-latest"
  },
  "concurrency": 8,
  "taskTimeoutMinutes": 10,
  "runTimeoutMinutes": 25,
  "verify": true,
  "judge": true,
  "maxCostUsd": 1,
  "include": [],
  "exclude": ["legacy/**"],
  "runtime": "opencode",
  "plugins": [],
  "reviewers": {},
  "pluginSettings": {}
}
```

`$schema` points editors at the file's [JSON Schema](https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/schema/config.v1.json) (draft 2020-12, generated from the code and tested against it) for completion and validation; ocra ignores it.

## Models

Models are written as `provider/model`, using OpenCode's provider IDs (for example `google`, `anthropic`, `openai`). Each tier takes one model or a failback chain:

| Tier | Used for |
|---|---|
| `standard` | Reviewer agents |
| `light` | Helper calls such as grouping changed files |
| `top` | The judge |

When a model is overloaded or rejects a request, the task retries on the next model in the chain. A rate limit with a stated wait of up to 90 seconds pauses that model for every task, then retries; one without a stated wait pauses it for 15 seconds, then 30, then 60. On the `direct` runtime a task keeps what it has done: the refused request is sent again after the pause, and the steps before it are not asked or paid for twice (new in v0.16.0); on `opencode` a task that ends on a rate limit starts again after the pause, and a session OpenCode would hold in its own retry for longer than 90 seconds (a daily limit's wait until midnight, say) is stopped within seconds and counts as that limit. Limits that arrive during a pause, as when tasks running at once are refused together, count as that pause. A daily limit, a longer wait, or a limit after three pauses in a row drops the model for the run. Each model has a circuit breaker: after two failures in a row it is skipped for a minute, then probed with one request; success restores it, failure doubles the pause (up to ten minutes). Credential errors stop at once, since the provider's other models would fail too.

Environment variables override the file, comma-separated for chains:

```bash
export OCRA_MODEL_STANDARD="google/gemini-3.5-flash,google/gemini-flash-lite-latest"
export OCRA_MODEL_LIGHT="google/gemini-flash-lite-latest"
export OCRA_MODEL_TOP="google/gemini-3.1-pro-preview"
```

## Models per agent

`reviewers.<id>.models` gives one reviewer its own model or chain (review tasks and plan call); `roles.<role>.models` does the same for the `verifier`, the `judge`, the `helper` calls (grouping files, relocating quotes) or the `writer` (the [walkthrough](./how-it-works#walkthrough)), or the `fixer` ([fixes](./how-it-works)); the `judge`'s also judge the [pre-merge checks](./how-it-works#pre-merge-checks). Same forms as a tier. Without one, an agent uses its tier's chain; the verifier and judge never take a reviewer's, so checking stays independent.

```json
{
  "models": { "standard": "google/gemini-3.5-flash", "top": "google/gemini-3.1-pro-preview" },
  "reviewers": { "security": { "models": ["anthropic/claude-sonnet-5-5", "google/gemini-3.5-flash"] } },
  "roles": { "helper": { "models": "google/gemini-flash-lite-latest" } }
}
```

Failback, rate-limit pauses and the circuit breaker work per model, so a model in two chains shares one circuit. The pre-review checks cover these chains: the provider's key must be set, a [declared provider's](./providers#your-own-endpoint) model must be priced there, and `ocra-<provider>/` models go through ocra Cloud. A plugin runtime that ignores an agent's chain uses the tier's. `provenance.agents` in the JSON report records each resolved chain, `--plan` shows each task's, and the configuration hash covers them.

## Effort

How much a model reasons before answering: `effort` sets it per tier, `reviewers.<id>.effort` per reviewer (review tasks and plan call), `roles.<role>.effort` for the `verifier`, `judge`, `helper` or `writer` calls. Levels: `none`, `minimal`, `low`, `medium`, `high`. An agent takes its own effort, else its tier's (reviewers by their tier, verifier and writer `standard`, judge `top`, helpers `light`); the verifier and judge never take a reviewer's. Unset sends nothing: the provider's default applies.

```json
{
  "effort": { "standard": "medium", "top": "high" },
  "reviewers": { "security": { "effort": "high" } },
  "roles": { "helper": { "effort": "minimal" } }
}
```

`OCRA_EFFORT_TOP`, `OCRA_EFFORT_STANDARD` and `OCRA_EFFORT_LIGHT` override a tier's effort.

- **`direct`** sends `reasoning_effort`, or `reasoning: { effort }` for a provider declared with `"effort": "openrouter"` ([Model providers](./providers#your-own-endpoint)); `none` is sent as `none`. A call with any other level omits `temperature` and `seed`, which reasoning models refuse or override. If the endpoint answers HTTP 400 naming the parameter, the call is retried once without it (not counted as a failure), that model's later calls omit it, and the run warns. A provider declared with `"type": "anthropic"` gets `output_config.effort` with adaptive thinking instead, `minimal` and `none` as `low` ([Model providers](./providers#an-endpoint-that-speaks-anthropics-api)).
- **`opencode`** sets the level in the model's provider options: `reasoningEffort` for OpenAI reasoning models (GPT-5, o-series), a thinking budget for Claude 4+ and Gemini 2.5, `thinkingLevel` for Gemini 3; OpenRouter models and [declared providers](./providers#your-own-endpoint) as their `effort` says. A thinking budget is a share of the model's output limit in OpenCode's catalog (`minimal` 1/32, `low` 1/16, `medium` 1/4, `high` 1/2; at least 1,024 tokens for Claude, within Gemini's bounds), or of 32,000 tokens without a limit; `none` turns thinking off (Claude: no thinking; Gemini 2.5 Flash: budget 0). Each model and level is its own OpenCode variant, so agents sharing a model can differ. Any level but `none` drops the configured `temperature`, as on `direct`. Other providers (Azure, Bedrock, Groq and the like) get no effort.
- Which levels a model takes comes from a table in ocra (`effortCapability` in `@open-cr-agent/core`) that can lag new models: on `opencode`, a level it does not list for a model (such as `minimal` for o3 or `medium` for Gemini 3), or an unknown model, gets no effort, and the run warns once per agent. A review never fails over it. If OpenCode's model catalog cannot be read at start, no level is sent, and the warning gives the cause.
- `provenance.agents` in the JSON report lists each agent's tier, effort, `applied` and `notApplied`; `--plan` shows each task's effort; the configuration hash covers it.

## Provider keys

Keys come from the environment only, in the variable OpenCode expects (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`; for Google, `GEMINI_API_KEY`, `GOOGLE_API_KEY` or `GOOGLE_GENERATIVE_AI_API_KEY`). Each provider's variables are on [Model providers](./providers), with how to declare your own endpoint under `providers`.

The agent runtime receives only `PATH`, `HOME`, locale, proxy and CA settings, and the credentials of the providers in your chains (for a provider ocra does not know, every variable starting with its uppercased id, such as `GROQ_`). Cloud credentials, `GITHUB_TOKEN` and the rest stay out; list any other variable a provider needs in `OCRA_RUNTIME_ENV`, comma-separated.

For providers that always need a key (Google, Anthropic, OpenAI, OpenRouter, Groq, Mistral, DeepSeek, xAI, Azure), ocra checks before starting and names a missing variable.

## Execution

| Key | Default | Meaning |
|---|---|---|
| `concurrency` | `8` | Review tasks running at once (1–32); `4` before v0.16.0. A review takes about as long as its model requests divided by this, so lower it only when your provider's rate limit keeps pausing the run |
| `taskTimeoutMinutes` | `10` | Limit for one review task, at most `35791` (about 24.8 days, the longest a timer keeps) |
| `runTimeoutMinutes` | `25` | Limit for the whole run, at most `35791` |
| `maxCostUsd` | none | Spend limit for the run: review tasks use up to 80% of it, verification and judging the rest (see `--max-cost-usd`) |
| `maxTasks` | `60` | Most review tasks one run starts. Past it, `--ultra`'s second passes go first, then later reviewers, so every file keeps its first reviewer as long as possible, files on sensitive paths longest; skipped files are reported as not reviewed (exit code `3`) |
| `judge` | `true` | Merge, filter and recalibrate findings across reviewers (one top-tier call per run with findings) |
| `ultra` | `false` | Favor recall over cost, as [`--ultra`](./how-it-works#modes) does; `false` keeps a review in the default mode even when your ocra Cloud account turns `ultra` on. `--ultra` and `--no-ultra` override it |
| `showPreExisting` | `true` | Report findings Verify traced to code from before the change, marked *pre-existing*. They never count towards the verdict; `false` leaves them out, with a warning giving their number |
| `verify` | `true` | Fact-check findings before reporting them (one standard-tier call per file with findings) |
| `walkthrough` | on for `--pr` and `--mr` | Write the [walkthrough](./how-it-works#walkthrough) of the change into the summary comment and the report (one standard-tier call per run); `false` leaves it out, `true` writes it for local reviews too |
| `mergeChecks` | none | [Pre-merge checks](./how-it-works#pre-merge-checks) in plain words, `[{ "id": …, "instruction": … }]`, each judged against the change (one top-tier call per run); at most 20, ids unique |
| `fixes` | `false` | Propose a checked [fix](./how-it-works) for findings a local edit of their lines fixes (at most one standard-tier call per file with candidates); `--fixes` turns it on for one run |
| `guidelineScope` | `"all"` | Which sections of `AGENTS.md` each review task is given, always whole sections in the file's order up to 20,000 characters, with the headings of the rest listed for the reviewer to read: `all` (every section, to every reviewer), `matched` (sections whose heading names a path, such as `## web/`, and the subsections under them, only to tasks with files there; every other section to every task) or `reviewer` (only to the `agents-md` reviewer). The `agents-md` reviewer always gets every section. `--guidelines` overrides it |
| `linkedTasks` | `true` | Give the reviewers the [issues the pull or merge request is linked to](./how-it-works#linked-tasks), each cut to fixed sizes; `false` (or `--no-linked-tasks`) leaves the prompts as they were |
| `sampling` | none | `{ "temperature": 0–2, "seed": n }` for every model call, each optional (unset: the provider's default); `--temperature` and `--seed` override it. `direct` sends both, except to a provider declared with `"type": "anthropic"`, which takes neither. `opencode` passes the temperature only to models its catalog says accept one ([declared models](./providers#your-own-endpoint) do) and reports a seed as not applied. `provenance.sampling` says what was applied. A seed makes runs repeatable only where the provider honors it |

A task that fails or times out never fails the run; its files are reported as `failed`.

## Depth

`depth` picks how thorough a review is in one word, `quick`, `standard` (ocra's defaults) or `deep`, and fills the settings below wherever no layer sets them itself: a key in the configuration, the account's settings, an `OCRA_EFFORT_*` variable or a flag always wins over the depth. `--depth` overrides it for one run.

| Setting | `quick` | `standard` | `deep` |
|---|---|---|---|
| Reviewers | `correctness` at every tier, `security` only at the `full` tier; `performance`, `docs` and `agents-md` off | By risk tier ([Reviewers](#reviewers)) | Every reviewer at every tier, two samples each (`ultra`) |
| `effort.standard` | `low` | unset | `high` |
| `effort.top` | unset | unset | `high` |
| `minInlineSeverity` | `warning` | unset | unset |
| `showPreExisting` | `false` | unset | unset |

Verification and the judge run at every depth. A reviewer entry of your own replaces the depth's for that reviewer whole. `--plan` lists what the depth filled with the source `depth`.

## Inline comments

On a pull or merge request, every finding anchored to lines in the diff becomes an inline comment unless you set a policy. These keys choose fewer; the findings left out are listed in a folded *not posted inline* section of the summary comment with the reason, stay in the [JSON report](./cli#json-output) (whose `inline.held` names them) and count towards the verdict as before.

| Key | Default | Meaning |
|---|---|---|
| `minInlineSeverity` | none | Post only findings at least this severe inline: `critical`, `warning` or `suggestion`. `--min-inline-severity` overrides it |
| `maxInlineComments` | none | Post at most this many of the review's findings inline (0 to 1000; 0 posts none). The most severe go first, then those Verify confirmed, then those it was unsure of, then unchecked ones, low-confidence findings last; ties go by file, line and fingerprint, so the same findings always win. The cap applies to each review on its own findings (a finding it already commented on in an earlier review and reports again takes a place but is not posted twice), so a change reviewed after several pushes can collect more inline comments than the cap. `--max-inline-comments` overrides it |

git, and what it starts (ssh, credential helpers, proxies), gets only part of ocra's environment, never its model keys or platform tokens: every `GIT_*` and `SSH_*` variable, `PATH`, `HOME`, `XDG_CONFIG_HOME`, `TMPDIR`, the proxy variables (`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`), `SSL_CERT_FILE`, `SSL_CERT_DIR`, `CURL_CA_BUNDLE`, and on Windows the system variables git needs (`PATHEXT`, `SYSTEMROOT`, `TEMP`, `USERPROFILE`, `APPDATA` and the like). A fetch also gets what credential helpers read: `GH_*`, `GLAB_*`, `GITLAB_*`, `GCM_*`, `GITHUB_TOKEN` and `GITHUB_ENTERPRISE_TOKEN`. A setup that needs another variable for git (Kerberos, a Nix certificate bundle) can pass it through git's own configuration, such as `GIT_SSH_COMMAND` or `GIT_CONFIG_*`.

## File selection

ocra skips binary files, likely secrets (`.env`, keys, certificates, cloud and registry credentials, Terraform variables and state), deleted files, media and archives, lock files, vendored and generated code, and very large diffs. Files over 1 MB are diffed as binary and skipped. A file whose name says text (`.ts`, `.py`, …) but that was skipped as binary gets a warning. Range, commit and pull request reviews read `.gitattributes` from the base commit (git 2.41 or later), so the reviewed change cannot mark its own files binary. Database migrations are never treated as generated code; what a migration tool writes next to them is (Drizzle's `meta/` snapshots and journal, Prisma's `migration_lock.toml`, EF Core's `*.Designer.cs` and model snapshot).

- `exclude`: globs to skip in addition.
- `include`: globs to review even if they would be skipped as generated or by extension. Secrets can never be included.

## Reviewers

`reviewers.<id>` turns a reviewer off, sets the risk tier it starts at, or sets its [models](#models-per-agent) or [effort](#effort). Risk tiers, from lowest: `trivial` (≤10 changed lines), `lite` (≤100), `full` (larger changes, more than 20 files, or a sensitive path: CI workflows, or a directory or file name with a word such as `auth`, `oauth`, `jwt`, `password`, `credential`, `secret`, `login`, `permission`, `acl`, `identity`, `crypto` or `security`).

```json
{ "reviewers": { "correctness": { "minTier": "lite" }, "security": { "enabled": false } } }
```

Pairs the matrix skips are listed under `skipped` in the JSON report; a file no reviewer covers shows up as `unreviewed` in coverage.

## Learnings

`learnings.requireReview` (default `false`): a pull or merge request `ocra learn mine --propose` opens is left for a person to merge instead of merging once its checks pass ([CLI](./cli#writing-them-back-by-pull-request)). A shared configuration may set it too.

## Trackers

`trackers` reads the tasks a change names from Jira or TAPD through your tracker's MCP server, next to the issues the platform links ([Linked tasks](./how-it-works#linked-tasks)):

```json
{
  "trackers": {
    "jira": {
      "projects": ["PAY", "AUTH"],
      "server": { "url": "https://mcp.example.com/jira", "tokenEnv": "JIRA_MCP_TOKEN" },
      "tool": "jira_get_issue",
      "keyArgument": "issue_key"
    },
    "tapd": {
      "workspace": "20001234",
      "server": { "url": "https://mcp.example.com/tapd", "tokenEnv": "TAPD_MCP_TOKEN" },
      "tools": { "story": "get_story", "bug": "get_bug", "task": "get_task" },
      "keyArgument": "id"
    }
  }
}
```

| Key | Meaning |
|---|---|
| `jira.projects` | Your Jira project keys: `PAY-12` in the title, description or branch (`feature/pay-12-retry` too) names a task; other projects' keys are ignored |
| `tapd.workspace` | Your TAPD workspace id: `--story=1001234`, `--bug=…`, `--task=…` and links to that workspace's stories, bugs and tasks name a task |
| `server.url` | The MCP server (Streamable HTTP), over https, or http on this machine. ocra never starts a server process |
| `server.tokenEnv` | The environment variable whose value is sent as `Authorization: Bearer …`; not a `GITHUB_`, `GITLAB_`, `AWS_` or other platform variable |
| `tool`, `tools` | The tool that reads one task; for TAPD, one per kind (a kind without one is skipped) |
| `keyArgument`, `arguments` | The argument the key (for TAPD, the numeric id) goes in, and fixed string arguments sent with it; TAPD also gets `workspace_id` |

The answer is read for the usual fields (`summary` or `title` or `name`, `description`, `status`, `labels`, under `fields` or one wrapping object), or used as plain text, at most 64,000 characters. Each task is one connection, at most 20 seconds per request. Reading needs the MCP SDK, which comes with ocra's optional dependencies. A shared configuration may set `trackers`; account settings may not. New in v0.11.0.

## Project documents

`projectDocs` lists the design documents a reviewer should check a change against: Markdown files (`.md`, `.mdx`), or directories whose Markdown files directly in them are read, by path in the repository ([Project documents](./how-it-works#project-documents)):

```json
{ "projectDocs": ["docs/architecture.md", "docs/design/"] }
```

They are read from the trusted revision, like `AGENTS.md`: at most 50 documents of up to 200,000 bytes each; a missing, larger or outside path is a warning. A shared configuration may set `projectDocs`; account settings may not. New in v0.11.0.

## Shared configuration

Repositories can extend an organization's common settings:

```json
{ "extends": "https://config.example.com/ocra.json#sha256=<hex>" }
```

The shared file may set `models`, `concurrency`, the timeouts, `verify`, `judge`, `showPreExisting`, `ultra`, `depth`, `minInlineSeverity`, `maxInlineComments`, `walkthrough`, `fixes`, `mergeChecks`, `linkedTasks`, `guidelineScope`, `trackers`, `projectDocs`, `maxCostUsd`, `maxTasks`, `include`, `exclude`, `effort`, `reviewers`, `roles`, `github`, `providers` (only when pinned) and `rules` (shaped like `.ocra/rules.json` entries). It cannot list plugins or choose a runtime, since it must not run code. The repository's values win; `include`, `exclude` and `rules` combine, and `models`, `effort`, `reviewers`, `roles`, `github` and `providers` merge key by key.

Only `https` URLs, without redirects, up to 256 KB. `#sha256=` pins the exact content; a file declaring `providers` must be pinned, since a provider decides where your code goes ([Model providers](./providers#your-own-endpoint)). If the file cannot be loaded or is invalid, ocra warns and uses the repository's settings alone, so limits set only there (such as `maxCostUsd`) do not apply; set must-hold limits in the repository too.

## ocra Cloud

| Key | Default | Meaning |
|---|---|---|
| `cloud.shareRepoName` | `false` | When [signed in](./cli#ocra-login-ocra-logout-ocra-whoami), every upload also names the repository: its path (`owner/name`, or deeper on GitLab) and its address as normalised for the hash, so ocra Cloud can show which repository a review is of. A repository without a host (a path remote, or no origin) is never named, nor one whose address the redaction pass would change. Set it in the repository's file or the one `--config` names; a shared configuration and the account cannot |

## Account settings

Signed in to [ocra Cloud](./cli#ocra-login-ocra-logout-ocra-whoami), `ocra review` layers your account's settings under the configuration. Highest first: command-line flags, the configuration (the repository's file or `--config`, what it `extends`, `OCRA_*` variables), account settings, ocra's defaults.

| Account key | How it applies |
|---|---|
| `runtime` (`opencode`, `direct` or `codex`), `models.<tier>`, `effort.<tier>`, `reviewers.<id>`, `roles.<role>` | Only where the configuration leaves it out; a reviewer's or role's entry in the configuration wins whole |
| `concurrency`, `taskTimeoutMinutes`, `runTimeoutMinutes`, `maxCostUsd`, `maxTasks`, `verify`, `judge`, `fixes`, `linkedTasks`, `sampling`, `ultra`, `depth`, `minInlineSeverity`, `maxInlineComments` | Only when the configuration does not set it (`sampling` as one setting): the account can bound an unbounded run, never loosen a limit |
| `include` | Combined: the configuration's patterns, then the account's |
| `exclude` | Only when the configuration sets none: a file the account excludes is neither reviewed nor counted as unreviewed, so an `exclude` in the configuration, even `[]`, keeps the account's out |
| `rules` | Added after the repository's and the shared ones: at most 50, each like an [`.ocra/rules.json`](./rules) entry with a rule of at most 2,000 characters, embedded in the prompt the same way |

Each key is checked against this file's schema; one that fails, or that this version does not know, is ignored with a warning naming it, and the rest apply. Models must be `ocra-<provider>/<model>`, which go through ocra Cloud with the keys stored there. The account can never set `providers`, `extends`, `github` (`botLogin` decides whose comments are trusted) or plugins: ocra ignores them with a warning.

Account settings apply to `--pr` and `--mr` runs too, under the base commit's configuration; they never come from the reviewed tree. What they filled in is printed (`From your ocra Cloud settings: …`), `--plan` lists every setting's source, and `provenance.accountSettings.version` names the version used. The configuration hash covers them and the account's rules, so a signed-out run keeps its hash. If ocra Cloud is unreachable, a warning says so and the configuration applies alone.

## Plugins

`runtime` picks the registered runtime: `opencode` (default), `direct` or `codex` ([Choosing the runtime](./providers#choosing-the-runtime)). `plugins` lists extra plugins by package name or path; `pluginSettings.<plugin-name>` holds each one's settings. See [Plugins](./plugins).
