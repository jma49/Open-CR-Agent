## GitHub Action

`ocra init --github` writes the [fork-safe workflow](#pull-requests-from-forks) below, or with `--same-repo-only` this one, for your provider's key ([ocra init](./cli#ocra-init)). By hand, add this workflow to the repository:

```yaml
name: ocra
on: pull_request

permissions:
  checks: write
  contents: read
  issues: read
  pull-requests: write

jobs:
  review:
    # A pull request from a fork gets no secrets on pull_request: skip it.
    if: github.event.pull_request.head.repo.full_name == github.repository
    # One review per pull request at a time: a new push cancels the older run.
    concurrency:
      group: ocra-${{ github.event.pull_request.number }}
      cancel-in-progress: true
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          fetch-depth: 0
      - uses: ocrahq/Open-CR-Agent@c13507b6357ca73661d83f09a275d8aa49c4f688 # v0.26.0
        env:
          GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}
```

- **Pin every action by commit**, with the version as a comment: a tag can move, a commit cannot. The recipes here and `ocra init` do, `actions/checkout` included. `git ls-remote --tags https://github.com/ocrahq/Open-CR-Agent v0.3.0` prints a release's commit; Dependabot updates the pin and comment.
- **Keep `fetch-depth: 0`:** ocra needs the history between base and head; a shallow checkout stops with a message.
- **Keep `concurrency`:** otherwise two quick pushes post the same comments twice, and the slower run can overwrite the summary with an older head. A cancelled run publishes nothing (unless already publishing) and leaves its partial report in the job log.
- **Keep `issues: read`:** with it the reviewers see the [issues the pull request closes](./how-it-works#linked-tasks); without it, a private repository's review goes on with a warning.
- **Store the model key as a repository secret.** Models come from the base branch's `.ocra/config.json` or `OCRA_MODEL_*` variables in `env`.

ocra retries GitHub's rate limits and short outages a few times, never a request that may already have posted a comment.

Since v0.1.1 the Action installs `@open-cr-agent/cli` from npm at its own version, dependencies pinned by its `package-lock.json`, install scripts off and, on the npm registry, signatures checked. It uses them only when each ocra package has [provenance](./stability#verifying-a-release) from this repository's release workflow at the version's tag; otherwise, or before the version reaches npm, it builds its own source with a warning (v0.1.0 always does). So `@main` runs `main`'s Action code with the release `main` names, or builds `main` if its package dependencies changed since.

| Input | Default | Meaning |
|---|---|---|
| `github-token` | `${{ github.token }}` | Token for reading the pull request and posting the review |
| `args` | | Extra `ocra review` options, such as `--reviewers correctness,security` (with `learn`, `ocra learn` ones; with `reply`, `ocra reply` ones), split on spaces and newlines (no quoting) |
| `fail-on-concerns` | `false` | Fail the job when the verdict is `significant_concerns` (a critical finding the verifier confirmed). An incomplete review (exit code `3`) always fails the job |
| `opencode` | `true` | Install OpenCode, the default runtime. Set `false` when the configuration sets `"runtime": "direct"`; see [The runtime](#the-runtime). New in v0.3.0 |
| `symbol-cache` | `true` | Keep the symbols ocra parses (definitions and uses per file, keyed by its content) in the Actions cache between runs, so a review parses only files no earlier run read. Entries no run read for 30 days are dropped. New in v0.8.0 |
| `learn` | | `mine` or `remember`: draft learnings and open them as a pull request instead of reviewing; see [Learning from history and notes](#learning-from-history-and-notes). New in v0.8.0 |
| `reply` | `false` | Answer the comment that started the workflow when it mentions `@ocra`, instead of reviewing; see [Asking ocra about the change](#asking-ocra-about-the-change). New in v0.10.0 |
| `sarif` | `false` | Also write the review as SARIF 2.1.0 for [code scanning](#code-scanning), to the file the `sarif` output names. It takes the place of `--format` and `--output` in `args` |

Give the step an `id` to read its outputs. They are set whenever ocra ran, also when the step fails, and come from the session this run wrote: a session that came with the pull request, or a link in place of `.ocra/sessions`, is never read.

| Output | Meaning |
|---|---|
| `verdict` | `approved`, `approved_with_comments`, `minor_issues` or `significant_concerns` |
| `exit-code` | ocra's [exit code](./cli#exit-codes), before `fail-on-concerns` turns `1` into a passing step |
| `run-id` | The run id, also in the summary comment and the SARIF log |
| `report` | Path to the JSON report, the shape of [`--format json`](./cli#json-output), under `$RUNNER_TEMP` |
| `findings` | The number of findings in the report |
| `sarif` | Path to the SARIF log, when `sarif` is `true` |
| `proposal` | With `learn`: the address of the pull request opened, empty when no learning was kept |

`verdict` is empty unless the review completed (exit code `0` or `1`): a run that did not review everything (`2` or `3`) may write a report, but its verdict says nothing about the unreviewed files. `run-id`, `report` and `findings` are empty when ocra wrote no report. To keep the report and put the verdict in the job summary:

```yaml
      - id: ocra
        uses: ocrahq/Open-CR-Agent@c13507b6357ca73661d83f09a275d8aa49c4f688 # v0.26.0
        env:
          GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}
      - if: ${{ !cancelled() && steps.ocra.outputs.report != '' }}
        uses: actions/upload-artifact@043fb46d1a93c77aae656e7c1c64a875d1fc6a0a # v7.0.1
        with:
          name: ocra-report
          path: ${{ steps.ocra.outputs.report }}
      - if: ${{ !cancelled() }}
        env:
          VERDICT: ${{ steps.ocra.outputs.verdict }}
          FINDINGS: ${{ steps.ocra.outputs.findings }}
          RUN_ID: ${{ steps.ocra.outputs.run-id }}
        run: echo "ocra: $VERDICT, $FINDINGS findings (run $RUN_ID)" >> "$GITHUB_STEP_SUMMARY"
```

Pass outputs to a script through `env`, as here, never as `${{ }}` inside `run`.

The verdict is advice ([why](./security#the-verdict-is-not-a-security-gate)): do not make the check a required status in place of human review, and with `fail-on-concerns` read a pass as "nothing confirmed", not "safe".

On `pull_request`, pull requests from forks get no secrets, so the `if:` skips them; to review them, see [Pull requests from forks](#pull-requests-from-forks).

### The runtime

OpenCode, the default runtime, with its native binary is 97 of the 108 packages the Action installs and about 165 MB of 175 MB. When every model in the base branch's configuration is on an endpoint you declare and it sets `"runtime": "direct"` ([Choosing the runtime](./providers#choosing-the-runtime)), set `opencode: false` (new in v0.3.0) to install 11 packages. If the configuration then selects `opencode`, the review stops before any model call with exit code `2`, naming the missing package.

```yaml
      - uses: ocrahq/Open-CR-Agent@<commit> # v0.26.0
        with:
          opencode: false
        env:
          OPENROUTER_API_KEY: ${{ secrets.OPENROUTER_API_KEY }}
```

The install is not cached: each run uses a fresh npm cache, so every package, signature and provenance statement comes from the registry, never from a cache another workflow could have written.

## What gets posted

- **Inline comments** for findings anchored in the diff, marked verified, unverified or not verified, in one `COMMENT` review; [`minInlineSeverity` and `maxInlineComments`](./configuration#inline-comments) post fewer and list the rest in the summary. ocra never approves. With `github.requestChanges`, a `significant_concerns` verdict requests changes once, withdrawn (dismissed) when a later verdict no longer blocks or the commit is overridden.
- **An `ocra review` check** on the head commit (new in v0.27.0): in progress while the review runs, then the verdict and counts as its title and every finding in one table, most severe first, under Details. It passes on an approval and is neutral otherwise, so it never fails a required check by itself; a review that is interrupted or fails ends it as cancelled with the reason. It needs `checks: write` in the workflow's permissions (a GitHub App: Checks, read and write); without it the review is still posted, with a warning.
- **One summary comment**, updated in place: verdict, summary, the [walkthrough](./how-it-works#walkthrough) of the change, the [pre-merge checks](./how-it-works#pre-merge-checks)' outcomes, findings outside the diff, what was fixed, coverage, cost and the run id. It counts unreviewed files, says whether the spend limit was reached, and lists partly reviewed files (a reviewer out of steps or stopped) with what to do.

Later pushes review **only what changed**: files changed since the previous review's commit, plus files it did not finish (failed task, reviewer out of steps, spend limit). Findings in unchanged files carry over, open, counted, not commented again. Everything is reviewed again when the previous commit left the branch (force-push, rebase), the push raises the risk tier, the summary was last edited by someone other than ocra (its remembered state is then ignored, though ocra still recognizes its own unedited inline comments), or you pass `--full`. Changing which reviewers run (`reviewers`, `--reviewers`, `--ultra`) does not; pass `--full` once. The summary says which kind of review it was and why.

Compared with the previous review:

- A finding already commented on is not commented again.
- A finding is **fixed** only when its code is gone from the file or the file was deleted; it is listed and its thread resolved.
- A finding not reported this time while its code is unchanged is **not reported this time**: model runs vary, so it stays open and counts at its severity until the code changes or it is dismissed. The same code gets the same verdict.
- A finding whose file was not reviewed this time is **not re-checked** and stays open.

Maintainers stay in charge. A maintainer, someone with write access (admin, maintain or write) other than the author, dismisses a finding by resolving its thread, replying `@ocra dismiss`, or replying with a message that opens with a clear decline ("won't fix", "will not fix", "by design", "false positive", "not a bug", "working as intended", "intended behavior") and is not a question. A dismissed finding no longer counts in this pull request unless a later run finds it at a higher severity. The words elsewhere in a reply ("this is not intended, good catch", "is this by design?") do not count, nor does "I disagree". Their other replies go to the judge when the finding returns; it may drop the finding for a specific reason, never a confirmed critical one. The author's replies are not shown and cannot dismiss, and a reply someone else edited does not count. A finding without an inline thread cannot be dismissed; [`ocra memory`](./cli#ocra-memory) silences it instead: at any severity, in every pull request, once `.ocra/memory.json` is on the base branch.

### Committable suggestions

An inline comment opens with the finding's title on a line of its own, with its severity, its reviewer and whether Verify confirmed it under it; then what goes wrong, a suggested fix, and the facts the reviewer checked, folded under **Evidence**.

When a coding agent ran the review (the [`codex` runtime](./providers)), ocra names it after itself, as `ocra · Codex`: in the summary comment's heading, under each inline comment and at the start of the check's title. The comments are still posted by ocra's account.

A finding can carry a fix: code that replaces the lines it is about. Its inline comment then carries a suggestion block that anyone with write access can commit (**Commit suggestion**, or in a batch). ocra offers one only when the comment sits on exactly the replaced lines, never in the summary, and posts the code exactly or not at all: a fix holding an HTML comment opener, `@ocra` or `/ocra`, a carriage return or a control or bidirectional character, or longer than 20,000 characters, gets no block; the finding is still posted. A suggestion is a model's proposal: read it before committing.

Fixes come from the [Fix stage](./how-it-works), which is off unless [`fixes`](./configuration) or `--fixes` turns it on ([ADR-0058](https://github.com/ocrahq/Open-CR-Agent/blob/main/docs/adr/0058-checked-fix-proposals.md)); without it, comments give suggestions as text.

## Code scanning

To also see findings as code scanning alerts, write SARIF with the `sarif` input and upload it with `upload-sarif`:

```yaml
permissions:
  checks: write
  contents: read
  issues: read
  pull-requests: write
  security-events: write

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          fetch-depth: 0
      - id: ocra
        uses: ocrahq/Open-CR-Agent@c13507b6357ca73661d83f09a275d8aa49c4f688 # v0.26.0
        with:
          sarif: true
        env:
          GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}
      - uses: github/codeql-action/upload-sarif@2892aa5e19bbd11bc0cff5427e3b750a04d9e3c2 # v4.38.2
        # Also after an incomplete review, which fails the step above.
        if: ${{ !cancelled() && steps.ocra.outputs.sarif != '' }}
        with:
          sarif_file: ${{ steps.ocra.outputs.sarif }}
          category: ocra
```

- The review is still posted and `report` still names the JSON report: SARIF only changes what ocra prints. `args: --format sarif --output ocra.sarif` does the same with your own path.
- Code scanning shows only results with lines, so file-level findings are not shown, nor are earlier findings in files unchanged since (later pushes review only what changed). Add `--full` to `args` to show every finding on every push, at the cost of a full review each time.
- Code scanning is available for public repositories; private ones need GitHub Code Security.
- File contents: [SARIF output](./cli#sarif-output).

### Importing an analyzer's results

Run Semgrep, CodeQL or another SARIF-writing analyzer first and pass its log with `--import-sarif`: its results on the change are verified and judged with ocra's own ([SARIF input](./cli#sarif-input)). ocra runs no tool itself.

```yaml
      - run: pipx run semgrep scan --config p/default --metrics=off --sarif --output semgrep.sarif
      - uses: ocrahq/Open-CR-Agent@c13507b6357ca73661d83f09a275d8aa49c4f688 # v0.26.0
        with:
          args: --import-sarif semgrep.sarif
        env:
          GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}
```

For a noisy tool, pass the log with `--sarif-evidence` instead: the reviewers see its results on and near the change and report only those they confirm ([SARIF as evidence](./cli#sarif-as-evidence)).

The import is tested on a Semgrep 1.178.0 log; this workflow has not run end to end in CI yet.

## Overriding a blocking verdict

To merge a change ocra blocks, someone with write access other than the author comments:

```
@ocra override <full head commit id> <reason>
```

For that commit the run exits `0` instead of `1`, so `fail-on-concerns` passes and a `requestChanges` review is withdrawn. The verdict stays `significant_concerns`; the summary shows who overrode it and why, and prints the command with the commit id to copy. A new push needs a new override. The full id is required because a crafted commit can match a short prefix. The author cannot override their own pull request, a command someone else edited into a comment does not count, and an incomplete review (exit `3`) is never overridden.

<Callout type="warn">

Someone with push access can push a workflow that gets the repository's secrets and posts as `github-actions[bot]`; with `on: pull_request`, even the review's workflow is their branch's copy. For a review they can neither change nor impersonate, use [the setup below](#a-review-your-own-developers-cannot-change).

</Callout>

## Asking ocra to remember

Anyone with write access, the author too, can comment on a pull request:

```
@ocra remember Amounts are integer cents; never parse them as floats.
```

The rest of the comment is the note. A review does nothing with it; [`ocra learn remember --pr <n>`](./cli#from-pull-request-notes) drafts a learning from each note with the files of the diff it names, and `--propose` writes them back by pull request. Notes from people without write access, comments someone else edited and ocra's own summary do not count.

### Learning from history and notes

With the `learn` input the Action drafts learnings instead of reviewing and opens them as a pull request ([`ocra learn ... --propose`](./cli#writing-them-back-by-pull-request)): `mine` from the fix commits, for a schedule, and `remember` from the notes of the pull request a comment is on. This workflow does both:

```yaml
name: ocra learn
on:
  schedule:
    - cron: "0 3 * * 1"
  issue_comment:
    types: [created]

permissions:
  contents: write
  issues: read
  pull-requests: write

jobs:
  learn:
    # On a comment, only a @ocra remember on a pull request by someone who
    # can write; ocra checks that again before drafting.
    if: >-
      github.event_name == 'schedule' ||
      (github.event.issue.pull_request &&
       (startsWith(github.event.comment.body, '@ocra remember') ||
        startsWith(github.event.comment.body, '/ocra remember')) &&
       contains(fromJSON('["OWNER","MEMBER","COLLABORATOR"]'), github.event.comment.author_association))
    concurrency:
      group: ocra-learn
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          fetch-depth: 0
      - uses: ocrahq/Open-CR-Agent@c13507b6357ca73661d83f09a275d8aa49c4f688 # v0.26.0
        with:
          learn: ${{ github.event_name == 'schedule' && 'mine' || 'remember' }}
        env:
          GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}
```

- **Which token decides how it merges.** A pull request opened with the workflow's own token starts no workflows, so required checks would never report on it: with `github.token` the Action passes `--require-review` and leaves the pull request for a person, with a notice saying so. Pass a GitHub App's installation token (contents and pull request write) as `github-token`, for example from `actions/create-github-app-token`, and it merges once its checks pass. A branch rule that requires an approving review still waits for one.
- **Let Actions open pull requests** for the workflow's own token: Settings → Actions → General → "Allow GitHub Actions to create and approve pull requests".
- Each draft is one helper model call, at most `--max` (20) a run; `args` passes options such as `--max 5` or `--max-cost-usd 1` to `ocra learn`. What a learning on the default branch, or on a proposal branch not yet merged or deleted, already records is not drafted again.

## Asking ocra about the change

Anyone with write access can ask in a comment, in the conversation or on a line of the diff:

```
@ocra why does this retry forever when the limit is negative?
```

and ocra answers in that thread ([`ocra reply`](./cli#ocra-reply)): one model call, from the description, the thread and the commented file, never a review. Comments from people without write access, comments someone else edited, ocra's own, comments it already answered and [commands](#commands-in-comments) get no answer. The [comment workflow](#the-comment-workflow) runs it. New in v0.10.0.

## Asking for a review again

Anyone with write access can comment on a pull request:

```
@ocra review
```

and ocra reviews the whole pull request again, as with `--full`: every file, not only what changed since the last review. Useful after a change to `.ocra/config.json`, the rules or the reviewers, or when a review was cut short. The [comment workflow](#the-comment-workflow) runs it, for a fork's pull request too, as the [fork-safe workflow](#pull-requests-from-forks) does. New in v0.10.0.

## Commands in comments

A command is a line of a comment that starts with `@ocra`, from someone with write access. This spelling and the generated comment workflow require ocra 0.27.0 or later; use `/ocra` with older releases.

| Command | What it does |
|---|---|
| `@ocra review` | Reviews the pull request again, every file ([above](#asking-for-a-review-again)) |
| `@ocra override <commit> <reason>` | Lets a blocking verdict pass for that commit ([Overriding a blocking verdict](#overriding-a-blocking-verdict)) |
| `@ocra dismiss` | In a finding's thread, dismisses the finding ([What gets posted](#what-gets-posted)) |
| `@ocra remember <note>` | Leaves a note for `ocra learn remember` ([Asking ocra to remember](#asking-ocra-to-remember)) |

Any other comment that mentions `@ocra` is a [question](#asking-ocra-about-the-change). `/ocra`, the earlier spelling of each command, still works but is deprecated and will be removed in a later release.

### The comment workflow

`ocra init --github` writes it as `.github/workflows/ocra-commands.yml`, next to the review's workflow. By hand, next to the [fork-safe workflow](#pull-requests-from-forks):

```yaml
name: ocra commands
on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]

permissions:
  checks: write
  contents: read
  issues: read
  pull-requests: write

jobs:
  review:
    # @ocra review on a pull request, by someone who can write: every file
    # again, as with --full.
    if: >-
      github.event_name == 'issue_comment' && github.event.issue.pull_request &&
      (startsWith(github.event.comment.body, '@ocra review') ||
       startsWith(github.event.comment.body, '/ocra review')) &&
      contains(fromJSON('["OWNER", "MEMBER", "COLLABORATOR"]'), github.event.comment.author_association)
    # The key repeats the if:, so any other comment gets a group of its own
    # and cannot cancel the review in progress.
    concurrency:
      group: >-
        ${{
          (github.event_name == 'issue_comment' && github.event.issue.pull_request &&
           (startsWith(github.event.comment.body, '@ocra review') ||
            startsWith(github.event.comment.body, '/ocra review')) &&
           contains(fromJSON('["OWNER", "MEMBER", "COLLABORATOR"]'), github.event.comment.author_association)
          ) && format('ocra-{0}-review', github.event.issue.number) || github.run_id }}
      cancel-in-progress: true
    runs-on: ubuntu-latest
    steps:
      # The base branch. Nothing from the pull request is checked out.
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          fetch-depth: 0
          # In a private repository, remove this line: ocra fetches the
          # pull request's commits with the checkout's credentials.
          persist-credentials: false
      - uses: ocrahq/Open-CR-Agent@c13507b6357ca73661d83f09a275d8aa49c4f688 # v0.26.0
        with:
          args: --max-cost-usd 2
        env:
          GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}
  reply:
    # Any other @ocra mention by someone who can write, answered in its
    # thread. ocra checks both again and answers each comment once.
    if: >-
      (github.event_name == 'pull_request_review_comment' || github.event.issue.pull_request) &&
      contains(github.event.comment.body, '@ocra') &&
      !startsWith(github.event.comment.body, '@ocra review') &&
      contains(fromJSON('["OWNER", "MEMBER", "COLLABORATOR"]'), github.event.comment.author_association)
    concurrency:
      group: ocra-reply-${{ github.event.comment.id }}
    runs-on: ubuntu-latest
    steps:
      # The base branch. Nothing from the pull request is checked out.
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          fetch-depth: 0
          persist-credentials: false
      - uses: ocrahq/Open-CR-Agent@c13507b6357ca73661d83f09a275d8aa49c4f688 # v0.26.0
        with:
          reply: true
        env:
          GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}
```

- **Keep the condition in the review job's concurrency group**: it shares the fork-safe workflow's group (`ocra-<number>-review`), and with a plain `ocra-<number>-review` every other comment on the pull request would cancel the review in progress. With the `pull_request` workflow above, whose group is `ocra-<number>`, use `format('ocra-{0}', github.event.issue.number)`; `ocra init --github --same-repo-only` does.
- **The workflow decides who may ask.** `issue_comment` runs the workflow file of your default branch with your secrets, so a pull request cannot change who may ask; the comment's text never reaches the Action, which only learns which pull request to review or which comment to answer.
- **Nothing from the pull request runs**, as on `pull_request_target`: the checkout is your default branch, and ocra reads the pull request's commits as git objects.
- **Override, dismiss and remember need no workflow of their own**: the next review reads them, and `ocra learn` reads the notes. A comment that gives one starts the reply job, which answers nothing.

## What the pull request can and cannot change

`.ocra/config.json`, `.ocra/rules.json`, `.ocra/rules.md`, `.ocra/memory.json`, `.ocra/learnings/` and `AGENTS.md` come from the **base** commit, and repository plugins never load. The diff, title and description reach reviewers as [untrusted data](./security#untrusted-input).

## Pull requests from forks

On `pull_request`, a fork's pull request runs without your secrets and with a read-only token. `pull_request_target` runs your default branch's workflow file with your secrets and the permissions you grant. This workflow replaces the one above and reviews your own branches too:

```yaml
name: ocra
on:
  pull_request_target:
    types: [opened, synchronize, reopened, labeled]

permissions:
  checks: write
  contents: read
  issues: read
  pull-requests: write

jobs:
  review:
    # Members and collaborators: every push. Anyone else: one review each
    # time a maintainer adds the ocra-review label.
    if: >-
      (github.event.action == 'labeled' && github.event.label.name == 'ocra-review') ||
      (github.event.action != 'labeled' &&
        contains(fromJSON('["OWNER", "MEMBER", "COLLABORATOR"]'), github.event.pull_request.author_association))
    # One review per pull request at a time: a new push cancels the older run.
    # The key repeats the if:, so a run the if: skips gets a group of its
    # own and cannot cancel the review in progress.
    concurrency:
      group: >-
        ocra-${{ github.event.pull_request.number }}-${{
          ((github.event.action == 'labeled' && github.event.label.name == 'ocra-review') ||
           (github.event.action != 'labeled' &&
             contains(fromJSON('["OWNER", "MEMBER", "COLLABORATOR"]'), github.event.pull_request.author_association)))
          && 'review' || github.run_id }}
      cancel-in-progress: true
    runs-on: ubuntu-latest
    steps:
      # The base branch. Nothing from the pull request is checked out.
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          fetch-depth: 0
          persist-credentials: false
      - uses: ocrahq/Open-CR-Agent@c13507b6357ca73661d83f09a275d8aa49c4f688 # v0.26.0
        with:
          args: --max-cost-usd 2
        env:
          GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}
```

GitHub warns against `pull_request_target` because a job that builds the pull request's code runs it with your secrets. ocra runs nothing from the pull request ([Threat model](./threat-model)); keep the workflow that way:

- **Never check out, install, build or test the pull request here:** no `ref: ${{ github.event.pull_request.head.sha }}`, no dependency install, no test run. Do those in a separate `pull_request` workflow, which gets no secrets for forks.
- **Keep the `if:` gate.** Anyone can open a pull request, and every review costs money: an outsider's pull request is reviewed once each time a maintainer adds the label (remove and re-add it for the next review). An outside author's push during a labelled review is skipped and leaves that review running; re-add the label to review the new head. `--max-cost-usd` caps each review.
- **Keep the condition in the concurrency group, and change both together.** A run the `if:` skips, such as one for an unrelated label, gets a group of its own, so it cannot cancel the review in progress.
- **Use a model key that serves only these reviews**, with a spending limit at the provider.
- **Pin the Action by commit.**

`author_association` is `MEMBER` only for public organization members; private members need the label too. In a private repository, drop `persist-credentials: false`: ocra fetches the pull request's commits with the checkout's credentials.

## A review your own developers cannot change

A workflow pushed by someone with push access gets the repository's secrets, and its `GITHUB_TOKEN` posts as `github-actions[bot]`, the account ocra trusts by default. To keep the review out of their hands, put three things where only your default branch reaches them:

1. **An environment for the secrets.** Create one, say `ocra-review` (Settings → Environments), allowing only your default branch under Deployment branches and tags. Move the model key there and delete the repository secret. A `pull_request_target` job runs on the default branch and gets them; a workflow pushed on another branch, or `on: pull_request`, does not.
2. **An account of ocra's own.** Create a GitHub App with repository permissions Pull requests (read and write), Checks (read and write) and Contents (read), and install it. Store its private key as the environment secret `OCRA_APP_KEY` and its client ID as the variable `OCRA_APP_CLIENT_ID`. On the default branch, set `github.botLogin` to the app's account, for example `{ "github": { "botLogin": "my-ocra[bot]" } }`, so a summary posted as `github-actions[bot]` counts for nothing.
3. **Review for the workflow and the configuration.** Protect the default branch and require a code owner's review for `.github/workflows/` and `.ocra/` (CODEOWNERS).

```yaml
name: ocra
on:
  pull_request_target:
    types: [opened, synchronize, reopened, labeled]

permissions:
  contents: read

jobs:
  review:
    if: >-
      (github.event.action == 'labeled' && github.event.label.name == 'ocra-review') ||
      (github.event.action != 'labeled' &&
        contains(fromJSON('["OWNER", "MEMBER", "COLLABORATOR"]'), github.event.pull_request.author_association))
    # One review per pull request at a time: a new push cancels the older run.
    # The key repeats the if:, so a run the if: skips gets a group of its
    # own and cannot cancel the review in progress.
    concurrency:
      group: >-
        ocra-${{ github.event.pull_request.number }}-${{
          ((github.event.action == 'labeled' && github.event.label.name == 'ocra-review') ||
           (github.event.action != 'labeled' &&
             contains(fromJSON('["OWNER", "MEMBER", "COLLABORATOR"]'), github.event.pull_request.author_association)))
          && 'review' || github.run_id }}
      cancel-in-progress: true
    runs-on: ubuntu-latest
    # Its secrets reach only jobs that run on the default branch.
    environment: ocra-review
    steps:
      - id: app
        uses: actions/create-github-app-token@bcd2ba49218906704ab6c1aa796996da409d3eb1 # v3.2.0
        with:
          client-id: ${{ vars.OCRA_APP_CLIENT_ID }}
          private-key: ${{ secrets.OCRA_APP_KEY }}
      # The default branch. Nothing from the pull request is checked out.
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          fetch-depth: 0
          persist-credentials: false
      - uses: ocrahq/Open-CR-Agent@c13507b6357ca73661d83f09a275d8aa49c4f688 # v0.26.0
        with:
          github-token: ${{ steps.app.outputs.token }}
          args: --max-cost-usd 2
        env:
          GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}
```

The rules for `pull_request_target` [above](#pull-requests-from-forks) apply. This exact setup has not been run end to end yet; if a step fails, [open an issue](https://github.com/ocrahq/Open-CR-Agent/issues/new/choose).

## Configuration

```json
{ "github": { "requestChanges": false, "botLogin": "github-actions[bot]" } }
```

`botLogin` is the account whose summary comment counts as ocra's earlier review; change it if you post with another token. Commands such as `@ocra override` never count from ocra's own summary or from model text, even when ocra posts with a person's token.

## From the command line

```bash
export GITHUB_TOKEN=...           # a token that can read the repository
ocra review --pr 42               # review and print, like a local review
ocra review --pr 42 --publish     # also post the review
```

The token comes from `GITHUB_TOKEN` or `GH_TOKEN`; for GitHub Enterprise Server set `GITHUB_API_URL` (for example `https://github.example.com/api/v3`). The repository comes from `--repo owner/name`, `GITHUB_REPOSITORY`, or an `origin` remote on github.com or on the server `GITHUB_API_URL` names. ocra fetches missing pull request commits.
